# `audit-core` obligations and how the sweep discharges them

The `audit` skill is the multi-domain sweep front door. Its step 0 states that the sweep "substitutes its own steps for the `audit-core` loop rather than running it, so it inherits none of that step implicitly" — which is a promise to restate every obligation it needs. A promise of that shape is not checkable by reading either file alone: `audit-core` states the obligation, `audit/SKILL.md` is where it is kept or dropped, and a dropped one is invisible because nothing in the sweep's text refers to what is missing from it.

This is that check, written down so it can be re-run rather than re-derived. One row per obligation `audit-core` states, with the disposition the sweep has chosen and where. Rows whose disposition is not **restated** are the interesting ones: each is a place the sweep deliberately diverges, and the "how" column is where that divergence is justified.

## Dispositions

| Disposition | Meaning |
|---|---|
| **restated** | `audit/SKILL.md` carries the same rule in its own words. |
| **adapted** | The sweep states a deliberately different rule, and says why in its own text. |
| **delegated** | Discharged by the `<domain>-audit` skill the sweep dispatches, which runs the real `audit-core` step. The sweep must not restate it, because restating it would give a domain agent two authorities for one rule. |
| **out of scope** | The sweep never reaches the obligation. Either it never reaches the step carrying it - report-only and fix-delegating, so the remediation half of the loop is structurally unreachable - or it reaches the step but the obligation exists to serve a later one it does not run. Both cases must name which, because the second is the one that can be wrong: an obligation that turns out to earn its keep at diagnosis time is a dropped obligation wearing this label. |

## How to re-run this check

Read `.agents/skills/audit-core/SKILL.md` whole — not a diff — together with every file in `.agents/skills/audit-core/references/`, because two sections of the engine live there and an obligation is `audit-core`'s wherever its text sits. For every sentence that tells a run to do something, find the row here. An obligation with no row is the defect this record exists to surface; add the row and either restate the obligation in `audit/SKILL.md` or record why it is not restated.

`tests/test_sweep_obligations.py` checks the half that can be mechanical: every anchor below occurs exactly once across `audit-core/SKILL.md` and its `references/` files, counted as one corpus so a sentence duplicated between two of them cannot satisfy the rule twice, every row carries a disposition from the vocabulary table above (parsed from this file, so the two cannot drift) and a non-empty justification, and every quotation in this document is verbatim from one of the files it describes. That catches the staleness mode this record is most exposed to — one of those files reworded, and the ledger silently stops describing it. Exactly once rather than merely present, because these anchors are short: a phrase that reappears in a later recap would let a row keep passing while the sentence it was written to pin got rewritten.

It also guards against the failure that would make all of the above worthless: a ledger the parser walks only part of, leaving a green suite behind while most rows go unexamined. Every table in this file must be one the parser recognises, no table row may be orphaned from its table, and an unreadable row is reported rather than skipped. Grouping the obligations under sub-headings is safe; a stray blank line inside a table is not silent.

What none of it can check is whether a disposition is *true*. That is the reading pass above, and it is the only thing here that catches a dropped obligation.

## The obligations

`audit-core`'s `## Running a route` obligations are **delegated** as a block, and that block is the one place in this table where the disposition is a design decision rather than an observation about what the sweep happens to say. The route contract describes frontmatter that `scripts/audit_checks.py` validates, so the sweep hands a dispatched agent a pointer to the section rather than a copy of it: a second prose description of validated fields is kept in step with the loader by hand, and a drift between the two reads as the contract disagreeing with itself. One route-contract obligation is **adapted** against that default, the sweep deliberately carrying a narrower form of it: choosing between an `argv_by_partition` key and the shared `argv` on a Yarn classic partition is a runner choice, so it sits in the bullet a Yarn classic agent is already reading, while the general rule over keys stays delegated. The runner obligations in the same section are **restated**, because the sweep's version says the same thing against a target's partitions and the inventory that enumerates them, which the engine has no use for - all but the `registry` field's own validation rules, which are frontmatter the loader checks and so fall back to the block default, leaving the sweep with the runner choice the field feeds and a pointer for the rest.

`audit-core`'s two `references/` files are dispositioned as blocks rather than sentence by sentence, and the reading pass should not expect a row per sentence inside them. `references/remediation-loop.md` holds the loop's steps 3 to 6, and the sweep is report-only and fix-delegating, so every obligation in it is the first out-of-scope case - structurally unreachable rather than reached and skipped. `references/authoring-a-new-auditing-skill.md` holds obligations addressed to whoever writes a check record, and a sweep run only ever consumes records it did not write, so record authoring has no addressee inside a run at all. Neither file gets a row per sentence; a sentence in either that seems to want a row of its own is covered by the block, and the way to disagree is to argue the block's disposition rather than to add a row beside it.
