# Audits

The standing records of what the `*-audit` skill family covers, each tracking the current state of the tree and regenerated or checked against it, alongside the dated verification records of what happened when the family's tooling entries were actually executed against a real target. The two tables below are the difference: a standing record goes stale by failing a gate, a verification record goes stale in silence when a tool changes version.

## Standing records

| Doc | Description |
|-----|-------------|
| [Handbook traceability matrix](handbook-traceability.md) | Every `##` section of the engineering handbook mapped onto the `*-audit` skill family: a class and a severity per clause, the checks it maps to, and the gap list ordered by severity. The severity × coverage cross-tab answers which high-risk clauses nothing currently checks. Generated from [`handbook-traceability.yaml`](handbook-traceability.yaml) by `scripts/render_handbook_traceability.py` — edit the YAML, never the Markdown |
| [Python fixture expectations](python-fixture-expectations.md) | What every `python:` tooling entry must observe when it runs against the seeded fixture partitions, written down before the run, under both grant states. The record states why that ordering is the whole point, so it is not restated here. Generated from `scripts/python_fixture_spec.py` by `scripts/render_python_fixture_expectations.py` — edit the module, never the Markdown |
| [TypeScript fixture expectations](typescript-fixture-expectations.md) | What every TypeScript command route must observe when it runs against the seeded npm and pnpm fixture partitions, written down before the run, under both grant states, with the TypeScript-route checks that get no expectation listed with their reasons. Generated from `scripts/python_fixture_spec.py` by `scripts/render_python_fixture_expectations.py` — edit the module, never the Markdown |
| [Sweep obligations ledger](sweep-obligations.md) | Every obligation `audit-core` states, and how the `audit` sweep discharges it: restated, adapted, delegated to the domain skill, or never reached. The sweep substitutes its own steps for the `audit-core` loop, so it inherits nothing implicitly — and a dropped obligation leaves no trace in the file that dropped it, which is what this record exists to make visible. `tests/test_sweep_obligations.py` checks what is mechanical — each anchor occurring exactly once across `audit-core/SKILL.md` and its `references/` files, counted as one corpus, a disposition from the vocabulary the ledger itself defines, a non-empty justification, and that no row escapes the checked set — but not whether a disposition is true, which is a reading pass |

## Verification records

| Doc | Description |
|-----|-------------|
| [Python fixture build smoke](python-fixture-build-smoke.md) | What happened when the five seeded Python fixture partitions were generated and every planted seed was put in front of a tool: what each partition committed, which tool or reading pass reached which seed, and the one seed nothing reached. It also carries the measured `pytest-randomly` shuffle seed, which the expectations record deliberately does not state - it is a property of the plugin's ordering rather than of the fixture definition, and the versions it was measured under are recorded beside it because it does not hold across them. A build gate on the fixture machinery, not the round that grades the `python:` tooling entries: no check record is corrected on its evidence |
| [TypeScript fixture build smoke](typescript-fixture-build-smoke.md) | What happened when the two seeded TypeScript fixture partitions, npm and pnpm, were generated: the manager versions each lock step ran under, what each partition committed, whether each lockfile resolved every pin exactly and put each dependency under the workspace member the expectations assume, and the measured vitest shuffle seed, recorded with the versions it was measured under. A build gate on the fixture machinery, not the round that grades the TypeScript command routes: no check record is corrected on its evidence |
| [TypeScript lens smoke run](typescript-lens-smoke-run.md) | What happened when every `typescript:` and `any:` tooling entry in `arch`, `deps`, `test` and `security` was executed against a real TypeScript repository, under both grant states: the result per entry, the defects the run exposed in tools that ran and produced nothing usable, and the records it corrected. Unlike the standing records above this one does not track the current tree - it is a dated finding about tool behaviour, and a tool that changes version can invalidate it without anything here failing |
| [Python lens smoke run](python-lens-smoke-run.md) | What happened when every `python:` tooling entry in `arch`, `deps`, `docs`, `security` and `test` was executed against five seeded Python partitions (uv, pip, poetry, pipenv, a PEP 751 pylock), under both grant states: the result per entry, the defects the run exposed in tools that ran and produced nothing usable, the records it corrected, and the seeded finding no tool reached. A dated finding about tool behaviour, not a tracked state of the tree - a tool version can invalidate it without any gate failing |

Its subject is the skills, not the audited codebase. Point-in-time audit reports of a specific codebase are that codebase's to keep, not this repository's. The `*-audit` family never writes one into the tree it audited: it writes to a path the caller supplies outside that tree and hands the report over, so the rule holds even when the codebase under audit is this one. This repo holds the handbook, the skills that audit against it, and the record of what they cover.
