# Goal

What this repository exists to deliver, stated once so that every issue can say which part of it the issue serves. The tracker is held against this document: an issue's `Serves:` line names an outcome below, a queue is composed in the order of the outcomes, and work in a "does not count" category is not opened as an issue without a reason recorded against this file.

## Deliverable

A productionization gap-assessment of an external agentic codebase against the engineering handbook in [`engineering/`](engineering/README.md), produced by running the audit skill family in [`.agents/skills/`](../.agents/skills) against that codebase as a Claude Code plugin. Two artifacts per audited repository: a **prose report**, ordered by area and priority, in two registers - *defects* (fix what exists: security, data exposure, unpinned dependencies) and *absences* (a phased adoption roadmap of the handbook's lifecycle) - and an **importable issue set**: one top-level epic, per-area child epics, findings clustered into labelled sub-issues, each body carrying `file:line` evidence and a handbook citation. The first recipients are two TypeScript document-management targets in one organisation, `<polyglot-monorepo-target>`, a pnpm and turbo monorepo of independently deployed services, and `<single-package-target>`, a Next.js application calling the provider SDK directly, and one Python target, `<python-target>`, the agent repository this handbook and the audit family were extracted from, whose earlier audit findings are on record. Every target's real name lives in the engagement's own records, never in this repository: this repository names no other project in its own organisation or its origin's. Two things travel with the reports: the audit family installs and runs as a plugin in the recipients' own organisation, and the handbook itself is handed over as a rendered document, so the reports cite a text the recipients hold. Beyond the engagement, the handbook is also published to the public, as an e-book and a paperback built from the same source.

## Outcomes

In order. The first is the one the deliverable is most blocked on.

- **O1 - The sweep gives an honest per-check status on the targets' actual shapes.** Reached when a full `/audit` run over `<polyglot-monorepo-target>` yields a findings matrix in which every check lands as `ok`, a finding, `not-applicable`, or `no-evidence` with its reason; every whole-graph metric states the graph scope - deployable, shared scope or undetermined partition - it was computed over; no check whose tools answer different halves reports `ok` with one half unobtained; every record declares its routes as data rather than prose, so nothing the harness holds a record to is inferred from typography; and every package manager a named target uses has been exercised against a seeded fixture with planted ground truth, so a tool that runs cleanly and reports half the truth is caught before a target meets it. Decided 2026-09-23: a package manager the family names and no named target uses waits for a target that needs it and is next-phase work. First because a wrong number in a client report is worse than a missing section.
- **O2 - Every handbook part the report must speak to has a lens or a stated report-only disposition.** Reached when the severity by coverage cross-tab in [`audit/handbook-traceability.md`](audit/handbook-traceability.md) shows no critical row unmapped. **Only critical rows count toward this outcome.** Decided 2026-09-17: a record for an Important or Minor unmapped row is welcome work when a target's report needs it, but it moves nothing this outcome measures and is not what a queue composes against O2 while a critical row stays unmapped. Of the lenses the epic planned, the model and provider supply chain has shipped, its row checked by `deps/model-pinning-and-eol`, `eval/reproducibility` and `data-protection/processor-register`; the other three - performance and observability, delivery trail, and the rest of the prompt-analyzer framework - belong to the next phase rather than to this outcome, decided 2026-09-23: none of them holds a critical row, so shipping or declining one moves nothing this outcome measures.
- **O3 - The issue set is produced by a script, not by hand.** Reached when `scripts/` holds an emitter that, given a sweep's findings file and a target repository, prints in dry-run mode the epic, child-epic and clustered sub-issue tree, with severity and labels throughout and `file:line` evidence and a handbook citation in every sub-issue body, creates nothing without an explicit flag, and has unit tests over its pure logic. The input is the findings file rather than the report's findings matrix because that matrix is capped to its significant rows by the report's own template, so an emitter reading it would drop the findings the report judged too minor to print and say nothing about having done so. The citation is asked of the sub-issue bodies because an epic aggregates findings across checks and has no single clause to cite, so requiring one there would be satisfied only by picking one arbitrarily. **Reached on 2026-09-17.** The emitter shipped in #129 against every clause above, its create path was exercised once against throwaway repositories, and #131's record and #10's dry run were produced with it; nothing remains for this outcome.
- **O4 - The sweep against `<python-target>` has been delivered, and it doubled as the family's gate.** It is both a recipient and the one target whose earlier audit findings are on record, so one full sweep against it is read two ways. As the gate: the diff against that record accounts for each finding as resolved, still open, or new, and every skill regression the run exposed is fixed or filed with a `Serves:` line. As the deliverable: the prose report is delivered and the emitter's dry-run issue set is reviewed for shape. Reached when both readings hold on the same run. It is the first target to deliver, because a repository with a known baseline is the only one where a missed finding is provable.
- **O5 - The plugin installs and runs in the recipients' organisation.** Reached when a member of that organisation has added the marketplace, installed the plugin and run `/audit` in one of the target repositories without help from this repository's maintainer, and what that session discovers as skills matches what this tree ships.
- **O6 - The handbook is handed over as a document.** Reached when the rendered handbook, one self-contained page built from [`engineering/`](engineering/README.md), has been delivered to the recipients alongside the first report, so every handbook citation in a report resolves to a text they hold. Handbook prose work serves this outcome whatever prompted it: a clause the recipients would act on counts, whether a target's report or this repository's own way of working surfaced it. **Current, not aspirational.** Decided 2026-09-17: the rendering pipeline exists in `scripts/render_handbook_artifact.py`, so this outcome is an activity to pick up, rendering the page and preparing the handover, rather than a design question.
- **O7 - The two client targets' sweeps have been delivered.** Reached when `<polyglot-monorepo-target>` and `<single-package-target>` each have a prose report delivered to the recipients and a dry-run issue set reviewed for shape, both from one run through the installed plugin, and every skill regression those runs exposed is fixed or filed with a `Serves:` line. Decided 2026-09-24: O1 measures whether the statuses are honest, read off the polyglot target's run; this outcome measures that both client reports reached the recipients, the way O4 does for `<python-target>`. The polyglot report comes from the run O1 reads, so that target needs no second sweep.
- **O8 - The handbook is published as an e-book and a paperback.** Reached when an EPUB built from [`engineering/`](engineering/README.md) by a script in this repository, reproducible from a tagged commit, passes `epubcheck`, carries the same heading ids as the rendered page, has working figures, in-book links and table of contents on two reading systems, and is available to the public through a channel the maintainer chose, under a licence the content's owner granted; and when a paperback whose interior and cover are built from the same source and the same tagged commit, carrying the same heading ids, has been accepted by KDP's previewer, checked as a proof copy and put on sale. Decided 2026-09-24: the maintainer chose to publish the handbook beyond the recipients, as a free EPUB and a print-on-demand paperback, and to build Markdown to EPUB with pandoc directly rather than through an AsciiDoc tree, so `engineering/*.md` stays the one source and a citation a report emits names the same id in the book as on the page. Handbook prose edits made for an outside reader serve this outcome, where O6 claims those a recipient would act on. It is last in the order because it widens who reads the handbook and no target's delivery waits on it.

## Does not count

Work this repository can absorb indefinitely and has decided not to. An item in one of these categories is written under `## Found, not fixed` in the pull request that found it, and becomes an issue only when the batch review returns `open` for it.

- **Verification-harness self-consistency beyond what a route or a fixture exercises.** Guards that hold one internal table against another, where no record's route and no seeded fixture reaches the difference. The routes and the fixtures themselves serve O1; a third layer of guards over them does not.
- **The engine's prose style and word count.** Settled by eval where it is settled at all, never by trimming to a number.
- **Repository housekeeping.** Conventions-file edits, dependency gates, run logs. Done inside the pull request that needs them, not as issues of their own.

## Done when

Every named target, `<python-target>` and the two TypeScript ones, has a delivered prose report and a reviewed dry-run issue set; the handbook has been handed over and its first public edition published in both formats; and every regression in the family those runs exposed is fixed or filed. The `<python-target>` run comes first and is O4; the two client runs are O7, the polyglot one read against O1 first.

## How the tracker uses this

- Every issue body carries `**Serves:** O<n>`. An issue that cannot name one is either a gap in this document or not work, and which of the two is the maintainer's call, recorded here. The one standing exception is the programme epic that spans the whole deliverable, whose children each name their own outcome: it carries `**Serves:** the deliverable` instead. Decided 2026-09-24.
- A queue for a batch of work - a nightshift, a sprint - is composed against the outcome order above, and at least four of every five items serve a named outcome.
- Next-phase work, a lens or capability this phase decided not to measure, carries the `Next phase` milestone and `**Serves:** next phase` in place of an outcome, until the next phase's goal document names one. A queue composed against this document does not draw from it.
- Something found while implementing goes under `## Found, not fixed` in the pull request body, one line each, and is triaged when the batch closes.
