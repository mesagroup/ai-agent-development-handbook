    kind: procedure
    applies_when: >-
      The CI platform is GitHub Actions, whose workflow syntax this reading names.
    note: >-
      Read the top-level and per-job `permissions:` and every read of the `secrets` context. Confirm least privilege, that no secret is echoed to a log, and that no secret or write-scoped token is in the effective scope of a run of a job that executes untrusted code. The definitions of a secret in scope and of untrusted code below are this record's, and `ci/trigger-safety` cites them for its two triggers. Each is a property, and the spellings given for it are examples of that property rather than a list to match: a spelling not named here that has the property is the same thing.

      **What is in scope.** For a job, read everything it can reach rather than only what it names. A secret is in scope when the job's own definition, under any key and in any step, or the workflow-level `env:` it inherits, reads the `secrets` context in any form - `secrets.NAME`, `secrets['NAME']`, `toJSON(secrets)`, the last putting every secret in scope - and, for a called workflow, when the call passes it, by an explicit `secrets:` mapping or by `secrets: inherit`. The `secrets` context's `GITHUB_TOKEN` entry, in any spelling (`secrets.GITHUB_TOKEN`, `secrets['GITHUB_TOKEN']`), is not one of those: it is the job's token, spelled like a secret, and it is judged by its permission like `github.token`. A read of the whole context, such as `toJSON(secrets)`, still puts every other secret in scope. The job's token is always in scope, with the permission its call chain gives it, read as below. That is what the job can reach; the effective scope is what a run of it receives, and it is judged per run, once for each kind of run in which the job executes untrusted code - each trigger, and for the three `pull_request` events below a fork run and a run from a branch of the repository apart - since each receives something different, and a way of reaching the job that several such runs share takes the most severe of their verdicts. A run receives what its job reads and what its token's permission gives, except where GitHub withholds some of it. A fork run of `pull_request`, `pull_request_review` or `pull_request_review_comment` is one such run: GitHub's events reference says such a run gets no secret but the job's token, and that token read-only, whatever the job reads and whatever its blocks grant. On a repository that is not public, the repository or organisation settings that send write tokens and secrets to workflows from fork pull requests can give such a run back what its job reads and its blocks allow, never more, and the clone shows neither setting. So a fork run's effective scope is the read-only token and nothing else where the audit establishes that the repository is public or that both settings are off; where the audit establishes that one is on, the run also receives what that setting sends - the secrets the job reads, or its token at the permission its blocks give; and where the audit cannot establish a setting, what that setting would send is what the clone cannot resolve, naming the setting, unless even with it the run would hold no secret and a read-only token. The token's permission is read level by level down the job's call chain, the calling job at the top and each called workflow's job below it. At each level the job's own `permissions:` block replaces its workflow's top-level block rather than narrowing it, so a level's block is the job's where it has one and else the workflow's, and a level with neither passes on what it receives; across a call, each lower level can only narrow what the level above grants. So the blocks are read per scope: a scope is settled without a write where any level's block grants it no write - `read`, `none`, or nothing at all, which is what a block gives a scope it omits, so `read-all` and `permissions: {}` settle every scope that way - and settled as a write where the top level sets a block and every level that sets one grants that scope write. The token is settled read-only where every scope is settled without a write, and settled as holding a write where any scope is settled as one; otherwise the blocks settle nothing, and the permission rests on the repository's default at the top of the chain, which the clone does not show. A token is read-only for a run where that fork rule fixes it so or where the blocks settle it so. It holds a write for a run where the blocks settle one and the run does not fix it read-only: a fork run's token holds one only where the audit establishes that the setting sending write tokens is on, and where the audit cannot establish that setting, the write the blocks settle is what the clone cannot resolve, naming the setting. This axis reads the `secrets` context and the token only.

      **Untrusted code** is code an outside author, one without write access to the repository, controls, and a job executes it wherever it lands. The pull request's code reaches a job by any step that fetches it - an `actions/checkout` whose `ref:` or `repository:` names the head sha or ref, the merge commit, a `refs/pull/<n>/` ref or the head repository, a `git fetch`, `git clone` or `gh pr checkout` of it, a package install from the head repository, or under `workflow_run` the triggering run's `head_sha`, `head_branch` or `head_repository` where that run's own event starts with `pull_request`, `pull_request_target` included, since after another `workflow_run` those fields name the default branch and the pull request's code is reached only by looking it up - and content derived from untrusted code reaches a job without any fetch of the pull request: an artifact whose content came from the pull request's code or from another such artifact, whether the run that made it executed that code or only built, packaged or copied it, and whether it was downloaded directly or passed on through other runs, by `actions/download-artifact` given a run's id or by any other step, and a `needs:` output computed from such content. An artifact or output of that kind that names a ref the job then fetches is a fetch of untrusted code, because the outside author could choose the ref; only executing its content is consuming it, and only where the artifact's origin cannot be traced is the ref something the clone cannot resolve. It executes in any step that runs what was fetched or consumed: a script, a local action, an install step whose hooks it supplies, a build tool reading its configuration from it, a script sourced from or written by an artifact's content, and an artifact's or output's content spliced into a shell command at run time, as `eval "$(cat pr.txt)"` does. Reading an artifact as data - a pull request number checked to be one, a coverage figure posted as a comment - is not executing it, and text a `${{ }}` expression interpolates into a `run:` script is `ci/workflow-correctness`'s injection axis rather than this. A reusable workflow the job calls and a composite action it uses are read through, as part of the job and under the caller's trigger, with the caller's `with:` inputs and passed secrets bound into them, so a ref or a secret that arrives as an input is the same as one written in place.

      A fetch the fetching tool refuses is not a fetch. `actions/checkout` carries a guard from v7.0.0, and from v2.8.0, v3.7.0, v4.4.0, v5.1.0 and v6.1.0 in the older majors, which fails the step rather than check out a fork's code. A checkout the list above counts as a fetch is refused, and so is not a fetch, only where all of these hold. First, the code it runs carries the guard: judged by the release a `uses:` tag, branch or sha resolves to when the audit runs, so `@v1` and any release before those carry none, and a vendored copy is judged by its own code. Second, the step's `allow-unsafe-pr-checkout` is off, which it is only where it is absent or a literal other than `true` in any letter case; an expression an outside author can make evaluate to `true` is on, and any other expression is a value the clone cannot resolve. Third, the event is `pull_request_target`, or a `workflow_run` whose triggering run's own event starts with `pull_request`, since under any other `workflow_run` the guard lets every checkout through. Fourth, the values the step receives at run time, its repository, ref and resolved commit, include the event's head repository, a `refs/pull/<n>/` ref, or a head or merge sha the event payload carries, since the guard compares those values and lets anything else through, a sha looked up after the event among them. Such a checkout failing any of the four is a fetch of untrusted code, and one where the audit cannot establish a part, such as which release a sha pin or a remote fork of the action is, is something the clone cannot resolve; a comment naming a release beside a sha is a claim, not that establishment. The guard refuses only a fork's code, so a checkout it refuses still fetches the head of a pull request from a branch of the repository itself. That is not a fetch of untrusted code: it is a gate in the sense `ci/trigger-safety` states, applied by the action rather than written in the workflow, because only someone with write access can push a branch there. It holds only while no workflow in the repository pushes an outside author's code to a branch here, as an "ok-to-test" or mirror job does, since that job lends the author its write access; where one does, the checkout is a fetch of it. A job whose other steps fetch the pull request's code without that guard is read on those steps. Every fetch above other than a guarded checkout stays one.

      **Which trigger, and which record.** Read this under every trigger, and decide ownership per way the untrusted code reaches a job, not per job. `ci/trigger-safety` owns one way: the pull request's code fetched and executed under `pull_request_target`, or under a `workflow_run` it counts, and that is reported there and not here. This record reports every other way, in the same job or another: untrusted code fetched and executed under any other trigger - an `issue_comment` job running `gh pr checkout`, for one - and an artifact's or output's content executed under any trigger. One job reached both ways is one row in each record, because each way has its own fix. A fork run of those three `pull_request` events is judged by its effective scope as defined above, so on a public repository it has nothing to expose on this axis.

      **The verdict** is taken per axis, and a job can carry a row on each. On the untrusted-code axis, for each way the code reaches the job that this record owns, the first that applies: a run whose effective scope holds no secret and whose token is read-only, as defined above, which has nothing to expose and is `ok` whatever else the clone cannot see about the code; then a gate, as `ci/trigger-safety` states it, releasing the code only after a writer's condition gives `ok`, or `warn` where its force is a repository setting, as that record says; then the band, where what the clone shows is enough - a secret in the run's effective scope, or a token that holds a write for that run, as defined above, in a job executing untrusted code - which is the Critical band's `violation`; then what the clone cannot resolve, where what it holds neither makes the band nor clears it - a workflow or action from another repository, a ref computed at run time, an artifact from a run the clone cannot trace, the fork settings above, or the repository's default token permissions where neither the blocks nor the fork rule settle the token's permission and no secret is in the run's effective scope - which is `warn`, naming what would settle it and who holds it, never `ok`; otherwise `ok`. The other two axes are judged whether or not a gate exists, since a gate releases code and not a log or a scope. A secret echoed to a log is the Critical band's `violation`. On least privilege, a `write-all` or write scope where read suffices, or a long-lived cloud credential where the platform offers OIDC, is the Important band's; a job where no level of its call chain sets a `permissions:` block - its own job and workflow, and for a called workflow its caller's - runs on the repository's default token permissions, which the clone does not show, so it is `warn`, naming that setting and whoever administers the repository, and never `ok`. A row records the workflow, the job and the axis. An untrusted-code row adds the trigger, how the code reaches the job and where it executes at its `file:line`, the gate if any, and each secret and the permission in scope with where it comes from. A log row adds the step that echoes the secret at its `file:line`. A least-privilege row adds the permission or credential and where it comes from.

# Permissions / secrets

Over-broad `permissions` (`write-all` or a write scope where read is enough, or no block, which leaves the repository's unseen default); secrets or a write-scoped token in reach of steps that run untrusted code, whether that code was fetched or arrived as a run's artifact or output; secrets echoed to logs; long-lived cloud credentials where OIDC/short-lived would do.

## Severity

**Critical** - a secret or a write-scoped token exposed to untrusted code, or a secret leaked to logs.

**Important** - over-broad `write-all` or write-scoped permissions where read suffices; long-lived cloud credentials where OIDC is available.

## Fix

Set top-level `permissions:` to least privilege (`contents: read`) and widen per-job only as needed.

**Replace long-lived secrets** with OIDC / short-lived credentials where the platform supports it.

**Keep untrusted code away from what it can use:** never execute an artifact's or output's content derived from untrusted code, whether the run that made it executed that code or only packaged it, in a job holding a secret or a write token, and read it as data with its shape checked instead; under a trigger an outside author can cause whose run receives a secret or a write token, fetch the pull request's code only after a writer's gate, into a job with no secret and a read-only token; on a repository that is not public, keeping the settings that send secrets and write tokens to fork pull requests off gives the three `pull_request` events that job by default.

**Keep secrets out of logs:** pass a secret by environment or file rather than on a command line, never print one, and mask any value derived from one with `::add-mask::`.

## Review lens

**Pipeline-security correctness** - is each trigger/permission/injection finding a genuine attacker path, and does the fix remove it (not just move the secret to another reachable step)?

**Least privilege preserved** - permission reductions didn't break a job that genuinely needed the write scope.
