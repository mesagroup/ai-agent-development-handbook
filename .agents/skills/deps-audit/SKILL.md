# Dependency Audit (licenses + supply chain)

A domain specialization of **[audit-core](../audit-core/SKILL.md)** - read that first; it owns the loop, the `## Running a route` contract that turns this skill's records into commands, and the cross-cutting rules. The checks are records in [`checks/`](checks/) beside this file; load the ones your slice needs, not the directory. This skill supplies the dependency lens. It owns the whole *third-party* surface; first-party code security and what the project's agents are granted belong to `security-audit`.

**Core principle:** the license verdict here is relative, not absolute - whether a copyleft dependency is a problem at all is judged against *this* project's own license and distribution model, not a universal rule. Most of the risk arrives transitively: a CVE or a copyleft license several levels down in the resolved graph binds the project exactly as much as one in a direct dependency, so the resolved graph, not the declared one, is ground truth. **That holds wherever a graph is resolved at all, which the model surface is not**: nothing resolves a model identifier, so `deps/model-pinning-and-eol` reads the declaration itself and the provider's own schedule, `deps/model-catalog-indirection` reads the path by which the declaration was reached, and the ground truth of both is the naming site rather than a graph below it.

**Announce:** "I'm using the deps-audit skill (on the audit-core engine) to audit the dependency surface."

**Not for:** first-party application-code security and what an agent is granted (use `security-audit`) or the pipeline's own supply chain (use `ci-audit`).

**Subject:** the project's declared and resolved dependency graph, and the licenses/vulnerabilities/freshness/usage of every node in it - plus the models and provider endpoints the application configures, which are dependencies with a version and a lifetime even though no package manager resolves them, and which `deps/model-pinning-and-eol` and `deps/model-catalog-indirection` read from the project's own configuration rather than from a lockfile - the first for the identifier's version and lifetime, the second for whether the identifier was reached through a catalog at all. Establish two things first, because they change the verdicts:

- **The project's own license** (the partition's manifest - e.g. `pyproject.toml` `[project] license` / classifiers for a Python partition, `package.json`'s `license` field for a JavaScript one - or a top-level `LICENSE`). Copyleft-compatibility is judged relative to it.
- **Distribution model** - is this a library published to an index (copyleft in a dependency is then high-stakes) or an internal/app deployment (copyleft is usually lower-stakes, but still policy-dependent)? Ask if unclear.

**Detect** the package manager and lockfile from the project inventory, which already records both per partition, and use its resolved graph as ground truth (transitive deps matter - most CVEs and copyleft licenses arrive transitively). **The model surface has no entry in that inventory**: its evidence is the application's own configuration. Where a sweep has already built data-protection's shared provider surface, `deps/model-pinning-and-eol` starts from it rather than building a second free to disagree with it; where none exists, which is every direct invocation of this domain, it works from the same homes and says in the report that it did. That surface is every outbound edge rather than every model provider, so it narrows the search and does not answer it - which of those edges serve model inference is the record's own work, and treating all of them as model providers reports a project with an error tracker and no model at all as running an unpinned default. It never withholds an answer for want of that artifact either, because whether the target processes personal data decides nothing about whether its models are pinned. A partition may declare dependencies in an ecosystem the rest of the repository does not use, and each declaration site is its own graph: a repository with a JavaScript lockfile and two Python requirements files has three, and auditing only the first reports the other two as clean. A manifest commonly separates dependency classes - production, optional or extras, and dev or peer groups - and each is a candidate for the resolved graph; scope out dev-only dependencies only if the distribution model justifies it, since a dev-dependency-only CVE or license issue is a routine finding otherwise missed.

Every `deps` check is **global**, which means whole-subject rather than single-partition: for six of the eight the subject is every resolved graph the target declares, taken together, so one agent walks all of the declaration sites and no check is sliced per partition. **For `deps/model-pinning-and-eol` and `deps/model-catalog-indirection` the whole subject is every place the application names a model or a provider endpoint**, which no graph contains, so they are global for the same reason and over a different subject - and the command advice in the rest of this paragraph reaches them nowhere, because neither prescribes a command. Global is not a licence to audit one graph and call the subject covered. **A workspace is the case where a single command quietly breaks that rule**, because the package manager's own subcommands disagree with each other about it: on one pnpm workspace `pnpm audit` and `pnpm licenses list` covered all 9 manifests by default while `pnpm outdated` covered only the root's 10 declared dependencies out of 254, reporting nothing to say the rest were never read. Check each command against the manifest count you established here, and reach for its recursive form (`-r`, `--workspaces`, the manager's equivalent) rather than assuming the default matches the subject.

Status per row: **ok / warn / violation** (for licenses: allowed / review-needed / disallowed). Suppressions (a known-accepted CVE, an approved license exception, a deliberately floating model alias, a migration off a sunset model that is scheduled rather than done, a call site that bypasses the model catalog on purpose) must be explicit and recorded with a reason - never silently dropped. The floating alias and the scheduled migration carry a date or a replacement as part of the reason, so that an audit taken after the date reads a broken promise rather than a clean result.

Most fixes here **touch the manifest / the lockfile / CI config**, so they are **not** docs-only: the domain gate is "the lockfile still resolves **and** the test suite passes." Take the actual install and test commands from the inventory's package manager and test runner rather than assuming one ecosystem's. **That gate is vacuous for a fix on the model surface**, which touches configuration no package manager resolves and changes behaviour no unit test asserts: it can come back green over a pin that now names a different model. `deps/model-pinning-and-eol` states its own close instead: the migration or the pin, plus a behavioural re-check on the project's own eval or smoke harness, because the model the product answers with has changed and nothing in this gate reads that. `deps/model-catalog-indirection`'s fix moves identifiers without changing which model runs, and its close is the check that the identifier resolved at each moved site is the one that was written there before. Add a **license allowlist/policy** and/or a CI gate (a vulnerability/license scanner matched to the partition's ecosystem, e.g. `pip-audit` / `pip-licenses` for Python) so the finding can't silently recur - this is the highest-leverage fix. Docs-only outputs: a `NOTICE`/`THIRD-PARTY-LICENSES` file, a generated SBOM, or the audit report itself.

**Opt-in deliverable:** SBOM generation (CycloneDX) as a deliverable - enable via argument or ask the user. The opt-in *checks* - SBOM completeness and the transitive-license deep dive - are `deps/inventory` and `deps/transitive-licenses`, loaded like any other.
