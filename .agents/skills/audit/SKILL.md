# Audit - the multi-domain sweep front door

The front door to the `*-audit` family. It runs several domain audits **at once**, each as a read-only subagent, and consolidates their findings into a single report. It does not add a new lens of its own - it orchestrates the existing ones (`docs-audit`, `deps-audit`, `arch-audit`, `security-audit`, `ci-audit`, `test-audit`, `eval-audit`, `prompt-audit`, `data-protection-audit`), all built on **[audit-core](../audit-core/SKILL.md)**.

**Coverage record:** which clauses of the [engineering handbook](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/engineering/README.md) each domain skill actually checks is recorded clause by clause in [handbook-traceability.md](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/audit/handbook-traceability.md), and the gaps in domain coverage - what no skill can see yet, and which issue would fix it - are tracked there. Both links are absolute: this family ships as a Claude Code plugin and runs against other repositories, and what it emits is copied into reports whose readers hold neither this repository nor the plugin cache, so a relative path would reach nobody.

**Core principle:** a sweep is for *breadth* - surface where the repo hurts across every dimension, cheaply and in parallel, without changing anything. Depth and fixes are a deliberate follow-up, one domain at a time. So this skill defaults to **report-only** and fans out; it never runs fixes in parallel (see "Fixes are delegated").

**Announce:** "I'm using the audit skill to run a multi-domain audit sweep (report-only) and consolidate the findings."

## When to use

- A whole-repo health check: "is this shippable / where are the problems?"
- Before a release, a public/open-source push, or an onboarding, when you want breadth across quality dimensions in one pass.
- The user says "audit the repo", "run all the audits", or names several domains at once.

**Not for:** a deep single-domain audit **with remediation** - invoke that domain's skill directly and by its qualified name (`handbook-audit:ci-audit`, `handbook-audit:deps-audit`, …), which runs the full audit-core loop through remediation. This front door is diagnosis-across-domains, not fix-one-domain-deeply.

## How it works

### 0. Scope + mode

- **Scope - argument-first.** `/audit` (no args) or `/audit all` → every available domain. `/audit ci security test` → just those. **Detect which domains are available from this skill's own siblings**, at `../<domain>-audit/checks/` relative to this skill's directory: a domain is available when that directory exists and holds at least one record. Resolve it relative to *this skill*, never to the audited repository, because a path relative to a repository root resolves inside the target: it finds nothing in a repository that has never carried the family, or the target's own copy in one that has, and either way the sweep reports a scope it did not audit. The audited repository's own skills, if it has any, are evidence for the prompt domain and are never the lens. **If the user explicitly names a domain that has no such checks directory, tell them it was skipped (and why) before fanning out** - never drop a requested scope silently. If the invocation is interactive and the scope is genuinely unclear, ask with the ask-the-user tool - but note that tool caps a question at **4 options**, so do **not** try to render every available domain as one checklist; offer a coarse choice instead (e.g. *All (recommended)* / *A subset I'll name* / *Just the security-relevant ones: security + deps + ci*). **Default = all.**
- **Mode - report-only by default.** The sweep produces findings, changes nothing, creates no branches/commits/PRs. Only ask about report+fix if the user explicitly wants fixes in this run - and then still hand each fix to the per-domain skill (see below), do not fan fixes out.
- **Opt-in sub-audits - resolve them here, once, for every selected domain at once.** A record carrying `optin: true` is a deeper pass the user chooses rather than a check the sweep owes them, and the fan-out is the wrong place to choose: parallel domain agents have nobody to ask, so an agent left to decide either skips a pass the user wanted or spends the run on one they did not ask for. Take each record's own default from its prose where it states one and off where it states none, then ask once for whatever that leaves undecided - one coarse question, within the same 4-option cap the scope question is subject to, not one question per domain. Pass each domain the list of its own opt-ins that were granted, and record in the report which were offered and which were granted, so a reader can tell a pass nobody asked for from a pass that found nothing. Granted is not the same as ran: a granted check that no tooling could answer is `no-evidence` in the matrix like any other, and the two belong in different places. **That list is the answer to the question the domain skill would otherwise ask** - so a dispatched domain agent takes the granted list as given and neither re-asks nor decides for itself. A second class is **not** resolved here: the opt-in *deliverables* a domain skill declares in its own prose rather than through a record - an SBOM, a generated layering-contract config, a rendered metric report - are **out of scope for a sweep however the user answers**, because each is an artifact *of* the audited project rather than findings *about* it, and producing one on the strength of a diagnosis nobody has read yet is the writing this skill exists not to do. Offer it in step 4 as a per-domain follow-up instead.
- **Inferred rubrics - settle here what a domain may judge against when the target documents no rule.** The bullet above reasons that a user-decidable question cannot be left to a parallel agent; this is the same class of question and it needs the same treatment. `audit-core` says to discover conventions from the target and "impose a standard only if none exists, **and confirm it with the user**", and a domain skill that finds nothing documented is told to infer a rule and confirm it before flagging anything against it - layering is where the family meets this most often. A dispatched agent has nobody to confirm with, and leaving it there hands it two exits while choosing neither: flag violations of a rubric nobody agreed to, which consolidation then forbids you to soften because the domain owns severity, so an invented standard is laundered into the roll-up as confirmed findings; or drop the domain's central check, which arrives as a near-empty matrix that reads as a clean lens. **So the sweep authorises no inferred rubric.** Pass a rule where the inventory or the user supplies one; where none exists, tell the agent to report *the absence* as the finding - "no layering rule is documented, so conformance to one is unassessed" - and to flag no violations against a standard it invented. That is not a weaker answer: a sweep is diagnosis, "you have not written this down" is a diagnosis, and "you violate the rule I made up for you" is not one.
- **Domain-scoping declarations the target's own nature settles - ask them here, once, for the domains selected.** A few domains are about a subject a repository does not always have, and `data-protection-audit` is the first: whether the target processes personal data at all decides whether its rows are findings or noise. It is the same class of question as the three bullets above and gets the same treatment, because a dispatched agent has nobody to ask and both of its wrong exits look like success - a target holding no personal data collects a stack of Criticals for a register it never needed, or the domain quietly reports nothing and reads as a clean privacy posture. **Ask the operator, pass the answer, and record it in the report as a declaration rather than as a finding**, because it is an assertion about the target made from outside it and no repository confirms it. Answered no, say in the roll-up that the domain was out of scope and why, the way a domain the user named with no checks directory is reported - never as `not-applicable` rows, which is a claim about a partition's languages and not about what the target does. Where the answer is unavailable, the domain skill's own default governs and the sweep does not invent one.
- **Grants for tooling that needs more than a read-only clone - resolve them here too, once, for the whole sweep.** A record classifies each of its routes by what must be present before it answers, in the route's own `needs`: absent means source, manifests and lockfiles suffice, `resolved-tree` means the dependency graph must be materialized, `target-execution` means the tool also runs code from the target's graph - the target's own, or an installed package's, which starting the partition's interpreter does through its `.pth` files, so any route whose command starts that interpreter needs it, which includes every `in_env` Python route and so Python's in-environment licence and freshness scanners. Both of the latter are permissions, both are off by default, and they are separate - a user who agreed to have the tree materialized and its metadata read has not thereby agreed to run a stranger's test suite in this environment. This is the same class of question as the two bullets above and gets the same treatment: ask once, before anything fans out, because a dispatched agent has nobody to ask and will otherwise either skip a check the user would have allowed or reach for an install nobody sanctioned. Pass every domain the grants that were resolved, whether or not that domain has a check needing one. Where a grant is withheld, a check whose every answering-kind, non-`forbidden` route in a partition's language needs it is `no-evidence (not-permitted)` - which is a different report from `no-evidence (tool-unavailable)` and must not be merged into it - **unless the record keeps an untiered answering route in that language, in which case that route runs and the check reports the domain's own status on what it answers with the missing evidence stated, and only `answers_ungranted: none` leaves `no-evidence (not-permitted)` standing for the check as a whole.** A withheld grant is not the same as an unanswerable question, and on the current record set most of the checks it silences can still answer something. `answers_ungranted` carries no prose of its own - it takes only the sentinel `none`, present exactly where every route able to answer the check in a language needs the withheld grant, and absent wherever the record keeps an untiered route there instead.
- **Target and output - resolve all three here, exactly as `audit-core`'s scope-and-mode step defines them**, before anything fans out: `target_root` (`git rev-parse --show-toplevel`, resolved to a real path, never inferred from the working directory), `target_ref` (the `HEAD` short SHA, the branch name, and whether the tree is dirty), and `out_path` (ask for it, and refuse any path resolving under `target_root`; the consolidated report is **always** returned in conversation as well, so a run given no path is never silent, and a non-interactive run therefore **defaults to** conversation only, writing a file only where the invocation itself supplied a path). This sweep substitutes its own steps for the `audit-core` loop rather than running it, so it inherits none of that step implicitly - and every step below names all three, so leaving them unresolved here is what lets a sweep invent an output path or audit whichever tree the shell happened to be in. Which `audit-core` obligations the sweep restates, which it adapts, which it delegates to the domain skill and which it never reaches is enumerated in [sweep-obligations.md](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/audit/sweep-obligations.md), because a promise to restate is not checkable from either file alone: a dropped obligation leaves no trace in the file that dropped it.

### 1. Fan out - one read-only subagent per selected domain, in parallel

**Build the project inventory first, once, and pass it to every domain.** It is `audit-core`'s parallel evidence step's shared ground-truth artifact, and the sweep is where the saving is largest: nine domain agents would otherwise each re-derive the same partition and language map over the same tree, and be free to disagree about it. Building it here also means a domain that needs only one field of it does not pay to discover that field itself.

**Classify each partition's languages by a file census plus declaration files, never from the presence of a manifest.** A partition's language is a set, not a single value, and a package carrying a JavaScript manifest for monorepo wiring while holding only Python is classified as JavaScript by any "has a manifest, therefore" rule - whereupon the wrong toolchain runs against no matching source, finds nothing, and reports a pass. In a sweep that misclassification is not contained: every selected domain consumes the one artifact, so all of them inherit it at once and agree on a clean bill of health for code none of them looked at, which reads as corroboration across lenses rather than as the single error it is. The sweep builds the artifact, so the sweep owes the rule - a domain agent handed the inventory cannot re-derive what it was given.

**Classify each partition as a deployable or a shared package while building the inventory, and record the reason where you cannot.** `audit-core`'s graph scope is read from this field, so a domain agent handed the inventory has nothing to derive and nothing to decide: a partition carrying its own deploy artefact - a container file, a deploy or serverless manifest, a CI job that deploys it, an application entry point - is a deployable whatever imports it, since a test, end-to-end or tooling partition that depends on an application does not make it a library; a partition with no such artefact that another partition imports, by a manifest dependency on it, by workspace protocol or by name, a build tool's dependency edge or a source import that resolves to it, is a shared package; and a partition with neither is recorded as undetermined with what was looked at, which is what tells the whole-graph `global` checks to compute per partition and say so rather than across the repository. Record beside each shared package which partitions import it, and list the shared scopes: the groups of shared packages connected by the import edges between shared packages, in either direction, a manifest dependency, by workspace protocol or by name, a build tool's dependency edge, or a source import resolved to the other package whether or not a manifest declares it, each named with its packages, a shared package with no such edge forming a scope of its own whatever deployables import it, so that every shared package is in exactly one. A domain agent reads the scopes off the inventory and never regroups them, because two domains grouping differently would report one library's findings under two names. A single-partition target is one deployable whatever the two signals say of it, undetermined never, since there is nothing to split; the field is still written, because the scopes list a domain returns and the report's scope line both read it to print `one deployable`.

**If either grant was given, materialize the tree once here too, and pass its path.** `target-execution` implies `resolved-tree` - the target's own code imports from the tree - so a sweep granted execution alone builds the tree here as well, rather than handing a domain agent a test command to run against an unresolved graph. It is `audit-core`'s parallel evidence step's shared-artifact rule applied to the most expensive artifact in the family: nine domain agents each copying the target and resolving its graph would spend nine installs to produce nine trees that are supposed to be identical, and would be free to disagree about the one thing the grant was obtained to establish. Copy the target to a scratch directory that does not resolve under `target_root`, resolve there with `--ignore-scripts`, and hand every domain the path plus the resolver command and whether the lockfile was frozen. **Tell every domain the tree is shared and that it may not install into it**, which is the cost of building it once: a check needing a package the target does not declare, such as a missing coverage provider or a mutation runner's plugin, copies that tree and installs into the copy, because adding it in place changes the graph every other selected domain is measuring at the same moment and leaves a dependency in the tree `deps` reads that the target never declared. **Tell every domain that an evidence pointer taken from that copy is expressed relative to `target_root`, never to the scratch tree** - the matrix requires a `file:line` on every row, a tool run against the copy reports the copy's paths, and a row carrying one cites a temporary directory that exists only inside this run, which the audited team cannot open and the consolidation step cannot repair because it never saw the tool output. An install hook is `target-execution` however it is triggered, so a tree that will not resolve with scripts disabled needs that grant as well or stays unresolved - do not quietly drop the flag to make an install succeed. The target itself is never installed into, and `git worktree add` is not a shortcut around that: it writes `.git/worktrees/` and leaves the working tree clean, so it passes the check in the cross-cutting rules below while breaching the invariant that check exists to enforce.

Dispatch all selected domains **concurrently** (a barrier - collect the matrices before consolidating; a domain that errors does **not** block the others). Give each subagent:
- `target_root`, `target_ref`, and **the requirement to confirm its own `git rev-parse --show-toplevel` matches `target_root` before it reads anything** - passing the path is not enough on its own, because an agent that resolves the tree itself lands in the primary checkout whenever the sweep runs from a worktree, and then reports ground-truth evidence from a tree nobody is auditing with nothing in its matrix to say which tree that was. Here the cost lands on a whole domain at once: one unconfirmed agent is one lens of the consolidated report answered against the wrong tree, and the roll-up gives a reader no way to tell that lens from the others.
- **This domain's granted opt-ins, named as a list, even when it is empty** - an empty list said out loud is what stops an agent treating the omission as a question it should answer itself. Step 0 already decided them; this bullet is where the decision reaches the agent that would otherwise re-ask or guess, and without it the resolution at step 0 changes nothing.
- **Any domain-scoping declaration step 0 resolved for this domain, stated even when the answer was "unavailable"** - for `data-protection-audit`, whether the target processes personal data. Same reason as the bullet above: an unstated declaration reads to an agent as a question it may answer itself, and here answering it itself means either inferring a personal-data surface from field names and flagging the code against the surface it invented, or dropping the domain's central checks and returning a matrix that reads as a clean privacy posture.
- **The grants, named explicitly, including the ones withheld** - and where either grant was given, the path to the tree built above, the resolver command and whether the lockfile was frozen. An unstated grant reads to an agent as a question it may answer itself, which is how a report-only sweep acquires an install nobody sanctioned. A withheld grant said out loud is what turns "the tool did not run" into `no-evidence (not-permitted)` rather than a guess about the environment. A withheld grant is where a record's untiered routes become load-bearing rather than decorative: where every answering route in the partition's language needs that grant, nothing is left to run, and the record marks that one case with `answers_ungranted: none`, which carries no prose, only the sentinel; where the record keeps a route that answers from a read-only clone, that route runs and the status comes from what it reports.
- The one line: "**Invoke the `handbook-audit:<domain>-audit` skill**, then load the records from its `checks/` directory that your audit needs - every record that is not `optin: true`, plus exactly the opt-in records named in the list above and no others, taking them all at once for a small domain or fanning out internally by `locality` (the `local` records per partition, one `global` check per sub-agent) for a large one - and execute that audit against `target_root` in REPORT-ONLY mode, through the findings-matrix step only. Treat the opt-in list as already settled: do not ask about it and do not add to it, whatever your own skill says about asking. Judge only against a rule the target documents or one passed to you here; where neither exists, report the absence as the finding and flag no violations of a rule you inferred. Produce no deliverable - findings rows only." **Pass no path to the lens.** Invoking the skill by name lets the harness resolve where the family is installed and hand the skill its own base directory, from which its `checks/` resolve; a path relative to a repository root resolves inside the audited repository instead. Qualifying the name with the plugin also stops a same-named project-level skill in the target from shadowing the lens under audit.
- **The project inventory**, which supersedes the per-domain list of grounding this bullet used to enumerate: the partitions and their language sets, whether each is a deployable, a shared package or undetermined with the reason recorded beside the last, which partitions import each shared package, the shared scopes the shared packages group into under their names, the monorepo tool and its workspace globs, the package managers and lockfiles, the test runners, the already-installed tooling, and the CI workflow list. The workspace globs are not decoration in a sweep: they are how the partitions being handed out were discovered, so a domain that disagrees with the partitioning has no way to see what produced it. One artifact rather than a list that had to grow with every new domain. Add only grounding the inventory does not carry, such as a declared architecture rule the user states, and pass it as a short pointer rather than a pasted lens.
- The hard constraints: **do NOT edit/create/delete any file, do NOT create branches/commits/PRs, report-only**; "keep raw tool output OUT of your final answer - return the matrix (**capped to the significant rows**), **the full findings list uncapped, as data** - one entry per finding with its domain, check id, severity, item, `file:line` evidence, handbook citations and any caveat on an id you could not confirm - the severity counts, **the coverage triple - checks that ran, `no-evidence`, `not-applicable` - counted over every check before the cap**, **the graph scopes its whole-graph `global` checks were computed over - each deployable, each shared scope the inventory lists read on its own and each undetermined partition, each under the name the inventory lists it by, with the module count it covered, `one deployable` with its module count on a single-partition target, or `none` where the domain computes no whole-graph property**, top findings, and a one-line-per-tool ran/fell-back log." The scopes come back as their own list for the same reason the triple does: they live in whole-graph rows' evidence pointers, a clean scope produces no significant row, and the consolidated report's `Graph scope` line cannot be rebuilt from a capped matrix. The coverage triple has to come back as its own count rather than be recounted downstream from the returned rows, because the cap removes precisely the rows it counts: a `no-evidence` row is not a significant finding, so a domain that could answer nothing returns a near-empty matrix, and a roll-up derived from those rows prints zero at every severity beside a coverage cell it cannot fill - which is the clean bill of health for a lens that measured nothing that the coverage column exists to prevent.
- Instruction to run the domain's detection tooling **without adding a dependency to the target**, which for a tool that has to be fetched at all means a one-shot runner that reaches the registry the tool is published in: `uvx <argv>` for a PyPI package, and `npx <argv>` for an npm one, with `pnpm dlx <argv>` and `yarn dlx <argv>` as same-registry equivalents on partitions whose manager provides them. Where the package that provides a route's command - its `package`, or its `tool` where it names none - is not the argv's first word, the runner is told the package and the argv runs after it, as `uvx --from <package>` does, because a runner handed only the command fetches whatever is published under the command's name - except on a command the route's `own_runner` marks complete as written, which runs as written; and an argv token naming `CLAUDE_PLUGIN_ROOT` between `${` and `}` is this plugin's install directory, which you substitute before the command runs, because nothing sets that variable in the shell you run it in. `## Running a route` states both rules and where the directory comes from. A route carrying `in_env: true` takes neither runner form: it runs against the materialized tree in the in-environment form for the partition - uv's on every Python partition, `uv run --no-sync --with <package>` on a `uv` one, the route's `package` or its `tool` where it names none, and the tree's own copy on TypeScript, `npx --no --` on npm and `pnpm --config.verify-deps-before-run=false exec` on pnpm - and the isolated runner and that form are not interchangeable; the field decides, not your reading of what the tool does, and `## Running a route` states each form in full, Yarn's and the non-`uv` Python partitions' included. **The runner has to reach the tool's registry; it does not have to be the partition's own package manager.** Not adding a dependency to the target is the whole of the constraint, and every one-shot runner satisfies it identically because none of them writes to the target - so using the partition's own manager is a preference, and where that manager has no one-shot form the move is another runner reaching the same registry, never treating the check as unrunnable. Matching the partition's manager is load-bearing for exactly one of the three kinds below, the package-manager subcommand, and for the reason given there. **Yarn classic is the case that makes the difference concrete: `dlx` is a Yarn 2+ command, and Yarn classic's CLI index documents no `dlx`, and no general-purpose one-shot runner in its place.** So on a Yarn 1 partition an npm-registry tool is fetched with `npx`, which ships with npm - confirm it from the inventory's already-installed field rather than assuming it, the same way you would any other tool - and which reaches the same registry - and a `yarn`-keyed `argv_by_partition` entry spelling `dlx` is Yarn Modern's form, with the route's shared `argv` being what a classic partition runs. That needs no version detection to follow, because `npx` is correct on either yarn; where you want to tell them apart in order to prefer `dlx`, Yarn's own migration guide is the signal - Modern "now uses `.yarnrc.yml`. Any other file is now ignored - this includes `.npmrc`", where classic read `.yarnrc` and `.npmrc`. Do not infer the major from a `packageManager` field in `package.json`: that is not what the migration guide names, and an agent guessing Modern on a classic partition lands back in the failure this rule exists to remove. Fetching ephemerally is a means to that constraint rather than the constraint itself, which is why most of what follows is about not fetching. For a package manager named above whose one-shot form turns out not to exist, and for one not named at all, use any documented one-shot form that reaches the tool's registry - the named list is where to start, not the set of what is allowed. Only where no runner at all can reach that registry do you fall back to what the record's own routes offer, where a route's `registry`, `note`, `disposition`, `alone_insufficient` and `needs` say what else answers. **A route's tool is one of three kinds of thing, and a one-shot runner reaches only the first, so read the route before choosing how to run it.** A *registry package* (`depcheck`, `pip-audit`, `@cdxgen/cdxgen`) is what the runners above are for - **as long as the audit runs it as a command**, and **as long as the runner you choose reaches the registry it comes from**. A `lang: any` or `lang: none` route's `lang` names no registry of its own, so such a route naming a registry package needs that package's *own* registry whatever the partition speaks - `test/new-code-coverage`'s `diff-cover` is a PyPI package, so `uvx diff-cover` is the invocation on a TypeScript partition too, or `pipx run diff-cover` where the environment carries `pipx` and not `uv`. **Never let the partition choose the registry for such a route**: an npm package named `diff-cover` also exists, an unrelated third-party port with working binaries, so `npx diff-cover` does not fail - it runs a different implementation and prints a plausible diff-coverage number with nothing to show the tool was swapped. This is the `cyclonedx-npm` hazard reached from the other direction, and the same rule closes both. **Read the route's `registry` to choose the runner, not its `note` and never its partition.** What the field means, where the loader requires it and what `lang` implies where it is absent are `## Running a route`'s, and this brief does not restate them. A registry package the audit has to *import* rather than execute (`ts-morph` for an AST walk, a parser or plugin an audit-owned linter config loads) is not served by a one-shot runner at all: the runner installs into a sandbox, and a script or config of the audit's own resolves its imports from where that file lives, so the import fails with `ERR_MODULE_NOT_FOUND` before the tool does anything. Install those into an audit-owned directory and keep the script or config beside them. That needs network rather than anything from the target, so it is available under no grant. A *subcommand of the target's own package manager* (`pnpm audit`, `npm sbom`, `yarn licenses list`) has nothing to fetch: run it directly, and run it only when that package manager is the partition's own, because such a subcommand resolves from the lockfile of the manager that owns it - an `in_env` Python route aside, which `## Running a route` runs on any Python partition because its subcommand reads the installed environment - `npm audit` on a pnpm partition reads a `package-lock.json` that is not there, and no runner can supply a subcommand of a manager the target does not use. A *standalone binary* (`osv-scanner`) belongs to no language registry at all, so it is available when the audit environment already carries it and otherwise unavailable, and no one-shot runner will install it. Fetching one of the latter two as if it were a package fails in the way a missing tool fails, which lands in the report as `no-evidence` for a check the target could in fact have answered - so the distinction is what keeps that status honest. **A second axis runs across all three kinds and each route answers it separately in its own `needs`**: what must be present in the target before the tool can answer. It is orthogonal to the kind - `knip` is a registry package a runner fetches happily and cannot report anything true without the tree, while `osv-scanner` is a standalone binary no runner can fetch and answers from a lockfile alone - so obtaining a tool is no evidence that it can run here. Prefer a tool that needs nothing present; reach for one marked `resolved-tree` or `target-execution` only against the tree built at the top of this step and only under the matching grant; and where the grant is absent, do not run the tool against an unresolved graph, which returns an empty result that reads exactly like a clean one. Where a tiered route sits beside one that needs nothing present for this partition's language, that untiered route is the "tool that needs nothing present" the preceding sentence already told you to prefer - run it, and this partition does not depend on `answers_ungranted` at all. The record may still carry the field, because it is required wherever any one language of the record has every answering route tiered, and that may be a different language from yours. **What that preference does not license is dropping a lens the record says still answers.** A route's `needs` tier is a claim about one invocation of a tool, and a record may describe another invocation of the same tool that needs nothing from the target - an audit-owned lint config with an audit-owned install, rather than the target's own config loaded from its `node_modules`. Where it does, that invocation is not the tiered one, so run it alongside the untiered tool instead of treating the untiered tool as the whole answer. The two are not interchangeable: on the run recorded in [the TypeScript smoke run](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/audit/typescript-lens-smoke-run.md) the untiered scanner returned zero findings over a tree where the tiered one, run its grant-free way, returned hundreds. Only where every answering route the record offers for this partition's language needs a grant does the withheld grant leave nothing to run, **and that is a test over routes, which a reading of the record's tools gets wrong.** What still answers is the record's own untiered routes, which include the ones carrying no tool at all - a `kind: procedure` route reading configuration, a `lang: none` route needing nothing installed - and those name no tool, so a reading of the record's tools misses them precisely where you would look for them. A `kind: subject` route is not an escape either, however untiered: the record is saying that running that tool answers a different check. So read the routes rather than a list of tools, treat the check as silenced only where every answering route in this language carries a tier, and take `answers_ungranted: none` as the sentinel that licenses `no-evidence (not-permitted)` for the check as a whole. **Always prefer a tool the inventory reports already installed**, which is pinned by the target's own lockfile and already trusted by that project. A one-shot runner is the fallback, and it is not free: it resolves a package at run time and executes it in the audit environment, so a run that promises only to read the target is nonetheless executing third-party code that could write to it - the same reason the no-writes invariant is checked rather than promised. So **record the resolved version of every ephemerally fetched tool in the report**, which makes the run reproducible and a bad version identifiable afterwards; and where policy forbids fetching at all, run only what is already installed and mark the remaining checks `no-evidence`, which is precisely what that status is for. Hardcoding one ecosystem's runner here would make every other ecosystem's tooling unrunnable no matter what the records say, and naming only one ecosystem's runner concretely while gesturing vaguely at the rest achieves genericity by omitting the hard part: an agent that cannot resolve the instruction falls through to the fallback, which is the same failure more quietly. And to **verify each finding against the real artifact** (source→sink, `file:line`, tool output) so scanner artifacts don't become findings. **Render `no-evidence` with the reason that produced it - never as a clean result, and never unlabeled:** `not-permitted` where the check needed a grant this run does not hold (as above); `tool-unavailable` where no candidate tool could be obtained - unfetchable, not installed, or no network - so every fallback for the check fails, or, on a check whose routes carry `answers`, every fallback for one axis fails, in which case the cell is that axis's and a sibling axis having run does not make the check `ok`, and where a route's grant was given but the tree it reads could not be built, with the evidence pointer naming the materialization step that failed and its error, except where that error names a lifecycle script the scripts-off install skipped, which the engine treats as a withheld `target-execution` grant and so `not-permitted`; `tool-failed` where a tool ran but errored or returned nothing parseable; `not-prescribed` where the record prescribes nothing that answers this partition - no command for it, and no `library` or `procedure` route applying here either, since those answer without prescribing a command line - and offers no route a grant would enable, so nothing about this run or this environment will ever answer it. **Where more than one of those is true, report the one a reader can act on** - a partition a record prescribes nothing for while keeping a tiered route is `not-permitted`, because re-running with the grant answers it and an absent prescription is not something the reader can fix. Put the other in the row's evidence pointer: the reason cell holds the one a reader can act on, and the pointer is where they learn the cheap path is closed for good. **If the check has no lens in the partition's languages, mark it `not-applicable` instead - also never as a clean result** - so neither a withheld grant, an unobtainable tool, a tool that ran and failed, a partition nothing is prescribed for, nor absence of a lens is reported as absence of findings.
- **A record carries `routes:` - one list of routes, each one way of answering the check in one language.** How a route becomes something to run is [audit-core](../audit-core/SKILL.md)'s `## Running a route`, and **this brief does not restate it** - beyond the yarn case the runner bullet above names, which it names there because choosing between a keyed entry and the shared `argv` is a runner choice, this brief says nothing about what a partition its map does not name is telling you, or about what `registry`, `then`, `own_runner`, `disposition`, `applies_when`, `alone_insufficient` and `answers` oblige, beyond the one axis clause the rendering rule above carries. So the item to pass a domain agent is the pointer rather than the contract: require it to read that section before it runs anything a record prescribes. It reads that file anyway - every domain skill opens by deferring to it - and a second copy of the contract here would be a prose description of frontmatter that `audit_checks.py` validates, kept in step with the loader by hand, where a drift between the two reads as the contract disagreeing with itself rather than as either copy being wrong.

One subagent per domain; do not split a single domain across subagents here (that's the domain skill's own internal concern).

**Partial results.** If a subagent dies, times out, or returns null/unusable output, do **not** stall the sweep: consolidate the domains that returned, and mark each missing one as `errored / incomplete` (with the reason) in the roll-up. **A domain whose coverage triple is 0 / 0 / 0 is missing too, whatever its section says came back**: a placeholder that arrived is not a matrix, a zero triple means no check ran, was refused or was ruled out - every check the domain loaded unaccounted for, since the triple is counted over all of them before the cap - and a verdict column that reads `pass` over it is the false clean at domain granularity that the coverage column exists to make visible. One sweep reported two such domains as pass with the contradiction sitting two lines below in its own caveats. A broken domain degrades the report; it does not block it.

### 2. Consolidate - into the report template

Merge the returned matrices into one report using the **template below**. Rules:
- **Carry each domain's self-verification forward.** Do not upgrade a Minor to a Critical (or invent a finding) during the merge; the domain subagent owns severity. If a domain reports a false positive it caught, keep that note - it is evidence the lens is grounded.
- **Surface cross-domain agreement.** When two domains flag the same root cause (e.g. "checks exist but aren't enforced", a shared shim), call it out as a theme - corroboration across lenses is a strong signal where the two domains answered with different methods and not merely with different records, for [the reason agreement is not corroboration](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/engineering/evaluation.md#agreement-is-not-corroboration). A theme is corroboration, **not a new finding**: it is not added to the severity totals.
- **Merge rows, never fold them.** A row is one instance, or the unit its record states, as `audit-core`'s findings-matrix step defines it, so two domains' rows over one location stay two rows under their two checks, and a theme across rows is named as a theme rather than collapsed into one row.
- Compute the severity roll-up by counting **per-domain matrix rows** (not themes); include the total Criticals, and any `errored / incomplete` domains from partial results. Take each domain's coverage triple from **the counts it returned**, never by recounting the rows it sent: those were capped to the significant ones, and coverage is a fact about the checks that produced no significant row. Fill the `Graph scope` line from the scopes lists the domains returned, for the same reason: merge them by scope name where two domains name the same deployable, the same shared scope or the same undetermined partition, under the name the inventory lists it by, keep each scope's module count as the domains returned it and, where two domains disagree on one scope's count, print both rather than one, and never fill a scope or its module count from the inventory alone, which knows the partitions but not what was computed over them; an undetermined partition's reason is the inventory's and is copied from it. Keep each domain's uncapped findings list as it arrived, concatenated across domains and otherwise untouched: it is what the findings JSON in step 3 carries, and the capped matrix cannot be reconstructed back into it.
- **Carry identifiers, never supply them.** A merged row may name an advisory id, a licence, a URL or a path the sweep never saw the tool output for - consolidation is the step that strips that output and then republishes the id as Markdown, HTML, a hosted page and the findings JSON. The JSON carries such a caveat in a `note` field on the finding rather than in prose beside it, because the reader there is a machine that will not infer one from a sentence. Carry each exactly as the domain reported it; where a domain reported an id it could not confirm, carry that caveat with it. "Unverified, tracked in issue #N" is an honest outcome and a plausible-looking advisory id filled in to complete a row is not.

### 3. Output - ask which format(s), then emit

Ask the user with the ask-the-user tool (**multi-select**, 4 options, all can be chosen; recommend Markdown and the findings JSON). Four is the cap that tool allows, so a fifth format would have to replace one rather than join them:
- **Markdown file** - write the report to the `out_path` resolved in step 0, which is never under `target_root`, whether or not the audited repository is the one asking. This is the durable, linkable, diff-able record; recommended default.
- **HTML file** - write a **self-contained** `.html` (inline CSS, no external assets) alongside the Markdown, for a shareable local file.
- **claude.ai Artifact** - publish a hosted page: first load the `artifact-design` skill to calibrate the design, write the page file, then publish via the Artifact tool. Use for a polished, shareable dashboard.
- **Findings JSON** - the machine-readable half, written beside the Markdown. It carries **every** finding rather than the significant rows the report is capped to, one object each with `domain`, `check`, `severity`, `item`, `evidence`, `handbook` and `note`, under a top-level `findings` key. `severity` is one of `critical`, `important` and `minor`, written in lowercase. **Beside `findings` the file carries its provenance**, the machine-readable form of the lines the report's `How the audit ran` section prints: `target` (the repository identity that section names), `target_ref` (a mapping of `commit`, the short SHA, `branch`, the branch name or `null` on a detached HEAD, and `dirty`, true or false), `mode` (`report-only` for a sweep), `plugin` (the lenses' short SHA, as the `Lenses` line gives it: the name of the directory `${CLAUDE_PLUGIN_ROOT}` resolves to in a plugin install, which is that SHA at twelve characters, and `git rev-parse --short=12 HEAD` there in a clone, so both give one string for one commit), `grants` (a mapping of `resolved-tree` and `target-execution`, each true or false, and never execution without the tree, for the reason the `Grants` line gives), and `generated` (the day the run started, as `YYYY-MM-DD`, which the `Date` line prints). A file that cannot say which tree, which lenses and which grants produced it cannot be diffed against a baseline or folded with another run without someone reconstructing that by hand, and the emitter refuses one that lacks any of these. `note` is where the caveat on an identifier you could not confirm travels, and it is a field rather than prose because the reader is a machine that will not infer one from a sentence - the consolidation rule above requires that caveat to stay with the id, and this is the only format in which it has nowhere else to live. It is what the emitter reads - `scripts/emit_audit_issues.py` under the plugin's install directory, as step 4 spells it - and the only thing it reads: the emitter does not parse the report, because a report capped to its significant rows would hand back an issue set silently missing the rest. Select it whenever filing issues is a possible next step, which is most sweeps.

Emit every format the user selects (writing an output file in report-only mode is fine **provided it lands outside `target_root`** - it is a report artifact, and inside the audited tree it would instead be an uninvited change to somebody else's branch), **and present the report in conversation whichever formats they selected**: the four options above are files to write, not alternatives to reporting, and step 0 already fixed the consolidated report as always returned in conversation as well. A non-interactive run has nobody to select a format or supply a path, so it follows step 0: write the Markdown **and the findings JSON** to `out_path` when one was supplied with the invocation, and otherwise return the report in conversation and write nothing. Never invent a path to satisfy a default - that is how a run with no stated destination writes into the audited tree.

**The findings JSON needs no second path**: it is written at `out_path` with its extension replaced by `.findings.json`, so step 0 still resolves three things rather than four. What it depends on is that path, not the Markdown: it is one of the four options and is selected like any of them, so selecting it alone writes the JSON and no report, which is the ordinary shape of a run whose purpose is to file issues rather than to hand somebody a document. Selecting the Markdown alone writes no JSON, and the emitter then has nothing to read. Selecting is what an interactive run does, though, and a non-interactive one has no selector: there a supplied `out_path` writes both, because the JSON needs no path of its own, it is the only one of the four an emitter can read, and a sweep whose findings are meant to be filed is exactly the kind that runs unattended. **A non-interactive sweep that supplied no path writes neither, and so nothing the emitter can read.** That is the right outcome rather than a gap to route around: a run with no stated destination is the one that should not be filing issues in somebody else's tracker.

### 4. Next steps

After presenting, offer (do not auto-run):
- **File issues** - `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/emit_audit_issues.py" <findings.json> --target <owner/repo>` prints the epic, per-domain child epics and clustered sub-issues it would create, and creates nothing without `--create`. The path is under the plugin's own install directory because that is where a consumer holds the script: a plugin install carries this whole repository, `scripts/` included, so the emitter is on disk in every repository that runs this skill from the plugin, and it imports only the standard library, so it needs no `uv` project and writes nothing into the plugin cache. From a clone of this repository the same command is `uv run python scripts/emit_audit_issues.py <findings.json> --target <owner/repo>` at the repository root. The clustering is one sub-issue per domain, check and severity, so a check's findings share a fix and a Critical is never scheduled with a Minor answering the same question. Add `--min-severity important` for the Important+ set the report template offers. A findings file written before its provenance fields were required is refused as it stands; `--accept-missing-provenance` reads it anyway, and the dry run says it was used and what the file lacks, so the output of such a run is never mistaken for one whose tree and lenses it can name. **The labels are the emitter's own vocabulary, not the audited project's**: `epic` on the top-level issue and each domain epic, `audit:<domain>` on each domain epic and its sub-issues, and `priority:urgent` / `priority:normal` / `priority:low` on each sub-issue. They are stated here because `--create` would create them in a repository this project does not own, and a tracker with its own `epic` or priority names ends up carrying two sets; check them against the target's before creating anything. It needs the findings JSON from step 3; without it there is nothing to emit from, and the report is not a substitute.
- **Fix a domain** - run report+fix on a specific domain via its skill (sequential, its own PR).
- **Produce an opt-in deliverable** - an SBOM, a layering-contract config, a rendered metric report: a per-domain run of the skill that owns it, since each is an artifact of the audited project rather than findings about it, which is why step 0 keeps it out of the sweep whatever the user asked for there.
- **Nothing** - the diagnosis is the deliverable.

## Fixes are delegated (why the sweep is report-only)

Report-only fans out safely because read-only subagents never collide. **Fix-mode does not fan out**, for [the handbook's fan-out clauses](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/engineering/lifecycle.md#fan-work-out-to-parallel-agents-and-merge-it-honestly)' reason plus one of its own: a single sweep-wide fix produces one incoherent mega-PR. So when the user wants remediation, this skill hands the chosen domain to its own skill - **invoked as `handbook-audit:<domain>-audit`**, qualified exactly as in the report-only fan-out - in report+fix mode, which runs the full audit-core loop - one domain, one coherent PR, per-item review - and does the next domain after. Breadth here; depth there. The qualified name matters more here than in the diagnosis path, not less: a bare `<domain>-audit` resolves to a same-named skill in the working tree wherever one exists, so a target carrying its own fork of the family would be diagnosed with the plugin's lens and then **remediated with its own**, and remediation is the half that writes.

## Consolidated report template

```markdown
# Repo audit - <project> (report-only, <YYYY-MM-DD>)

<one-sentence verdict: overall health + the single most important thing to fix>

## Severity roll-up
| Domain | Critical | Important | Minor | Coverage (ran / no-evidence / n-a) | One-line verdict |
|---|---|---|---|---|---|
| <domain> | n | n | n | n / n / n | <pass/warn/fail + gist> |
| ... |
| **Total** | **n** | **n** | **n** | **n / n / n** | |

Coverage is not optional decoration. A domain whose every check returned `no-evidence` shows zero findings at every severity, which is indistinguishable from a clean domain in a severity-only table, and on a foreign repository with none of the expected tooling installed that is the likely case rather than the exotic one. **When coverage is partial, the one-line verdict must lead with coverage**, not with the finding count. For the same reason, a `no-evidence` cell carries its reason - `not-permitted`, `tool-unavailable`, `tool-failed` or `not-prescribed` - because a reader deciding what to do next needs to tell the checks a grant would answer from the ones no tool could answer here and from the ones nothing will answer whatever they change.

## Criticals (<count>)
1. <finding> (<domain>) - <evidence file:line / tool result>
   ...   (omit this section if zero Criticals)

## Cross-cutting themes
- <theme>: <which domains agree, and the shared root cause>

## Per-domain findings
### <domain>
<the domain's findings matrix: Item | Check | Status | Severity | Evidence | Handbook - capped to the significant rows>
Top findings: <2-3 one-liners>

## How the audit ran
- Target: <repository identity - the remote's `owner/repo` if one is configured, else the repository directory's own name; never a filesystem path> at <short SHA> on <branch, or detached><, working tree dirty if it was>
- Lenses: handbook-audit @ <short SHA>
- Date: <YYYY-MM-DD, the day the run started>
- Scope: <domains run> · Mode: report-only
- Opt-ins: <offered → granted / declined, one entry each; "none offered" if that is the case> · Deliverables: none (a sweep produces findings, not artifacts)
- Grants: <resolved-tree granted/withheld, target-execution granted/withheld - the execution grant implies the tree grant, so granted execution is never reported beside a withheld resolved-tree> · Dependency tree: <read in place | reconstructed outside the target with `<resolver command>`, lockfile frozen yes/no (weaker evidence than a lockfile read in place - it can differ from what the audited team actually has installed) | not materialized>
- Stacks present: <partition: languages, tested yes/no, in CI yes/no> (one line each)
- Graph scope: <one line per scope the whole-graph `global` checks were computed over, from the scopes lists the domains returned - each deployable, each shared scope the inventory lists read on its own, each undetermined partition computed alone with the inventory's reason, each under the name the inventory lists it by - with the module count it covered; `one deployable` with its module count on a single-partition target; `none` where every domain returned `none`>
- Per-domain tool log: <ran / fell back / no runner available> (one line each)
- Verification note: <any false positives caught and discarded>
- Target tree unchanged: <yes, or the git status delta observed>

## Recommended remediation sketch
- <domain>: <the smallest change that retires its most severe row, one line each>

A sketch, not a plan: `audit-core` asks a report-only run to present one, and the plan proper belongs to the per-domain run that will do the work. Sketch only what a finding in this report grounds.

## Next steps
- File issues (the plugin's `scripts/emit_audit_issues.py` over the findings JSON, `--min-severity important` for the Important+ set) / run report+fix on <domain> / nothing
```

**The `Dependency tree:` line names no path, and the omission is deliberate.** What lets a reader discount a reconstructed graph is that it was reconstructed, what resolver produced it and whether the lockfile was frozen - all three stay in the report. The scratch directory tells that reader nothing they can act on, and it is precisely the environment-specific value the last cross-cutting rule below bars from any emitted report: this report is handed to the audited team, written to a file, and optionally published as a hosted page, so an absolute temp path in it reaches every one of those readers. `audit-core` still requires the run to "record the scratch directory each reconstruction used" - state the path in conversation at the moment the tree is reconstructed, where it reaches the operator who ran the sweep and stops there, and keep it out of the report body, which is what gets written to a file and published. Do not restore the path to the template: a machine path is worth having where the operator can go and delete the directory, and is a leak in everything the report is copied into.

## Cross-cutting rules

- **Project-agnostic.** Detect available domain skills and each domain's tooling; run the subset that applies; never hardcode a fixed set, and detect the domains from this skill's own siblings rather than from the audited repository.
- **Report-only means no writes to the target's working tree or git history.** The only files this skill may write are the report artifacts in step 3, and they land outside `target_root`. Verify it rather than assert it, per `audit-core`'s invariant: `git status --porcelain` at the target before and after. Materializing dependencies under a grant does not weaken this: the resolution happens in a scratch copy outside `target_root`, so the comparison at the target must come back identical either way, and a delta is a defect of the audit run whether or not a grant was held.
- **Verify against evidence** is inherited from audit-core and enforced per-domain - the consolidation must not weaken it.
- **No environment-specific values** in any emitted report (placeholders with prose, not machine paths / personal profiles).
