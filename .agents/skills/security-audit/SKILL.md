# Security Audit (first-party code and agent grants)

A domain specialization of **[audit-core](../audit-core/SKILL.md)** - read that first; it owns the loop (scope → parallel evidence → findings matrix → plan → subagent-driven fixes → review → PR), the `## Running a route` contract that turns this skill's records into commands, and the cross-cutting rules. The checks are records in [`checks/`](checks/) beside this file; load the ones your slice needs, not the directory.

**Core principle:** find the places where untrusted input meets a dangerous operation, where a secret could leak, and where an agent has been granted more reach than its task needs. For the code checks a finding is only real when you can name the source of untrusted data and the sink it reaches; a scanner hit with no reachable attacker path is noise, and a real dataflow the scanner missed is the finding that matters, so verify both directions against the actual code. Not every check here has a path to name: `security/agent-privilege-surface` names a combination of grants one agent holds, and the two secrets checks name a literal and the commit carrying it. What makes each of those real is stated in its own record rather than here.

**Announce:** "I'm using the security-audit skill (on the audit-core engine) to audit the first-party code and what the project's agents are granted."

**Not for:** third-party dependency CVEs (use `deps-audit`), CI/pipeline secret and permission hardening (use `ci-audit`), the stored artifacts that outlive a call - traces, run records, eval datasets, fixtures extracted from real cases (use `data-protection-audit`, which owns them; this skill owns the call site that wrote them), whether a prompt or an agent *behaves* under adversarial input, which is a measurement over runs rather than a path through code (use `eval-audit`; this skill owns the same injection as an exposure, tracing a model or tool output to a dangerous sink), or a formal pentest of a deployed service (out of scope - this is static, first-party).

**Subject:** the project's own source tree (the importable package plus scripts and entry points) and the trust boundaries in it, plus what the project's agents are *granted* - the tool, MCP and permission declarations that say what an agent may reach before any of that code runs. Establish the boundaries first, because they set what "untrusted" means:

- **Trust boundaries / input surfaces** - where external data enters (HTTP handlers, CLI args, file/S3 reads, message queues, LLM/tool outputs, env vars). These are the sources.
- **Threat context** - is this an internet-facing service, an internal tool, or a library others import? It changes severity (an injection in a public endpoint outranks the same pattern in a local dev script).

Slice the parallel evidence pass by top-level package/entry point, or by trust boundary where the tree does not partition cleanly by package - one read-only agent per slice, each running the detection below over its own code and judging every weakness class within it. Most checks here are `local` to a code slice, so they ride along with that one agent rather than each getting their own. A check is `global` when its subject is one object the repository has once rather than one per slice, which no per-slice agent can see: `security/secret-history`, because git history is one object, and `security/agent-privilege-surface`, because the set of agents and what each is granted is one surface and the finding is a combination across it. Being `global` says nothing about being opt-in - the first is, the second is not.

**Detect** what the project already has from the project inventory, which records the audit-relevant tools each partition already runs: a SAST scanner (e.g. `bandit`, or `ruff` with the `S` = flake8-bandit ruleset for a Python partition, `eslint` with `eslint-plugin-security` for a TypeScript one, or the language-agnostic `semgrep`), a secret scanner (`detect-secrets`, `gitleaks`, `trufflehog`), and any type checker (a strict typechecker catches some misuse). Prefer a tool the project already runs; fall back otherwise.

For the code checks, read the trust-boundary map above and record source + sink `file:line` as the evidence pointer. Where a finding is not a path through code there is no source and no sink to name, so the pointer is whatever identifies the thing found: the agent and the granting tool for a grant, the `file:line` of a literal, the commit for a secret already in the history.

Status per row: **ok / warn / violation** (secrets: none / suspected / confirmed-leak). Suppressions (a scanner false positive, an intentionally allowed pattern with a `# noqa`/`# nosec`-style marker) must be explicit and recorded with a reason - never silently dropped. **A secrets verdict is scoped by whether the history scan ran, and the row says which scope it has.** Being opt-in, as above, `security/secret-history` may not have run, and on a run that did not enable it every secrets row is read off the working tree alone and reports that scope beside its value rather than leaving a reader to infer it from a clean one. What that scope leaves out is what the clause behind `security/secret-history` is about: a secret removed in a later commit is invisible to every working-tree scanner, so deleting one without rotating it produces exactly the clean pass this scoping exists to qualify. Why the check is opt-in is stated in its own record and not repeated here.

Most security fixes **touch code** (and sometimes secret-management infra), so they are **not** docs-only: the gate for those is "the SAST/secret scan is clean (or every remaining hit is a recorded suppression) **and** the test suite passes" - run the normal install + lint/typecheck/test CI plus the scanner, and the code-review gate. A fix that changes a *declaration* rather than code is not closed by either, because neither the scanner nor the suite can see a narrowed tool list or an added approval hook; the record prescribing such a fix states the read that closes it. **A `security/secret-history` finding is closed by neither either**, for a sharper reason: the domain's own secret scan reads the working tree, so it comes back clean over a secret that is still in the history - the pass the scoping above exists to qualify. What closes one is the history scan re-run plus rotation at the provider, which no scan of this repository can attest to. **Highest-leverage fix:** wire the SAST + secret scan into CI (and pre-commit) so the class of finding can't silently recur. Docs-only outputs: the findings report, a `SECURITY.md` / disclosure policy, and a threat-model note.

**Dependency-CVE cross-check** - hand off to `deps/vulnerabilities` rather than scanning third-party code here; note the handoff in the report. **CI/secret-hardening cross-check** - hand off pipeline secrets / permissions to `ci/permissions-secrets`; note the handoff.
