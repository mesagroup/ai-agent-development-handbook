# Audit Core - the shared audit engine

Every `*-audit` skill is the **same loop** applied through a different lens. This skill owns that loop so the domain skills stay thin and behave consistently. A domain skill provides the lens (its checks, evidence sources, tooling, severity rubric, and fix patterns) and defers the mechanics to here.

**Core principle:** an audit is only as good as the evidence under it. Gather evidence from the actual artifacts (source, config, lockfiles, workflow files, test runs) - never from a summary, a stale doc, or an assumption. A confident finding built on a guess is worse than no finding.

**Announce (from the domain skill):** "I'm using the `<domain>-audit` skill (on the audit-core engine) to audit `<subject>`."

**Pin every subagent to the working tree you are in.** When the audit runs from a git worktree, a dispatched agent given a bare or main-repo-rooted path can silently operate on the *primary* checkout instead, often many commits stale. Both directions fail quietly. A read-only evidence agent then reports ground truth from a tree nobody is auditing, which is the stale-source failure the core principle above forbids. An implementer's edit lands where `git status` in your worktree will never show it, so the fix drops out of the commit and reads afterwards as though the agent simply missed it. Resolve `git rev-parse --show-toplevel` once as `target_root`, pass it in every dispatch, and require each agent to confirm its own `--show-toplevel` matches before it reads or edits.

## The loop

Runs in order; each step feeds the next.

0. **Scope + mode.** Fix the subject (which package/tree/config) and the depth. **Always ask the user the mode:** *report-only* (produce the findings matrix + report and stop) or *report + fix* (continue through remediation). For a large subject in fix mode, deliver in **increments** (one coherent slice per PR) rather than one giant change. Resolve any opt-in sub-audits here too (ask once if an argument didn't specify).

   **Resolve the target, once, and record it.** An audit of another repository is the normal case, not the exception, so nothing may infer the subject from the working directory.
   - `target_root`: `git rev-parse --show-toplevel`, resolved to a real path. Every tool invocation and every glob is pathed at it. It often equals the working directory and nothing may *assume* that, because the assumption is what silently audits the wrong tree.
   - `target_ref`: the `HEAD` short SHA, the branch name, and whether the tree is dirty. A target checked out on a non-default branch is common, and a report that omits the ref neither reproduces nor maps onto what the audited team sees on their own default branch.
   - `out_path`: where the report file goes. **Ask for it, and refuse any path that resolves under `target_root`.** The consolidated report is always returned in conversation as well, so a run given no path is never silent. A non-interactive run defaults to conversation only and writes nothing.
   - `grants`: whether this run may materialize the target's dependency tree, and whether it may execute the target's own code. Both are **off unless the user grants them**, they are separate, and holding the first does not confer the second. The implication runs the other way and only that way: **`target-execution` implies `resolved-tree`**, because the target's own code imports from the tree, so a run granted execution alone still materializes the tree first rather than running the suite against an unresolved graph. Resolve them here for the same reason the opt-in sub-audits are resolved here: a dispatched agent has nobody to ask, so a permission that has to be asked for is a permission it cannot obtain. Record which were granted, and record the scratch directory each reconstruction used.

1. **Gather evidence - fan out read-only subagents in parallel.** This is the load-bearing step. Dispatch one read-only agent per slice of the subject (per package, per config file, per check - whatever partitions cleanly) to collect *ground-truth* evidence: run the domain's tools, read the relevant files, and report a structured result. Run the domain's detection/measurement tooling here (see the domain skill for which, and `## Running a route` below for how a record's route becomes a command line). Also gather the project's existing conventions (contributor guide, prior audits, existing config) so remediation matches house style.

   **Match the fan-out axis to each check's *locality*, don't hardcode one axis.** Build any shared ground-truth artifact (a parsed graph, a resolved dependency tree, a coverage map) **once** and let agents consume it, rather than each rebuilding a possibly-inconsistent copy. **The first such artifact is always the project inventory**, and it is the one every domain needs: per repository the `target_root`, the `target_ref`, the dirty flag, the monorepo tool and its workspace globs, and the CI workflow list; per partition the path, the **language set**, the package manager and lockfile, the test runner, and which audit-relevant tools the partition already has.

   A partition's language is a set and never a single value, and a manifest is not a language detector: a package that carries a JavaScript manifest for monorepo wiring while containing only Python is classified as JavaScript by any "has a manifest, therefore" rule, whereupon the wrong toolchain runs against no matching source, finds nothing, and reports a pass. Detect by a file census plus declaration files. The already-installed field is what gives every record's "detect before it prescribes" an input, because nothing else computes what the target already runs. Then slice **local** checks (decidable from one partition) per-partition, and give each **global** check (one that needs the whole subject - a cycle, a whole-graph ratio, a cross-file flow) its own agent over the whole artifact, because a per-partition agent cannot compute a whole-subject property from its slice. Do **not** fan a cheap local check out to its own agent - that duplicates the shared build for no gain.

   **What a tool needs *present* is a different question from where it comes from, and a record answers both.** A `tooling:` name may be obtainable and still unable to answer: `knip` is a registry package any one-shot runner can fetch and it wants `typescript` and `@types/node` installed before it reports anything true, while `osv-scanner` is a standalone binary no runner can fetch and it reads a lockfile straight off a read-only clone. The record's `needs:` frontmatter carries the second axis per tool - absent means the tool answers from source, manifests and lockfiles; `resolved-tree` means it needs the dependency graph materialized to read package metadata; `target-execution` means it needs that and runs the target's own code. Read it before choosing a tool, because the failure it prevents is not a tool that refuses to start: it is a tool that starts, finds an empty dependency graph, and reports nothing wrong. A record declaring `routes:` instead of `tooling:`/`needs:` states the same axis per route, as that route's own `needs` field, so the same read-before-choosing rule applies one route at a time rather than through a shared mapping.

   **Never install into the target; reconstruct outside it.** Installing dependencies writes to the tree under audit, so it is barred by the invariant below whatever the user granted - and `git worktree add` is barred with it, because it writes `.git/worktrees/` and leaves no working-tree delta, so it would slip past the very `git status --porcelain` comparison that watches for this. Where the run holds the `resolved-tree` grant (which `target-execution` implies, so a run holding only the execution grant materializes the tree here as well rather than running the target's code against an unresolved graph), copy the target to a scratch directory that does **not** resolve under `target_root` - the same refusal `out_path` gets, for the same reason - and resolve there, with `--ignore-scripts` or that package manager's equivalent. **A check that needs a package the target does not declare copies again rather than adding it to that tree.** The reconstruction is a shared artifact by the rule above, built once and handed to every domain at once, so a package installed into it to make one check runnable - a missing coverage provider, a mutation runner's plugin - changes the graph the other domains are concurrently measuring, and the disagreement building it once exists to prevent then arrives by the sanctioned route instead of from parallel resolutions. It also plants a dependency the target never declared in the tree `deps` reads, where nothing distinguishes it from one the target did declare. So an install a check needs for itself goes into a copy that check owns, and a record prescribing one says which copy it means; **a package the audit added is never evidence about the target**, in any domain. **Express every evidence pointer taken from that copy relative to `target_root`, never to the scratch tree.** Step 2 requires a `file:line` on every row, and a tool run against the copy reports the copy's paths, so a licence or hygiene finding carried through unchanged cites a temporary directory that exists only inside this run - a path the audited team cannot open and cannot check the finding against. Say so in the report: a reconstructed graph is weaker evidence than a lockfile read in place, because it can differ from what the audited team actually has installed, and a reader who is not told cannot discount it. Where the run holds no grant, a check with nothing left that answers in this partition's language is `no-evidence (not-permitted)` rather than clean, and which fields settle that is a question about the schema the record declares. **On a record declaring `tooling:`, the silenced case is a language whose every tool carries a `needs:` tier, and the escape is that record's `ungranted_note`, which says what the check still answers without the grant.** The note is required on exactly the records this rule would silence, so the answer is there to read rather than inferred: a note naming a source-reading, syntax-tree or registry pass means the check reports the domain's own status with the missing axis named, and only the sentinel `none` means the whole question is unanswerable here. **On a record declaring `routes:`, decide it over that language's answering-kind (`command`, `library`, `procedure`), non-`forbidden` routes and over nothing else** - a `kind: subject` route names what the check inspects rather than what answers it, so it neither gives a language a claim to silence nor supplies one's escape, and a `lang: any` or `lang: none` route applies whatever the partition's language is. **There the escape is the untiered route itself rather than a field to read**: run whatever answering route that language still offers carrying no tier before treating the withheld grant as the end of the question. `answers_ungranted` carries no prose of its own - only the sentinel `none` - and is present exactly where no untiered answering route is left, so its absence beside an untiered route is the ordinary answered case and not a missing field. **Never read the silenced case off a migrated record's `tooling`/`needs` pair.** Those two are projected from its routes, and the projection carries tools and tiers and no ungranted claim at all: `arch/complexity-gate` tiers ESLint under `typescript` and names it `kind: subject`, so the projected pair reads that language as fully tiered while no route there was answering the check in the first place, and `arch/complexity` and `arch/hidden-coupling` read the same way through the projection while each keeps a TypeScript route that needs no grant. **The pair over-reports tiering a second way that has nothing to do with `kind: subject`, so an agent that has learned only the subject-route mechanism still misreads it:** the projection collapses a record's routes onto their tools, so one tool carrying a tiered route beside an untiered one reads as simply tiered. `deps/inventory` is that shape - `cyclonedx-py` prescribes the per-partition subcommands that read a dependency file, and separately, as an `alternative`, `cyclonedx-py environment`, which reads the installed environment and carries `resolved-tree` because it must. The pair therefore reports that tool as needing the tree while the route the record actually prescribes answers from a read-only clone. So read the tier off the route you are about to run, never off the tool: a tier on any one of a tool's routes is not a claim about the others. Assigning `no-evidence` to a check whose record says otherwise records an unanswered question that the clone could have answered, which is the same false negative as reporting a tool's empty output as a clean result.

   **An install hook is execution, not resolution.** A `postinstall` runs third-party code from the target's graph in the audit environment, which is the `target-execution` tier by what it does rather than by when it happens. So a tree that will not resolve with scripts disabled does not license dropping the flag under a `resolved-tree` grant: either the run also holds `target-execution`, or the check falls to the rule above - on a record declaring `tooling:`, where every tool it offers for this partition's language needs the grant, its `ungranted_note` governs, so the check is `no-evidence (not-permitted)` only where that note is the sentinel and otherwise reports the domain's own status with the missing axis named; on a record declaring `routes:`, where every answering-kind, non-`forbidden` route for that language needs the grant, `answers_ungranted: none` is what the record carries and the check is `no-evidence (not-permitted)`, while an untiered answering route left in that language is itself what still runs and there is no field to consult; and on either schema, where the record keeps something that answers from a read-only clone, that answers and there is no note to consult. This costs real coverage on a graph with native builds, and the alternative costs more - a grant the user understood as "read the licences" silently running whatever a dependency's install hook contains.

2. **Build the findings matrix.** Consolidate the evidence into a table: **item × check × status × severity × handbook**, plus a one-line evidence pointer (`file:line`, tool output, or metric) for every row. The `handbook` cell is read from the check record's `handbook:` frontmatter, so the matrix introduces no new source of truth; a record carrying an empty list renders its `handbook_note` instead, marked as deliberately beyond the handbook. Cite a stable identifier, a matrix row `id` or a heading, never a line number, for the reason the record schema already gives.

   Status is a small fixed scale the domain defines (e.g. pass / partial / fail, or ok / warn / violation). Whatever scale the domain picks, three outcomes are distinct and must never collapse into one another: the domain's own clean-result value (`ok` in the example scale above) means the check ran against this partition and found nothing, while **`no-evidence`** and **`not-applicable`** are additions to that scale, not replacements for it - **`no-evidence`** means the check applies here and no tooling or fallback could run, and **`not-applicable`** means the check has no lens in this partition's languages. `no-evidence` carries a reason, because the three ways a check can fail to run are not equally anyone's fault: `not-permitted` (it needed a grant this run does not hold, so re-running with the grant answers it), `tool-unavailable` (no candidate could be obtained - unfetchable, not installed, or no network, so the audit environment answers it), and `tool-failed` (a tool ran and errored or returned nothing parseable, so neither does). Render it with the status, as `no-evidence (not-permitted)`. The scale itself does not grow: a fourth status would collapse the distinction this paragraph just drew, in the other direction. Reporting `no-evidence` as a clean result reports absence of tooling as absence of findings; reporting `not-applicable` as a clean result is how a polyglot repository earns a clean bill of health for code nobody looked at. Severity is Critical / Important / Minor. Summarize counts. Write the findings report to the `out_path` resolved in step 0, never under `target_root`, and record any policy decisions so they are not re-litigated. The rule is unconditional, and it holds when the audited repository is the one asking: a point-in-time report is a fact *about* a tree at a ref rather than a part of that tree, and writing one into the audited tree turns a read-only audit into an uninvited commit on somebody else's branch. A carve-out for the self-audit case would also make step 0's refusal conditional on something step 0 cannot yet know, and would put a sanctioned write inside the very tree the no-writes check watches.

**If the mode is report-only, stop here** - present the findings matrix + report (with a short recommended-remediation sketch), modify no files, and ask the user whether to proceed to fixes. Steps 3–6 run only in report + fix mode.

3. **Plan remediation.** Turn the fail/violation rows into a work list. Write a plan file under the project's plans location (fall back to `docs/plans/`).
   - **One task per coherent fix** (or tightly-coupled group), each independently verifiable.
   - **Global-constraints block** copied verbatim into every task: the domain's fix conventions, the gate that must stay green (link-checker / test suite / linter - whichever the domain uses), style/commit conventions, and **no environment-specific values** (no absolute machine paths, personal profiles, hostnames - use placeholders).
   - **Forward-safe ordering + per-item gate:** order tasks so none depends on a later task's output, and have each task leave the domain gate green in its own commit, so a regression is attributable to the task that caused it.
   - Ground each task in the Phase-1 evidence (exact `file:line` / tool findings) so the implementer verifies rather than guesses.

4. **Apply fixes - subagent-driven with per-item review.** Work one task at a time, tracking progress in a durable ledger (so the run survives interruption):
   1. Dispatch a **fresh implementer subagent** with: where the fix fits, the task brief + evidence, the global constraints and the report-file path. It makes the change, re-runs the domain gate to green, commits, and self-reviews.
   2. **Review against evidence:** a reviewer subagent (or inline if subagents are unstable) verifies the fix actually resolves the finding *against the real artifact/tool output* - not just that it looks plausible. Spec compliance + quality.
   3. **Resolve findings:** fix Critical/Important before advancing; apply easy correct Minor fixes; resolve any "can't verify from the diff" item yourself against the evidence.
   4. Record the task complete in the ledger. **One implementer at a time** (parallel implementers collide on shared files).

5. **Whole-branch review - a multi-reviewer, confidence-scored pass.** After all fixes, review the whole branch with **several specialized reviewer subagents running in parallel**, each taking one lens (the lenses are assembled from the `## Review lens` sections of the records whose fixes were applied; always include a "verify claims against the real artifact/tool output" reviewer). Collect their findings, then **rate each finding on a described three-point confidence scale** for whether it is real rather than a false positive - `confirmed` (a reviewer checked the claim against the artifact or tool output and the mechanism holds), `likely` (the mechanism is sound on reading but nothing was checked against the artifact), `speculative` (it reads as plausible and no mechanism was established) - and **act at a named point on that scale**: fix `confirmed` and `likely` (and easy, correct minor ones), and report the full findings list with a disposition for each (fixed / not-a-real-issue-with-reason / deferred-with-reason). Resolve anything a reviewer "couldn't verify from the diff" yourself against the evidence. Fix everything real in one follow-up pass; use the most capable model available for this gate.

6. **Finish.** Open a PR. State the CI implications up front - a docs/config-only audit usually stays off the heavy code gates; a code-changing audit needs the normal lint/typecheck/test (and any review) gates. Update the tracking issue and tick only acceptance criteria you verified. **Do not merge without explicit user approval.**

## Running a route

A record's frontmatter says what the check runs, and turning that into a command line is this section's subject. It is engine doctrine rather than the sweep's, because the deep-audit entry point is a domain skill invoked directly by name: such a run reads its own `SKILL.md`, this file, and the records in its own `checks/` directory, so an instruction kept anywhere but those does not reach it - and leaving it to the records means every record carrying its own copy of it, which is what the record schema exists to avoid. What must be *present* in the target before a tool answers is step 1's subject, not this one - read the grants and tiers there and the route's own `needs` here.

**A route hands you the tool's own command line, not a runner's, so getting the tool is a separate question from running it.** A `kind: command` route's `argv` spells the command the record prescribes - `pytest --cov-branch`, `pip-audit -r requirements.txt`, `cyclonedx-py requirements` - and a tool the audit environment does not already carry has to be obtained before that command runs. Obtain it with a **one-shot runner in front of the prescribed command** rather than by installing anything, because step 1's **Never install into the target** is unconditional and a check is not a reason to breach it: `uvx <tool>` for a package published on PyPI, `pipx run <tool>` where the environment carries `pipx` and not `uv`, `npx <tool>` for a package published on npm. **`uvx` and `uv run --with` are not interchangeable, and the routes this record schema prescribes fall on both sides of the line.** uv's own documentation puts it as `uvx <name>` being nearly equivalent to `uv run --no-project --with <name> -- <name>`, so it always runs the tool isolated from the project, and says that a tool which should *not* be isolated - naming `pytest` and `mypy` - takes `uv run` instead. A route whose tool only reads the target's files takes `uvx`; a route whose tool has to import the target's own code or load its plugins takes `uv run --with <tool>`, which is why `test/coverage-reach`'s `pytest --cov-branch --cov-report=term-missing` is a `uv run --with pytest-cov` invocation and not a `uvx pytest` one - the isolated form gets an environment without the target's package or its plugin, and fails in a way that reads as the check having no answer. The named forms are where to start rather than the set of what is allowed: where a runner named here is absent from the audit environment, or the tool's registry is one none of them reaches, use any documented one-shot form that does reach that registry. Only where no runner at all reaches it is the tool genuinely unobtainable, and that is `no-evidence (tool-unavailable)` for this route rather than for the check, since another route may still answer it. **The runner has to reach the registry the tool is published in, and a route's `lang` does not name that registry** - `lang` says which of the target's languages the route applies to, so a `lang: any` or `lang: none` route naming a registry package needs that package's own registry whatever the partition speaks, and `test/new-code-coverage`'s `diff-cover` is a PyPI package, so `uvx diff-cover` is the invocation on a TypeScript partition too. Letting the partition choose the registry is how a different implementation runs under the same name and nothing says so: an unrelated npm package called `diff-cover` also exists, so `npx diff-cover` does not fail - it prints a plausible diff-coverage number computed by a tool nobody prescribed. **A runner reaches only one of the three kinds of thing a record can name, so read what the route names before choosing how to run it.** A *registry package* is what the runners above are for, as long as the audit runs it **as a command**; one the audit has to *import* rather than execute - a parser an audit-owned script walks with, a plugin an audit-owned config loads - is not served by a one-shot runner at all, because the runner resolves the package into a sandbox and the audit's own script or config resolves its imports from where that file lives, so the import fails before the tool does anything. A *subcommand of the target's own package manager* has nothing to fetch: run it directly, and run it only where that package manager is the partition's own, because such a subcommand resolves from the lockfile of the manager that owns it, and no runner can supply a subcommand of a manager the target does not use. A *standalone binary* belongs to no language registry at all, so it is available where the audit environment already carries it and unavailable otherwise, and no one-shot runner will install it. Attempting either of the latter two as if it were a package fails the way a missing tool fails, which lands in the report as `no-evidence (tool-unavailable)` for a check the target could in fact have answered. **Prefer whatever the inventory reports already installed**, which is pinned by the target's own lockfile and already trusted by that project, and treat the runner as the fallback: it resolves a package at run time and executes third-party code in the audit environment, which is the same exposure the no-writes invariant below is checked rather than promised for, so **record the resolved version of every tool fetched this way** and, where policy forbids fetching at all, run only what is already installed and mark the rest `no-evidence`.

**A record may carry `routes:` instead of `tooling:`, replacing it and its `needs:`/`ungranted_note:` side-mappings with one list of routes, each one way of answering the check in one language - read the frontmatter for which schema a given record uses before choosing how to run anything, since the migration between the two is partial and ongoing and either can appear.** Match a route to your partition by its `lang`, except a `lang: any` or `lang: none` route, which applies regardless of the partition's language - `arch/complexity-gate`'s `lang: none` route, a repo-wide fact read off configuration rather than a lens over source, and skipping it because it names no partition language leaves the check unanswered. Within your language, a route's `kind` says what it is, not only what it names: a `kind: command` route is the only one that hands you something to run - its `argv`, or the matching entry in `argv_by_partition` for your own partition - so do not invent a command line for any other kind. Where such a route carries no shared `argv` and its per-partition map does not name your partition, that is the record saying this partition has no command for the check, not a defect and not a licence to supply one: report `no-evidence` for that language unless another route answers it, because the input the missing command would need is exactly what the record is telling you the partition does not have. Such a route may also carry a `then` - a second command the record prescribes in sequence, the same route's second half rather than a route of its own - and you run both, in the order the record writes them: dropping the second reports a tool that produced nothing, which is why `coverage run -m pytest` followed by `coverage report --show-missing` is one route rather than two. It may also carry `own_runner`, which says the prescribed command is complete as written, so the one-shot runner the paragraph above otherwise requires goes in front of nothing - `true` where every command the route prescribes needs none, its shared `argv` and its per-partition overrides alike - or, on a route carrying no shared `argv`, the commands its map names, those being every command it prescribes - and a list of partitions where only their overrides do. Fronting such a command fetches a package the command never calls, and the run then reports that package's resolved version as the one that answered. A `kind: library` route is code the check computes over rather than invokes; treat it as an audit-owned script would be treated, not as something a one-shot runner executes. A `kind: procedure` route is what a record uses wherever it tells you what to do rather than what to run, which includes every tool it names without prescribing a command line for it, and it includes a tool that is itself a command-line tool for which the record still prescribes no command line - follow what its `note` instructs (read a contract, read CI config, walk a computed edge set) rather than guessing an invocation for it. A `kind: subject` route names a tool that is the check's subject rather than its instrument - running it answers a different check, the way `arch/complexity-gate` names `ruff`, `radon` and `xenon` as what `arch/complexity` runs rather than what this gate does - so a `subject` route answers nothing for the check that lists it. A route's `disposition` defaults to `runs`; `alternative` and `superseded` are offered but not run by default - a `superseded` route stays in the record to name the trap its replacement narrows, such as `cycles.md`'s bare `pydeps --show-cycles` and bare `madge --circular`, each of which can exit 0 with nothing on a real cycle - and `forbidden` marks a route named only to warn against, never one to run. `alone_insufficient` marks a route whose clean result does not by itself answer the check, so pair it with whatever its `note` says is still missing, and `applies_when` states a precondition the target must carry for the route to apply at all, skipped otherwise. A route's own `needs` carries the same two tiers `tooling:`'s side-mapping does, but per route rather than per record; `answers_ungranted: none` is the routes-schema counterpart of `ungranted_note: none`, and it is scoped the same way step 1 scopes that field - only where every answering-kind, non-forbidden route for your partition's language needs the withheld grant does the sentinel license `no-evidence (not-permitted)` for that language, so run whatever untiered route your language still offers before treating the sentinel as the end of the question.

## Authoring a new auditing skill

A `<domain>-audit` skill is thin: it states the lens and defers the loop above to this engine.

**Checks are records, not prose.** Each check the domain runs is one file under that domain's own skill, at `<domain>-audit/checks/<slug>.md`, with its machine-checkable attributes in YAML frontmatter (`id`, `domain`, `locality`, `handbook`, `optin`, an optional `evidence` carrying what this check measures and what a row records as its evidence, where that belongs to the check rather than to any one route, and one of two mutually exclusive schemas for what the check runs: `tooling`/`needs`/`ungranted_note`, or `routes`/`answers_ungranted`) and its judgment prose in the body: the claim as lead prose, then `## Severity`, `## Tooling fallback`, `## Fix`, `## Review lens`, omitting any section the check has nothing to say in. `## Tooling fallback` is a section of a record declaring `tooling:`; a record declaring `routes:` has none, because there the routes are the fallback and a section beside them is a second copy nothing holds against the first - what the section carries on one schema, a route's `note`, `alone_insufficient` and `needs` carry on the other. An executing agent loads the subset its slice needs - `locality: local` checks per partition, one `global` check per agent - so no agent pays for the rest of the domain. A check that is decidable per-partition except for one repo-global fact splits into a `local` check and a `global` one, because "report this once" is not something N parallel agents can honour. `handbook` lists the handbook clauses grounding the check and is validated against the traceability matrix in both directions; a check that deliberately exceeds the handbook carries an empty list and a `handbook_note` saying why. Every record **detects before it prescribes** - prefer a tool the target project already runs, and give a fallback that works when none is installed, because a check that only works with its favourite tool present reports absence of tooling as absence of findings, and a tool that needs more than a read-only clone is named in `needs:` (or, on a record declaring `routes:`, on the route's own `needs` field) as well as in the prose, so the constraint is machine-readable where a run selects tools and explained where an agent reads what to do instead. That obligation is the record's rather than any one section's, and each schema discharges it in its own place: a record declaring `tooling:` in `## Tooling fallback`, which states which of its candidates applies to a partition and in what order; a record declaring `routes:` in the routes themselves, where their order and each route's `disposition` state the preference, and a route's `note`, `alone_insufficient` and `applies_when` say what still answers where the preferred tool is absent. A record whose every tool in some language needs a grant also carries an `ungranted_note` saying what the check still answers when that grant is withheld, because what a tool needs and what a check can do without it are different claims, and deriving the second from the first is wrong wherever the check has an axis that needs no tool at all. Under `routes:` the same rule runs per route rather than per tool and its field says less: `answers_ungranted` takes only the sentinel `none`, it is required exactly where a language's every answering-kind, non-`forbidden` route needs the grant, and what the check still answers there is carried by the untiered routes themselves - so a record keeping one of those carries no such field, and its absence is the answer rather than an omission. A `handbook_note` cites a stable identifier - a matrix row `id`, a check id, a heading - and never a line number: a `grep` command may stay in the note as the reproduction step, but the citation itself must survive an edit to the file it points at, since a line number a later edit shifts silently stops pointing at the clause it was written to ground. See `../arch-audit/checks/` for the reference set.

A domain's records live with the domain, not in a shared tree here: this engine owns the record *schema*, each skill owns its *instances*. That keeps a domain portable - a repo adopting three of the nine copies three skill directories plus this engine - and keeps a record one hop from the `SKILL.md` naming it rather than two hops through a sibling skill, which is the nesting depth Anthropic's skill guidance warns leads an agent to preview a file instead of reading it.

**The skill file holds only what does not vary by check:** the subject and how to slice it, the ground-truth artifact to build once, the status scale, whether fixes touch code, and any opt-in *deliverables* (a generated config, a rendered report - things that produce an artifact rather than findings-matrix rows). Measured across the eight migrated domains, the header body ranges from about 370 words (`deps`) to about 1020 words (`prompt`) - measure your own domain rather than copying either number forward as a target. Check count does not predict the size: `arch` carries 11 checks in the low 500s and `test` needs about 590 for 7. What actually drives it is (a) how many of the domain's checks are `global`-locality *and* need a stated, non-generic reason why no per-partition agent can decide them - a domain where every check shares one uniform reason (`deps`) states it once cheaply, while one with several case-by-case exceptions (`ci`, `eval`) must justify each - and (b) whether the domain carries a cross-cutting classification or fix pattern that applies across many checks at once and has no single check to record it in. `prompt`'s tier split (which checks apply to a formal SOP versus a general prompt) is exactly the second case, and it is why `prompt`, despite having only one `global` check, is the densest header in the family.

## Cross-cutting rules (all domains)

- **Verify against evidence, always.** Every finding and every fix cites the artifact/tool output it rests on. Reviews exist to catch confident-but-wrong claims.
- **Cross-link, don't duplicate.** If another skill/doc already owns a topic (e.g. `security-audit` and `deps-audit` both touch CVEs), one owns it and the other links.
- **Attribution / provenance honesty.** Never fabricate a source, URL, license, or CVE id; "unverified, tracked in issue #N" is an acceptable honest outcome.
- **Fix pre-existing issues you touch** if small and real; discuss larger ones before expanding scope.
- **Keep the domain gate green per task**, so regressions are attributable.
- **No environment-specific values** in committed artifacts - placeholders with prose explaining what they resolve to.
- **No writes to the target's working tree or git history.** Not "do not touch the target": the emitter may later create issues in the audited project's tracker, which leaves the working tree untouched, and a rule worded too broadly would have to be broken instead of kept. Check it rather than promise it: capture `git status --porcelain` at `target_root` when scope is fixed and again after the matrix is built, and report any delta as a defect of the audit run. This catches the accidental case, because a package manager asked only to read will write a cache or a lockfile into the tree given the chance. Installing the target's dependencies is the same violation done deliberately, so it is never the way to satisfy a tool that needs them; `git worktree add` is barred for the same reason and is the more dangerous case, since it writes only under `.git/` and so leaves the working-tree comparison above green.
- **Project-agnostic.** Discover packages/layout/tooling/conventions from the target repo via the project inventory (its manifests and lockfiles, whatever they are, plus the contributor guide and existing config); impose a standard only if none exists, and confirm it with the user.
