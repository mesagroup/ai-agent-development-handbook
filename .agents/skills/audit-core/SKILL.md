# Audit Core - the shared audit engine

Every `*-audit` skill is the **same loop** applied through a different lens. This skill owns that loop so the domain skills stay thin and behave consistently. A domain skill provides the lens (its checks, evidence sources, tooling, severity rubric, and fix patterns) and defers the mechanics to here.

**Core principle:** an audit is only as good as the evidence under it. Gather evidence from the actual artifacts (source, config, lockfiles, workflow files, test runs) - never from a summary, a stale doc, or an assumption. A confident finding built on a guess is worse than no finding.

**Announce (from the domain skill):** "I'm using the `<domain>-audit` skill (on the audit-core engine) to audit `<subject>`."

**Pin every subagent to the working tree you are in.** When the audit runs from a git worktree, a dispatched agent given a bare or main-repo-rooted path can silently operate on the *primary* checkout instead, often many commits stale. Both directions fail quietly. A read-only evidence agent then reports ground truth from a tree nobody is auditing, which is the stale-source failure the core principle above forbids. An implementer's edit lands where `git status` in your worktree will never show it, so the fix drops out of the commit and reads afterwards as though the agent simply missed it. Resolve `git rev-parse --show-toplevel` once as `target_root`, pass it in every dispatch, and require each agent to confirm its own `--show-toplevel` matches before it reads or edits.

## The loop

Runs in order; each step feeds the next.

0. **Scope + mode.** Fix the subject (which package/tree/config) and the depth. **Always ask the user the mode:** *report-only* (produce the findings matrix + report and stop) or *report + fix* (continue through remediation). For a large subject in fix mode, deliver in **increments** (one coherent slice per PR) rather than one giant change. Resolve any opt-in sub-audits here too (ask once if an argument didn't specify).

   **Resolve the target, once, and record it.** An audit of another repository is the normal case, not the exception, so nothing may infer the subject from the working directory.
   - `target_root`: `git rev-parse --show-toplevel`, resolved to a real path. Every tool invocation and every glob is pathed at it. It often equals the working directory and nothing may *assume* that, because the assumption is what silently audits the wrong tree.
   - `target_ref`: the `HEAD` short SHA, the branch name, and whether the tree is dirty. A target checked out on a non-default branch is common, and a report that omits the ref neither reproduces nor maps onto what the audited team sees on their own default branch.
   - `out_path`: where the report file goes. **Ask for it, and refuse any path that resolves under `target_root`.** The consolidated report is always returned in conversation as well, so a run given no path is never silent. A non-interactive run defaults to conversation only and writes nothing.
   - `grants`: whether this run may materialize the target's dependency tree, and whether it may execute code from the target's graph, the target's own or an installed package's. Both are **off unless the user grants them**, they are separate, and holding the first does not confer the second. The implication runs the other way and only that way: **`target-execution` implies `resolved-tree`**, because the target's own code imports from the tree, so a run granted execution alone still materializes the tree first rather than running the suite against an unresolved graph. Resolve them here for the same reason the opt-in sub-audits are resolved here: a dispatched agent has nobody to ask, so a permission that has to be asked for is a permission it cannot obtain. Record which were granted, and record the scratch directory each reconstruction used.

1. **Gather evidence - fan out read-only subagents in parallel.** This is the load-bearing step. Dispatch one read-only agent per slice of the subject (per package, per config file, per check - whatever partitions cleanly) to collect *ground-truth* evidence: run the domain's tools, read the relevant files, and report a structured result. Run the domain's detection/measurement tooling here (see the domain skill for which, and `## Running a route` below for how a record's route becomes a command line). Also gather the project's existing conventions (contributor guide, prior audits, existing config) so remediation matches house style.

   **Match the fan-out axis to each check's *locality*, don't hardcode one axis.** Build any shared ground-truth artifact (a parsed graph, a resolved dependency tree, a coverage map) **once** - once per graph scope for a parsed graph, once for everything else - and let agents consume it, rather than each rebuilding a possibly-inconsistent copy. **The first such artifact is always the project inventory**, and it is the one every domain needs: per repository the `target_root`, the `target_ref`, the dirty flag, the monorepo tool and its workspace globs, and the CI workflow list; per partition the path, the **language set**, the package manager and lockfile, the test runner, which audit-relevant tools the partition already has, and whether it is a **deployable** or a **shared package**, decided from two signals read in this order and recorded as undetermined, with what was looked at, where neither decides: a partition carrying a deploy artefact of its own - a container file, a deploy or serverless manifest, a CI job that deploys it, an application entry point - is a deployable whatever imports it, because a test, end-to-end or tooling partition that depends on an application does not make the application a library; a partition with no such artefact that another partition imports - a manifest dependency on it, by workspace protocol or by name, a build tool's dependency edge, or a source import that resolves to the partition whether or not a manifest declares it - is a shared package; a partition with neither is undetermined, so an undetermined partition is by construction imported by nothing and its set has no inbound edges, and a repository of one partition is the exception the graph-scope paragraph below states, its one partition the one deployable whatever the signals say. An edge from one deployable into another is read in the importer's graph as an edge into a foreign module, the way an edge into a shared package is, and puts neither deployable in a shared scope; it is also the importer's own finding, because two partitions that ship separately and import each other's source are coupled across a deploy boundary, so the edge is reported in the importer's row as a crossing edge, and two deployables importing each other are that finding in each row rather than a cycle that neither graph holds both halves of. The inventory records which partitions import each shared package, and it lists the **shared scopes**: the groups of shared packages connected by the import edges between shared packages, in either direction, where an edge is a manifest dependency, by workspace protocol or by name, a build tool's dependency edge, or a source import resolved to the other package, declared or not, so a one-way import between two shared packages puts both in one scope, and two packages whose sources import each other with neither manifest declaring it are one scope with an undeclared dependency for `deps` to report rather than two lone scopes with a cycle that neither owns, and a shared package with no import edge to or from another shared package is a scope of its own, whatever deployables import it: an edge from a deployable never joins two scopes and never keeps a package out of the list. Every shared package belongs to exactly one listed scope, so no finding inside one is left without an owner. The inventory names each scope by the shared packages it holds, and that name is the label a row computed over the scope carries, so a number over a scope of several packages is never reported under one of them alone.

   A partition's language is a set and never a single value, and a manifest is not a language detector: a package that carries a JavaScript manifest for monorepo wiring while containing only Python is classified as JavaScript by any "has a manifest, therefore" rule, whereupon the wrong toolchain runs against no matching source, finds nothing, and reports a pass. Detect by a file census plus declaration files. The already-installed field is what gives every record's "detect before it prescribes" an input, because nothing else computes what the target already runs. Then slice **local** checks (decidable from one partition) per-partition, and give each **global** check (one that needs the whole subject - a cycle, a whole-graph ratio, a cross-file flow, a fact the repository has once) its own agent, because a per-partition agent cannot compute a whole-subject property from its slice. Where the property is a whole-graph one, that agent is computing once per graph scope read from the inventory rather than over the repository, because a repository-wide agent computes it over modules that never meet; a `global` check whose answer is one fact about the project - a register's existence, a declaration the project makes once, a configured threshold - has no graph to scope and is reported once for the repository rather than once per tier, in the row shape its record states, naming every home read and what each held, the binding-rules file, a register, and each partition's own configuration where the fact can live there, so a partition that declares nothing is named as such rather than covered by its neighbour's declaration. Do **not** fan a cheap local check out to its own agent - that duplicates the shared build for no gain. The rules in this step, but for the graph scope below, are the audit-specific shape of the handbook's fan-out clauses, which state them once for any parallel run: [Fan work out to parallel agents, and merge it honestly](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/engineering/lifecycle.md#fan-work-out-to-parallel-agents-and-merge-it-honestly). The general form of each is stated there and not repeated here. Two of them have no counterpart in this step and none anywhere else in this engine's own loop either - that a merged multi-agent artifact is coverage-asserted before anything reads it, and that a rubric a sweep applies grows during the sweep - so the handbook is where a run meets them rather than a second home here. The first of those is a claim about this engine's own merges rather than about the family: `eval/merge-coverage-assertion` asks it of an audited project's pipeline, and nothing asks it of an audit run's own fan-out. The half about writes is stated in [references/remediation-loop.md](references/remediation-loop.md), which is the only step that writes.

   **The graph scope is a third thing beside `local` and `global`, and it is the target's, never the executing agent's to choose.** Locality says how much has to be read before a verdict; the graph scope is the unit a whole-graph property is computed over, and a repository holding several independently deployed services is several graphs rather than one. The default scope is the deployable, read from the inventory's classification above: each deployable is its own graph, holding its own modules, the modules of every shared package it reaches through import edges, directly or through another shared package, and every edge among all of those, an edge from a shared package back into the deployable included, and every edge out of the deployable into another deployable, in its set as a crossing edge though that deployable's modules are not, so a cycle that leaves the deployable and returns through two packages lies whole in the graph the ownership rule below assigns it to; and a shared package that several deployables import is read inside each deployable's graph and also reported once, under the shared scope the inventory lists it in. The shared reading is one scope per shared scope the inventory lists, the shared packages connected by import edges in either direction, not one per package, and its edge set is the scope's modules, the edges among them, **every edge into them from the partitions that import them, deployable or undetermined**, and every edge out of them into a partition outside the scope: a hub inside the package has its fan-in from its importers, `Ca` is the count of those inbound edges, and a set holding the package's modules alone would report the library everyone imports as coupled to nothing; and an edge from a shared package into any partition outside the scope, a deployable whether or not it imports the scope through this or another of its packages, is the scope's own finding, a library importing an application, reported in its row as a crossing edge the way a deployable's edge into another deployable is; that the deployable also imports the scope makes the pair a cycle across the boundary, which is the deployable's cycle row because its graph holds both halves, while the scope's edge into the deployable is still the scope's own crossing-edge row: two findings, a cycle and a library importing an application, each with one owner. The two readings answer different questions and a finding belongs to exactly one of them, so nothing is reported twice and nothing is left with no owner: a finding whose every module is a shared module - a cycle among a package's modules or across two packages of the scope, a hub inside the package with its inbound edges counted, a ratio over the scope, and any count of a shared symbol's consumers, its importers, the implementers of its abstraction, the callers of its wrapper, the registrants of its registry, the values bound to its parameter - is the shared scope's row, computed there once over every partition that imports the scope and never repeated under an importer, because one importer's graph sees only its own consumption of the symbol and would report that as the symbol's total, a single implementer per deployable for a base class the whole repository implements twice; the shared reading reads the importing modules its inbound edges name for that count; a finding that involves at least one of a deployable's own modules is that deployable's row, an edge crossing from the deployable into a package included, which is why the package's modules are in the deployable's graph at all, but not a single edge crossing into the deployable from a scope, which the rule below gives to the side that imports; and an edge that crosses a scope boundary belongs to the side that imports, whichever kind of partition it starts in or lands in, so no edge is left to a graph that never sees it. Underneath every clause above is one rule: every import edge in the repository is in its importer's set, a deployable's, a shared scope's or an undetermined partition's, and an edge into a shared scope from outside is counted there for fan-in and owned as a finding where it starts. Every module is a deployable's, a shared scope's or an undetermined partition's, so every finding has exactly one owner. That is what makes a cycle inside the shared package found once rather than once per importer, and what keeps a library defect out of the severity roll-up of every service that happens to depend on it; a coupling ratio over two services that never import each other is never computed at all. Where the inventory records a partition as undetermined, compute per partition over a set of its own, its modules, the edges among them and every edge out of it into another partition, which it owns as their importer, report that as the reason beside every number it produced, and never compute across the repository: a whole-graph ratio over modules that never call each other is not wrong so much as meaningless, and a reader has no way to tell which reading produced it. A single-partition repository is one deployable, one graph, one scope, stated once, whatever the two signals say of it: the classification exists to split a repository into graphs, a repository of one partition has nothing to split, and a library with no deploy artefact and no importer is listed as the one deployable rather than as undetermined, so its numbers carry no reason. The scope governs whole-graph properties computed over the import graph and nothing else: a `global` check whose answer is a declaration or a configured fact has no graph to scope and is reported once for the repository, in the row shape its record states, naming every home read and what each held, each partition's own configuration among them; and a `global` check whose subject is coupling the import graph does not contain reads its tells in every partition and confirms a pairing across the whole repository, because the pair it looks for, two modules touching one shared state, two writers or a writer and a reader through a global, a singleton or a locator, is exactly what no scope's edge set holds. A single-module tell, an import-time side effect or a dynamic import, is its module's partition's row. A pairing is owned by the scope of the module that declares the shared state, the shared scope for a shared package's export and the deployable for its own, whatever name the state is re-exported under, for the reason a consumer count is the shared scope's: the pair has no single importer, and the declared state is the one element both touch. The classification does not assume a deployable is a process boundary and the reading is over source, so the row names the partitions the touching modules belong to, and a reader who knows the deployment can tell a pair sharing one object at runtime from two processes each holding their own copy. Nothing about this changes a record: `locality` stays what it is, and the scope is read from the inventory by the agent running a whole-graph check rather than declared per check. This rule is the audit's own rather than the audit-specific shape of a handbook clause: the handbook's fan-out section sends a whole-subject question to one agent holding the whole thing, and says nothing about what the whole thing is when a repository holds several graphs.

   **What a tool needs *present* is a different question from where it comes from, and a record answers both.** A `tooling:` name may be obtainable and still unable to answer: `knip` is a registry package any one-shot runner can fetch and it wants `typescript` and `@types/node` installed before it reports anything true, while `osv-scanner` is a standalone binary no runner can fetch and it reads a lockfile straight off a read-only clone. The record's `needs:` frontmatter carries the second axis per tool - absent means the tool answers from source, manifests and lockfiles; `resolved-tree` means it needs the dependency graph materialized to read package metadata; `target-execution` means it needs that and runs code from the target's graph, the target's own or an installed package's. Read it before choosing a tool, because the failure it prevents is not a tool that refuses to start: it is a tool that starts, finds an empty dependency graph, and reports nothing wrong. A record declaring `routes:` instead of `tooling:`/`needs:` states the same axis per route, as that route's own `needs` field, so the same read-before-choosing rule applies one route at a time rather than through a shared mapping.

   **Never install into the target; reconstruct outside it.** Installing dependencies writes to the tree under audit, so it is barred by the invariant below whatever the user granted - and `git worktree add` is barred with it, because it writes `.git/worktrees/` and leaves no working-tree delta, so it would slip past the very `git status --porcelain` comparison that watches for this. Where the run holds the `resolved-tree` grant (which `target-execution` implies, so a run holding only the execution grant materializes the tree here as well rather than running the target's code against an unresolved graph), copy the target to a scratch directory that does **not** resolve under `target_root` - the same refusal `out_path` gets, for the same reason - and resolve there, with `--ignore-scripts` or that package manager's equivalent. **A check that needs a package the target does not declare copies again rather than adding it to that tree.** The reconstruction is a shared artifact by the rule above, built once and handed to every domain at once, so a package installed into it to make one check runnable - a missing coverage provider, a mutation runner's plugin - changes the graph the other domains are concurrently measuring, and the disagreement building it once exists to prevent then arrives by the sanctioned route instead of from parallel resolutions. It also plants a dependency the target never declared in the tree `deps` reads, where nothing distinguishes it from one the target did declare. So an install a check needs for itself goes into a copy that check owns, and a record prescribing one says which copy it means; **a package the audit added is never evidence about the target**, in any domain. **Express every evidence pointer taken from that copy relative to `target_root`, never to the scratch tree.** Step 2 requires a `file:line` on every row, and a tool run against the copy reports the copy's paths, so a licence or hygiene finding carried through unchanged cites a temporary directory that exists only inside this run - a path the audited team cannot open and cannot check the finding against. Say so in the report: a reconstructed graph is weaker evidence than a lockfile read in place, because it can differ from what the audited team actually has installed, and a reader who is not told cannot discount it. Where the run holds no grant, a check with nothing left that answers in this partition's language is `no-evidence (not-permitted)` rather than clean, and which fields settle that is a question about the schema the record declares. **On a record declaring `tooling:`, the silenced case is a language whose every tool carries a `needs:` tier, and the escape is that record's `ungranted_note`, which says what the check still answers without the grant.** The note is required on exactly the records this rule would silence, so the answer is there to read rather than inferred: a note naming a source-reading, syntax-tree or registry pass means the check reports the domain's own status with the missing axis named, and only the sentinel `none` means the whole question is unanswerable here. **On a record declaring `routes:`, decide it over that language's answering-kind (`command`, `library`, `procedure`), non-`forbidden` routes and over nothing else** - a `kind: subject` route names what the check inspects rather than what answers it, so it neither gives a language a claim to silence nor supplies one's escape, and a `lang: any` or `lang: none` route applies whatever the partition's language is. **There the escape is the untiered route itself rather than a field to read**: run whatever answering route that language still offers carrying no tier before treating the withheld grant as the end of the question. `answers_ungranted` carries no prose of its own - only the sentinel `none` - and is present exactly where no untiered answering route is left, so its absence beside an untiered route is the ordinary answered case and not a missing field. **Never read the silenced case off a migrated record's `tooling`/`needs` pair.** Those two are projected from its routes, and the projection carries tools and tiers and no ungranted claim at all: `arch/complexity-gate` tiers ESLint under `typescript` and names it `kind: subject`, so the projected pair reads that language as fully tiered while no route there was answering the check in the first place, and `arch/complexity` and `arch/hidden-coupling` read the same way through the projection while each keeps a TypeScript route that needs no grant. **The pair over-reports tiering a second way that has nothing to do with `kind: subject`, so an agent that has learned only the subject-route mechanism still misreads it:** the projection collapses a record's routes onto their tools, so one tool carrying a tiered route beside an untiered one reads as simply tiered. `deps/inventory` is that shape - `cyclonedx-py` prescribes the per-partition subcommands that read a dependency file, and separately, as an `alternative`, `cyclonedx-py environment`, which starts the partition's interpreter to read the installed environment and carries `target-execution` because it must. The pair therefore reports that tool as needing that grant while the route the record actually prescribes answers from a read-only clone. So read the tier off the route you are about to run, never off the tool: a tier on any one of a tool's routes is not a claim about the others. Assigning `no-evidence` to a check whose record says otherwise records an unanswered question that the clone could have answered, which is the same false negative as reporting a tool's empty output as a clean result.

   **An install hook is execution, not resolution.** A `postinstall` runs third-party code from the target's graph in the audit environment, which is the `target-execution` tier by what it does rather than by when it happens. So a tree that will not resolve with scripts disabled does not license dropping the flag under a `resolved-tree` grant: either the run also holds `target-execution`, or the check falls to the rule above - on a record declaring `tooling:`, where every tool it offers for this partition's language needs the grant, its `ungranted_note` governs, so the check is `no-evidence (not-permitted)` only where that note is the sentinel and otherwise reports the domain's own status with the missing axis named; on a record declaring `routes:`, where every answering-kind, non-`forbidden` route for that language needs the grant, `answers_ungranted: none` is what the record carries and the check is `no-evidence (not-permitted)`, while an untiered answering route left in that language is itself what still runs, and where the record's routes carry `answers` that field says which axis it answers and which stays `no-evidence`; and on either schema, where the record keeps something that answers from a read-only clone, that answers and there is no note to consult. This costs real coverage on a graph with native builds, and the alternative costs more - a grant the user understood as "read the licences" silently running whatever a dependency's install hook contains.

   **Starting the target's interpreter is execution too.** A Python interpreter runs the `.pth` files in its `site-packages` when it starts, and those files are code the target's graph installed, so a route whose command starts the partition's interpreter executes that graph whatever it then reads, and it is `target-execution` for the reason an install hook is: by what it does. That covers every `in_env` Python route run through the in-environment forms `## Running a route` names, all of which start the partition's interpreter, and any other route whose command starts it, `in_env` or not, and it holds for a tool that only reads package metadata, such as `pip-licenses` or `uv pip list --outdated`. Measured on the seeded uv and pip partitions, a marker-writing `.pth` planted in a scratch copy's venv was written by each `in_env` Python route that had been tiered `resolved-tree`, in `deps/freshness`, `deps/hygiene`, `deps/licenses` and `deps/transitive-licenses`; `uv pip list --python` wrote it whenever its cached description of the interpreter was stale, which it is on a tree step 1 has just built, so a run that happens to find the cache warm is not evidence that the route runs nothing. `resolved-tree` is therefore a grant to read the materialized graph without running anything in it, and a route that needs the interpreter started needs `target-execution` as well.

2. **Build the findings matrix.** Consolidate the evidence into a table: **item × check × status × severity × handbook**, plus a one-line evidence pointer (`file:line`, tool output, or metric) for every row. **A row is one instance of what the check finds**, the one thing its evidence pointer names: a location - a `file:line`, an import edge, a function, a dependency - for a finding in the code; the graph scope, for a whole-graph metric computed over one; and the home that was read, for something found absent there. So the same defect in three places is three rows, and two runs over the same tree report the same count rather than two groupings of it. A record whose unit is something else states it instead, as the first sentence of its `evidence` field, in the form `Row unit: <unit>, because <why>` - the project, for a declaration the project either made or did not - and a row then covers that unit however many locations its pointer lists. A pattern the rows share is the report's theme and the emitter's cluster, never a reason to fold rows into one. A row carrying a whole-graph metric states in that pointer the graph scope it was computed over, the deployable, the shared scope or the undetermined partition by the name the inventory lists it under, and the module count it covered; a number with no scope beside it is a finding against the report rather than a metric, because a ratio over one service and a ratio over the whole repository print alike and mean different things. A row a scope owns names that scope in its pointer whether or not it carries a number, and a row reported once for the repository names the repository. The `handbook` cell is read from the check record's `handbook:` frontmatter, so the matrix introduces no new source of truth; a record carrying an empty list renders its `handbook_note` instead, marked as deliberately beyond the handbook. Cite a stable identifier, a matrix row `id` or a heading, never a line number, which a later edit shifts so that it silently stops pointing at the clause it was written to ground.

   Status is a small fixed scale the domain defines (e.g. pass / partial / fail, or ok / warn / violation). Whatever scale the domain picks, three outcomes are distinct and must never collapse into one another: the domain's own clean-result value (`ok` in the example scale above) means the check ran against this partition and found nothing, while **`no-evidence`** and **`not-applicable`** are additions to that scale, not replacements for it - **`no-evidence`** means the check applies here and no tooling or fallback could run, for the check or, where the record's routes carry `answers`, for one of its axes, and **`not-applicable`** means the check has no lens in this partition's languages. `no-evidence` carries a reason, because the ways a check can fail to run are not equally anyone's fault and each reason names what would answer the question next time: `not-permitted` (it needed a grant this run does not hold - for the check, or, where the record's routes carry `answers`, for the axis whose routes all needed it - so re-running with the grant answers it), `tool-unavailable` (no candidate could be obtained - unfetchable, not installed, or no network, so the audit environment answers it - or no candidate could be obtained for this axis, where the record's routes carry `answers` and a sibling axis having run is not a reason to report `ok`; and a route whose grant the run holds but whose tree step 1 could not build is this reason too, because no tool ran to have failed: an install that failed is answered by the same audit environment, network, registry access or a system library a build needs, and a lockfile its manager refuses under the frozen install step 1 chooses is the run's way of building the tree failing rather than a tool, the refusal being a candidate `deps` finding in its own right, so the row's evidence pointer names the materialization step that failed and the error it printed, which is how the reader learns it was the tree and not the tool - except where that error names a lifecycle script the scripts-off install skipped, or an artefact one would have produced, which step 1's install-hook rule treats as a withheld `target-execution` grant, so the route is `not-permitted` and the check falls to the ungranted rule, the pointer recording that the hook was inferred from the error rather than run), `tool-failed` (a tool ran and errored or returned nothing parseable, so neither does), and `not-prescribed` (the record prescribes *nothing that answers this partition* - no command for it, and no `library` or `procedure` route that applies here either - and offers no route a grant would enable, so nothing about this run or this environment will ever answer it - the gap is in the record or in the ecosystem, and only a report that says so lets a reader stop looking for a fix that does not exist). **Every clause of that gloss is required, and the two after the first are what keep it honest.** "No command" alone is not the test, because a `kind: library` route hands you code to compute over and a `kind: procedure` route tells you what to do rather than what to run, and a language whose only routes are those still answers: `arch/over-decomposition` prescribes exactly one Python route, an untiered `grimp` library route that reads a read-only clone, and a rule testing only for a command would certify that check as permanently unanswerable. And: a partition a record prescribes nothing for while keeping a tiered route is `not-permitted`, because the grant does answer it, and reporting the absent prescription there is the standing false lead this vocabulary exists to prevent. So where more than one reason is true, report the one a reader can act on, and put the other in the row's evidence pointer: a partition can be both answerable with a grant and permanently without any route that answers from a read-only clone, and the reason cell holds one of those while the pointer is where the reader learns the cheap path is closed for good. **The vocabulary grows only for a genuinely different answer to that question**, which is the test to apply to a fifth reason rather than counting the ones already here. The *status* scale does not grow at all: a fourth status would collapse the distinction this paragraph just drew, in the other direction. Render the reason with the status, as `no-evidence (not-permitted)`. Reporting `no-evidence` as a clean result reports absence of tooling as absence of findings; reporting `not-applicable` as a clean result is how a polyglot repository earns a clean bill of health for code nobody looked at. Severity is Critical / Important / Minor. Summarize counts. Write the findings report to the `out_path` resolved in step 0, never under `target_root`, and record any policy decisions so they are not re-litigated. The rule is unconditional, and it holds when the audited repository is the one asking: a point-in-time report is a fact *about* a tree at a ref rather than a part of that tree, and writing one into the audited tree turns a read-only audit into an uninvited commit on somebody else's branch. A carve-out for the self-audit case would also make step 0's refusal conditional on something step 0 cannot yet know, and would put a sanctioned write inside the very tree the no-writes check watches.

**If the mode is report-only, stop here** - present the findings matrix + report (with a short recommended-remediation sketch), modify no files, and ask the user whether to proceed to fixes. Steps 3–6 run only in report + fix mode.

**If the mode is report + fix, the remaining four steps are** [references/remediation-loop.md](references/remediation-loop.md) - plan the remediation, apply the fixes one task at a time with a per-item review, review the whole branch, open the PR. Read it at this point and follow it from step 3; the numbering continues, and `## Cross-cutting rules (all domains)` below applies to those steps as much as to these. A report-only run reaches none of it.

## Running a route

A record's frontmatter says what the check runs, and turning that into a command line is this section's subject. It is engine doctrine rather than the sweep's, because the deep-audit entry point is a domain skill invoked directly by name: such a run reads its own `SKILL.md`, this file, the references this file sends it to, and the records in its own `checks/` directory, so an instruction kept anywhere else does not reach it - and leaving it to the records means every record carrying its own copy of it, which is what the record schema exists to avoid. What must be *present* in the target before a tool answers is step 1's subject - read the grants and tiers there and the route's own `needs` here, and read this section's closing clause for how step 1's ungranted rule is scoped over a record's routes.

**A route hands you the tool's own command line, not a runner's, so getting the tool is a separate question from running it.** A `kind: command` route's `argv` spells the command the record prescribes - `pytest --cov-branch`, `pip-audit -r requirements.txt`, `cyclonedx-py requirements` - and a tool the audit environment does not already carry has to be obtained before that command runs. Obtain it with a **one-shot runner in front of the prescribed command** rather than by installing anything, because step 1's **Never install into the target** is unconditional and a check is not a reason to breach it: `uvx <tool>` for a package published on PyPI, `pipx run <tool>` where the environment carries `pipx` and not `uv`, `npx <tool>` for a package published on npm. **Where a route's `package` differs from its `tool`, the runner is told which package provides the command, and the argv runs as written after it:** `uvx --from <package>`, `pipx run --spec <package>` and `npx --package=<package> --` each name the package to fetch and then run the command that follows from it, so `deps/inventory`'s isolated `cyclonedx-py` route runs as `uvx --from cyclonedx-bom cyclonedx-py environment <path-to-venv-python>`, the distribution being published under a name the command does not carry. The bare form asks the registry for a package carrying the command's name, which is not the package the record names. A route that names no `package` is fetched by its `tool`, and on an `in_env` route the `package` is the `--with` package instead, as below. **A route's argv can name a file this plugin ships, as a token reading `CLAUDE_PLUGIN_ROOT` between `${` and `}` followed by the file's path under it, and you replace that token with the plugin's install directory before the command runs.** The shell a sweep's commands run in does not set that variable, measured in a Claude Code session, and a check record is read as a file, so nothing substitutes the token on its way to you: left as written, the shell expands it to nothing and the tool is handed a path under the filesystem root, which fails as a missing file and lands as a `tool-failed` row for a check the plugin could have answered. The install directory is three levels above the base directory Claude Code prints when it loads any skill of this plugin, which is `.agents/skills/<skill>/` under that directory; wherever Claude Code loaded this text as a skill it is also the path shown here, ${CLAUDE_PLUGIN_ROOT}; and where the environment does set the variable, its value is that same directory. **`uvx` and `uv run --with` are not interchangeable, and the route says which it needs rather than leaving it to your judgement of what the tool does.** uv's own documentation puts it as `uvx <name>` being nearly equivalent to `uv run --no-project --with <name> -- <name>`, so it always runs the tool isolated from the project, and says that a tool which should *not* be isolated - naming `pytest` and `mypy` - takes `uv run` instead. **`in_env: true` is the field that says a route's command has to run inside the materialized environment**, which is why the loader refuses `own_runner` beside it - a suppressed prefix never arrives there - and it is the same reason the isolated form is wrong for such a route. The field decides which copy of the tool runs and which environment it sees, whatever kind of thing the route names: the command runs from the partition's own package directory against the tree step 1 built, under the grant the route's own `needs` names, and without that grant the route is not run at all - the isolated form is no fallback for it. The form differs by language. **On a Python partition the form is uv's on every package manager, and the tool comes in from outside the environment while the command runs against it:** `uv run --no-sync --with <tool>` on a `uv` partition, and `uv run --no-project --python <path-to-venv-python> --with <tool>` on a `pip`, `poetry`, `pipenv` or `pylock` one, naming the interpreter that partition's own materialization built. The `--with` package is the route's `package` where it names one and its `tool` otherwise, and a route's `then` runs under the same prefix as its `argv`. The flag beside `--with` is load-bearing on each, for one reason: a bare `uv run` locks and syncs the project it discovers before running anything. On a `uv` partition `--no-sync` runs the command in the project's venv as it stands, where without it a lock gone stale beside its `pyproject.toml` is rewritten and the venv the checks read is re-synced - and `--frozen` is not the substitute, because it leaves the lock alone and still syncs the venv to it, reinstalling whatever step 1 left out. On the others `--no-project` stops `uv run` discovering the copy's `pyproject.toml` at all, where without it it writes a `uv.lock` the tree never had and resolves the tool into a fresh project environment instead of the one named, and `--python` is what makes this the opposite of the `uvx` equivalence above rather than a spelling of it: the `--with` layer sits on the named venv, so the tool sees everything the target installed. The partition's own runner, `poetry run` or `pipenv run`, is not the substitute it looks like, because making the tool reachable that way installs it into the venv the checks read - measured on a poetry partition, it replaced the exact pin a freshness check was there to find outdated. A package-manager subcommand on an `in_env` Python route takes the same form, with its manager as the `--with` package - `deps/freshness`'s `pip list --outdated` has to run under the partition's interpreter rather than whichever `pip` the audit host carries, and a venv built without pip has none of its own - and where the command needs the environment named as well, the record's argv names it, as `deps/freshness`'s `uv pip list --outdated --python <path-to-venv-python>` does. `test/coverage-reach`'s `pytest --cov-branch --cov-report=term-missing` is an `in_env` registry-package route, and the package to fetch is its tool, `pytest-cov`, so the invocation is `uv run --no-sync --with pytest-cov` on a `uv` partition and the `--no-project` form elsewhere, rather than `uvx pytest`, which would get an environment holding neither the target's package nor the plugin. **On a TypeScript partition there is no layer outside the tree to bring a tool in through, so the command runs the tree's own copy:** `npx --no -- <argv>` on npm, where `--no` declines the install prompt rather than fetching and `--` ends npx's own options, so a trailing flag such as `--version` reaches the tool rather than npx; `pnpm --config.verify-deps-before-run=false exec <argv>` on pnpm, which puts the package's `node_modules/.bin` on `PATH` and passes everything after `exec` to the tool, and whose flag is load-bearing for the same reason `--no-sync` is on uv: pnpm 11 defaults `verifyDepsBeforeRun` to `install`, so a bare `pnpm exec` installs into the tree first wherever it judges `node_modules` out of date, outside the frozen, scripts-off build step 1 made; and on Yarn, which no fixture here exercises and which these forms therefore take from Yarn's own documentation alone, `yarn run -B <argv>` on Yarn Modern, whose `--binaries-only` stops a `package.json` script of the same name from running in the tool's place and which takes `-T` as well where the tool is declared at the workspace root rather than in the package, and `yarn run <argv>` on Yarn classic, whose documentation lets that name be a script or a locally installed executable and documents no flag to choose between them, so where the package's `scripts` has a same-named entry run `npx --no -- <argv>` instead, which reads the same `node_modules/.bin`, once the inventory confirms the audit environment carries `npx`. The `.yarnrc.yml` signal the sweep's runner bullet gives is what tells the two Yarns apart. The isolated form is wrong there for the same reason as for Python, and fails less visibly: `npx --yes --package=<tool>` uses the tree's copy only where one matches and otherwise fetches a registry copy without asking - npm assumes `--yes` wherever standard input is not a terminal - and `pnpm dlx` always fetches from the registry, so either can run a version the target's lockfile never pinned, with nothing in the output to say which copy ran. The Python form is wrong outright: `uv run --with vitest` resolves `vitest` against PyPI, which is not the registry an npm tool is published in, and runs it in an environment holding none of the target's packages. Two things follow from there being no outside layer. **Confirm from the inventory that the tree carries the tool before running it**, because none of these forms is confined to the tree - `npx --no` resolves from npx's own cache as well, so a copy an earlier one-shot fetch left there still runs and still prints a version, and `pnpm exec` runs whatever its `PATH` holds - so a tool that runs is no evidence that the tree carries it. And **where the tree does not carry the tool, the route is `no-evidence (tool-unavailable)`**, never a reason to fetch it isolated or to install it into the target; a record whose route needs a companion package the target does not declare says in its own note where that package goes, as `test/coverage-reach`'s vitest route does for its coverage provider. A subcommand of the partition's own package manager on a TypeScript partition already reads that partition's tree, so it runs bare, as the three kinds below say, `in_env` or not. A standalone binary is never fetched on either language, `in_env` or not: on an `in_env` route it runs as the audit environment carries it, pointed at the tree, and nothing goes in front of it as a `--with` package. A route without `in_env` does not run inside the environment, and where it names a registry package the one-shot runner named above for its registry is right for it. **Do not decide this from what the tool looks like it does.** `pip-licenses` itself imports none of the target's code and loads no plugin, and its routes are `in_env`, because the command they prescribe reads whichever environment it runs in, so the isolated runner would have it report on an environment holding nothing of the target's - which is the empty result that reads exactly like a clean one. Reading installed metadata does not decide it either: `deps/inventory`'s `cyclonedx-py environment <path-to-venv-python>` reads the same metadata and is not `in_env`, because its argv names the interpreter whose environment it reads, so it runs isolated and still reports on the target's venv. The route's `in_env` is what to read. An `in_env` route whose in-environment form the audit environment cannot run takes the tree's own copy where the inventory shows the tree carries the tool, running the route's argv from the tree's own bin directory - `<venv>/bin/<argv>` on Python, `node_modules/.bin/<argv>` on TypeScript, the argv's first word being the command and not necessarily the route's `tool` - and is `no-evidence (tool-unavailable)` otherwise - never run through an isolated runner instead. The named forms are where to start rather than the set of what is allowed on a route without `in_env`: where a runner named here is absent from the audit environment, or the tool's registry is one none of them reaches, use any documented one-shot form that does reach that registry. Only where no runner at all reaches it is the tool genuinely unobtainable, and that is `no-evidence (tool-unavailable)` for this route rather than for the check, since another route may still answer it. **The runner has to reach the registry the tool is published in, and a `lang: any` or `lang: none` route's `lang` names no registry at all** - `lang` says which of the target's languages the route applies to, so such a route naming a registry package needs that package's own registry whatever the partition speaks, and `test/new-code-coverage`'s `diff-cover` is a PyPI package, so `uvx diff-cover` is the invocation on a TypeScript partition too. Letting the partition choose the registry is how a different implementation runs under the same name and nothing says so: an unrelated npm package called `diff-cover` also exists, so `npx diff-cover` does not fail - it prints a plausible diff-coverage number computed by a tool nobody prescribed. **The route's `registry` names it, so read the field rather than inferring the registry from anything else.** A `kind: command` route carries `registry: pypi` or `registry: npm` wherever its `lang` implies no registry, which is exactly the `lang: any` and `lang: none` case, and the loader requires it there wherever the command is not already complete as written - `test/new-code-coverage`'s `diff-cover` route carries `registry: pypi`, which is where `uvx` on a TypeScript partition comes from. Where `lang` names a language the registry is the one that language implies, `python` PyPI and `typescript` npm, and the loader holds the field against `lang` so the two cannot disagree. **Nothing holds the field against the route's `note`**, so where a note and a registry name different registries the field is what you act on and the note is what needs fixing. A route carrying `own_runner: true` fetches nothing and so carries no registry at all - the loader rejects one there - and on a record still declaring `tooling:` rather than `routes:` there is no field to read either, where `## Tooling fallback` is what says which registry that record's candidates come from. **A runner reaches only one of the three kinds of thing a record can name, so read what the route names before choosing how to run it.** A *registry package* is what the runners above are for, as long as the audit runs it **as a command**; one the audit has to *import* rather than execute - a parser an audit-owned script walks with, a plugin an audit-owned config loads - is not served by a one-shot runner at all, because the runner resolves the package into a sandbox and the audit's own script or config resolves its imports from where that file lives, so the import fails before the tool does anything. A *subcommand of the target's own package manager* has nothing to fetch: run it directly, and run it only where that package manager is the partition's own, because such a subcommand resolves from the lockfile of the manager that owns it, and no runner can supply a subcommand of a manager the target does not use. An `in_env` Python route is the exception, as above: its subcommand reads the installed environment rather than a lockfile, so it runs on any Python partition, its manager brought in with `--with` over the partition's interpreter. A *standalone binary* belongs to no language registry at all, so it is available where the audit environment already carries it and unavailable otherwise, and no one-shot runner will install it. Attempting either of the latter two as if it were a package fails the way a missing tool fails, which lands in the report as `no-evidence (tool-unavailable)` for a check the target could in fact have answered. **Prefer whatever the inventory reports already installed**, which is pinned by the target's own lockfile and already trusted by that project, and treat the runner as the fallback: it resolves a package at run time and executes third-party code in the audit environment, which is the same exposure the no-writes invariant below is checked rather than promised for, so **record the resolved version of every tool fetched this way** and, where policy forbids fetching at all, run only what is already installed and mark the rest `no-evidence`.

**A record may carry `routes:` instead of `tooling:`, replacing it and its `needs:`/`ungranted_note:` side-mappings with one list of routes, each one way of answering the check in one language - read the frontmatter for which schema a given record uses before choosing how to run anything, since the migration between the two is partial and ongoing and either can appear.** Match a route to your partition by its `lang`, except a `lang: any` or `lang: none` route, which applies regardless of the partition's language - `arch/complexity-gate`'s `lang: none` route, a repo-wide fact read off configuration rather than a lens over source, and skipping it because it names no partition language leaves the check unanswered. Within your language, a route's `kind` says what it is, not only what it names: a `kind: command` route is the only one that hands you something to run - its `argv`, or the matching entry in `argv_by_partition` for your own partition - so do not invent a command line for any other kind. **A partition key names a package manager, not a version of one, so a keyed entry can spell a subcommand this partition's manager does not have: where it does, the shared `argv` is what you run and the keyed entry is not.** `yarn` is the live case - every `yarn`-keyed entry in the tree spelling `dlx` is Yarn Modern's form, `dlx` does not exist in Yarn classic, and each of those routes carries an `npx`-led shared `argv` reaching the same registry for exactly this reason. Taking the keyed entry because its key matched is how a tool that was obtainable all along gets reported `no-evidence (tool-unavailable)`; the runner rule above says why the shared form is a real answer rather than a downgrade. Where such a route carries no shared `argv` and its per-partition map does not name your partition, that is the record saying this partition has no command for the check, not a defect and not a licence to supply one: report `no-evidence (not-prescribed)` for that partition unless another route answers it, because the input the missing command would need is exactly what the record is telling you the partition does not have. **Read "unless another route answers it" as including a route a grant would enable**: where the record keeps a tiered route for this language, the reason is `not-permitted` and not `not-prescribed`, because re-running with the grant answers the check and reporting an absent prescription instead sends the reader after a fix that does not exist. **This is a different question from `answers_ungranted`, and the two do not compete**: that sentinel is decided per language over the record's answering routes and says whether the check is silenced for the language as a whole, while the reason step 2 renders is read off what has a command on *this* partition - which is why a record can carry no sentinel, because the language keeps an untiered answering route, and still leave one of its partitions with nothing to run. Such a route may also carry a `then` - a second command the record prescribes in sequence, the same route's second half rather than a route of its own - and you run both, in the order the record writes them: dropping the second reports a tool that produced nothing, which is why `coverage run -m pytest` followed by `coverage report --show-missing` is one route rather than two. It carries `registry` wherever its `lang` implies none and its command is not already complete as written, naming the registry the runner in front of it has to reach, which is the field the runner paragraph above chooses from. It may also carry `own_runner`, that field's complement, which says the prescribed command is complete as written, so the one-shot runner the paragraph above otherwise requires goes in front of nothing - `true` where every command the route prescribes needs none, its shared `argv` and its per-partition overrides alike - or, on a route carrying no shared `argv`, the commands its map names, those being every command it prescribes - and a list of partitions where only their overrides do. Fronting such a command fetches a package the command never calls, and the run then reports that package's resolved version as the one that answered. A `kind: library` route is code the check computes over rather than invokes; treat it as an audit-owned script would be treated, not as something a one-shot runner executes. A `kind: procedure` route is what a record uses wherever it tells you what to do rather than what to run, which includes every tool it names without prescribing a command line for it, and it includes a tool that is itself a command-line tool for which the record still prescribes no command line - follow what its `note` instructs (read a contract, read CI config, walk a computed edge set) rather than guessing an invocation for it. A `kind: subject` route names a tool that is the check's subject rather than its instrument - running it answers a different check, the way `arch/complexity-gate` names `ruff`, `radon` and `xenon` as what `arch/complexity` runs rather than what this gate does - so a `subject` route answers nothing for the check that lists it. A route's `disposition` defaults to `runs`; `alternative` and `superseded` are offered but not run by default - a `superseded` route stays in the record to name the trap its replacement narrows, such as `cycles.md`'s bare `pydeps --show-cycles` and bare `madge --circular`, each of which can exit 0 with nothing on a real cycle - and `forbidden` marks a route named only to warn against, never one to run - on a `kind: command` route the argv it carries, and on a `kind: procedure` route the tool it names, which is the shape a record takes to warn against a tool it prescribes no invocation for, its `note` saying why, as `docs/source-wrapping` does for `markdownlint` and `test/coverage-reach` for `c8` around a Vitest command; such a route answers no axis and is never what a language still answers with once a grant is withheld. `alone_insufficient` marks a route whose own result does not by itself answer the check, in either of two ways the field says which of: a clean result that needs pairing with whatever the field or the route's `note` says is still missing, or a hit that is a candidate rather than a finding until the confirmation the field names has run, as a source-to-sink trace confirms a scanner hit or a read of the importing modules confirms a coupling tell - so do what the field says before reporting either a clean result or a finding from that route, and `applies_when` states a precondition the target must carry for the route to apply at all, skipped otherwise. `answers` names the axis of the check a route answers, where a record's routes in one language answer different halves of it: two routes with the same value are alternatives for that axis and their `disposition` states the precedence, two with different values are complements, and a record whose every route answers the whole check carries the field nowhere. **The check is answered in a language only when every distinct `answers` value in that language has a route that ran**, a route having run when it produced its axis's evidence rather than `no-evidence`; an axis with no such route is `no-evidence` with the reason read over that axis's routes alone by the per-route rules above, never `ok`, whatever a sibling axis returned. Findings a route produced on the way are reported as findings in their own rows whatever its axis's status, as they always are; what the unanswered axis decides is the check's status where the answered axis found nothing, and the coverage count, where a half-answered check counts as `no-evidence` rather than as ran. The check's row names in its evidence the axis that answered and the one that did not, so a reader can tell a half-answered check from a clean one. The status scale does not grow for this: `no-evidence (tool-unavailable)` on the unanswered axis is what a run that got one tool and not the other reports, and `no-evidence (not-permitted)` what a withheld grant leaves on an axis whose routes all needed it. On a record still declaring `tooling:`, a withheld grant is read through its `ungranted_note` as step 1 says, the domain's own status with the missing axis named; that reading belongs to the legacy schema and ends with its migration, and a record on `routes:` with `answers` reads by this rule alone. A route's own `needs` carries the same two tiers `tooling:`'s side-mapping does, but per route rather than per record; `answers_ungranted: none` is the routes-schema counterpart of `ungranted_note: none`, and it is scoped the same way step 1 scopes that field - only where every answering-kind, non-forbidden route for your partition's language needs the withheld grant does the sentinel license `no-evidence (not-permitted)` for that language, so run whatever untiered route your language still offers before treating the sentinel as the end of the question.

## Authoring a new auditing skill

[references/authoring-a-new-auditing-skill.md](references/authoring-a-new-auditing-skill.md) - **read it when writing or restructuring a `<domain>-audit` skill, and not during a run.** What a skill file holds and what belongs in a check record instead, why a domain's records live with the domain, and the record schema an author has to satisfy. ## Cross-cutting rules (all domains)

- **Verify against evidence, always.** Every finding and every fix cites the artifact/tool output it rests on. Reviews exist to catch confident-but-wrong claims.
- **Cross-link, don't duplicate.** If another skill/doc already owns a topic (e.g. CVEs are reached from more than one lens), one owns it and the other links.
- **Attribution / provenance honesty.** Never fabricate a source, URL, license, or CVE id; "unverified, tracked in issue #N" is an acceptable honest outcome.
- **Fix pre-existing issues you touch** if small and real; discuss larger ones before expanding scope.
- **Keep the domain gate green per task**, so regressions are attributable.
- **No environment-specific values** in committed artifacts - placeholders with prose explaining what they resolve to.
- **No writes to the target's working tree or git history.** Not "do not touch the target": the emitter creates issues in the audited project's tracker, which leaves the working tree untouched, and a rule worded too broadly would have to be broken instead of kept. Check it rather than promise it: capture `git status --porcelain` at `target_root` when scope is fixed and again after the matrix is built, and report any delta as a defect of the audit run. This catches the accidental case, because a package manager asked only to read will write a cache or a lockfile into the tree given the chance. Installing the target's dependencies is the same violation done deliberately, so it is never the way to satisfy a tool that needs them; `git worktree add` is barred for the same reason and is the more dangerous case, since it writes only under `.git/` and so leaves the working-tree comparison above green.
- **Project-agnostic.** Discover packages/layout/tooling/conventions from the target repo via the project inventory (its manifests and lockfiles, whatever they are, plus the contributor guide and existing config); impose a standard only if none exists, and confirm it with the user.
