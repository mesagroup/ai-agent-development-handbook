# Audit Core - the shared audit engine

Every `*-audit` skill is the **same loop** applied through a different lens. This skill owns that loop so the domain skills stay thin and behave consistently. A domain skill provides the lens (its checks, evidence sources, tooling, severity rubric, and fix patterns) and defers the mechanics to here.

**Core principle:** an audit is only as good as the evidence under it. Gather evidence from the actual artifacts (source, config, lockfiles, workflow files, test runs) - never from a summary, a stale doc, or an assumption. A confident finding built on a guess is worse than no finding.

**Announce (from the domain skill):** "I'm using the `<domain>-audit` skill (on the audit-core engine) to audit `<subject>`."

**Pin every subagent to the working tree you are in.** When the audit runs from a git worktree, a dispatched agent given a bare or main-repo-rooted path can silently operate on the *primary* checkout instead, often many commits stale. Both directions fail quietly. A read-only evidence agent then reports ground truth from a tree nobody is auditing, which is the stale-source failure the core principle above forbids. An implementer's edit lands where `git status` in your worktree will never show it, so the fix drops out of the commit and reads afterwards as though the agent simply missed it. Resolve `git rev-parse --show-toplevel` once as `target_root`, pass it in every dispatch, and require each agent to confirm its own `--show-toplevel` matches before it reads or edits.

## The loop

Runs in order; each step feeds the next.

0. **Scope + mode.** Fix the subject (which package/tree/config) and the depth. **Always ask the user the mode:** *report-only* (produce the findings matrix + report and stop) or *report + fix* (continue through remediation). For a large subject in fix mode, deliver in **increments** (one coherent slice per PR) rather than one giant change. Resolve any opt-in sub-audits here too (ask once if an argument didn't specify).

   **Resolve the target, once, and record it.** An audit of another repository is the normal case, not the exception, so nothing may infer the subject from the working directory.
   - `target_root`: `git rev-parse --show-toplevel`, resolved to a real path. Every tool invocation and every glob is pathed at it. It often equals the working directory and nothing may *assume* that, because the assumption is what silently audits the wrong tree.
   - `target_ref`: the `HEAD` short SHA, the branch name, and whether the tree is dirty. A target checked out on a non-default branch is common, and a report that omits the ref neither reproduces nor maps onto what the audited team sees on their own default branch.
   - `out_path`: where the report file goes. **Ask for it, and refuse any path that resolves under `target_root`.** The consolidated report is always returned in conversation as well, so a run given no path is never silent. A non-interactive run defaults to conversation only and writes nothing.
   - `grants`: whether this run may materialize the target's dependency tree, and whether it may execute the target's own code. Both are **off unless the user grants them**, they are separate, and holding the first does not confer the second. The implication runs the other way and only that way: **`target-execution` implies `resolved-tree`**, because the target's own code imports from the tree, so a run granted execution alone still materializes the tree first rather than running the suite against an unresolved graph. Resolve them here for the same reason the opt-in sub-audits are resolved here: a dispatched agent has nobody to ask, so a permission that has to be asked for is a permission it cannot obtain. Record which were granted, and record the scratch directory each reconstruction used.

1. **Gather evidence - fan out read-only subagents in parallel.** This is the load-bearing step. Dispatch one read-only agent per slice of the subject (per package, per config file, per check - whatever partitions cleanly) to collect *ground-truth* evidence: run the domain's tools, read the relevant files, and report a structured result. Run the domain's detection/measurement tooling here (see the domain skill for which, and `## Running a route` below for how a record's route becomes a command line). Also gather the project's existing conventions (contributor guide, prior audits, existing config) so remediation matches house style.

   **Match the fan-out axis to each check's *locality*, don't hardcode one axis.** Build any shared ground-truth artifact (a parsed graph, a resolved dependency tree, a coverage map) **once** and let agents consume it, rather than each rebuilding a possibly-inconsistent copy. **The first such artifact is always the project inventory**, and it is the one every domain needs: per repository the `target_root`, the `target_ref`, the dirty flag, the monorepo tool and its workspace globs, and the CI workflow list; per partition the path, the **language set**, the package manager and lockfile, the test runner, and which audit-relevant tools the partition already has.

   A partition's language is a set and never a single value, and a manifest is not a language detector: a package that carries a JavaScript manifest for monorepo wiring while containing only Python is classified as JavaScript by any "has a manifest, therefore" rule, whereupon the wrong toolchain runs against no matching source, finds nothing, and reports a pass. Detect by a file census plus declaration files. The already-installed field is what gives every record's "detect before it prescribes" an input, because nothing else computes what the target already runs. Then slice **local** checks (decidable from one partition) per-partition, and give each **global** check (one that needs the whole subject - a cycle, a whole-graph ratio, a cross-file flow) its own agent over the whole artifact, because a per-partition agent cannot compute a whole-subject property from its slice. Do **not** fan a cheap local check out to its own agent - that duplicates the shared build for no gain. The rules in this step are the audit-specific shape of the handbook's fan-out clauses, which state them once for any parallel run: [Fan work out to parallel agents, and merge it honestly](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/engineering/lifecycle.md#fan-work-out-to-parallel-agents-and-merge-it-honestly). The general form of each is stated there and not repeated here. Two of them have no counterpart in this step and none anywhere else in this engine either - that a merged multi-agent artifact is coverage-asserted before anything reads it, and that a rubric a sweep applies grows during the sweep - so the handbook is where a run meets them rather than a second home here. The half about writes is stated in [references/remediation-loop.md](references/remediation-loop.md), which is the only step that writes.

   **What a tool needs *present* is a different question from where it comes from, and a record answers both.** A `tooling:` name may be obtainable and still unable to answer: `knip` is a registry package any one-shot runner can fetch and it wants `typescript` and `@types/node` installed before it reports anything true, while `osv-scanner` is a standalone binary no runner can fetch and it reads a lockfile straight off a read-only clone. The record's `needs:` frontmatter carries the second axis per tool - absent means the tool answers from source, manifests and lockfiles; `resolved-tree` means it needs the dependency graph materialized to read package metadata; `target-execution` means it needs that and runs the target's own code. Read it before choosing a tool, because the failure it prevents is not a tool that refuses to start: it is a tool that starts, finds an empty dependency graph, and reports nothing wrong. A record declaring `routes:` instead of `tooling:`/`needs:` states the same axis per route, as that route's own `needs` field, so the same read-before-choosing rule applies one route at a time rather than through a shared mapping.

   **Never install into the target; reconstruct outside it.** Installing dependencies writes to the tree under audit, so it is barred by the invariant below whatever the user granted - and `git worktree add` is barred with it, because it writes `.git/worktrees/` and leaves no working-tree delta, so it would slip past the very `git status --porcelain` comparison that watches for this. Where the run holds the `resolved-tree` grant (which `target-execution` implies, so a run holding only the execution grant materializes the tree here as well rather than running the target's code against an unresolved graph), copy the target to a scratch directory that does **not** resolve under `target_root` - the same refusal `out_path` gets, for the same reason - and resolve there, with `--ignore-scripts` or that package manager's equivalent. **A check that needs a package the target does not declare copies again rather than adding it to that tree.** The reconstruction is a shared artifact by the rule above, built once and handed to every domain at once, so a package installed into it to make one check runnable - a missing coverage provider, a mutation runner's plugin - changes the graph the other domains are concurrently measuring, and the disagreement building it once exists to prevent then arrives by the sanctioned route instead of from parallel resolutions. It also plants a dependency the target never declared in the tree `deps` reads, where nothing distinguishes it from one the target did declare. So an install a check needs for itself goes into a copy that check owns, and a record prescribing one says which copy it means; **a package the audit added is never evidence about the target**, in any domain. **Express every evidence pointer taken from that copy relative to `target_root`, never to the scratch tree.** Step 2 requires a `file:line` on every row, and a tool run against the copy reports the copy's paths, so a licence or hygiene finding carried through unchanged cites a temporary directory that exists only inside this run - a path the audited team cannot open and cannot check the finding against. Say so in the report: a reconstructed graph is weaker evidence than a lockfile read in place, because it can differ from what the audited team actually has installed, and a reader who is not told cannot discount it. Where the run holds no grant, a check with nothing left that answers in this partition's language is `no-evidence (not-permitted)` rather than clean, and which fields settle that is a question about the schema the record declares. **On a record declaring `tooling:`, the silenced case is a language whose every tool carries a `needs:` tier, and the escape is that record's `ungranted_note`, which says what the check still answers without the grant.** The note is required on exactly the records this rule would silence, so the answer is there to read rather than inferred: a note naming a source-reading, syntax-tree or registry pass means the check reports the domain's own status with the missing axis named, and only the sentinel `none` means the whole question is unanswerable here. **On a record declaring `routes:`, decide it over that language's answering-kind (`command`, `library`, `procedure`), non-`forbidden` routes and over nothing else** - a `kind: subject` route names what the check inspects rather than what answers it, so it neither gives a language a claim to silence nor supplies one's escape, and a `lang: any` or `lang: none` route applies whatever the partition's language is. **There the escape is the untiered route itself rather than a field to read**: run whatever answering route that language still offers carrying no tier before treating the withheld grant as the end of the question. `answers_ungranted` carries no prose of its own - only the sentinel `none` - and is present exactly where no untiered answering route is left, so its absence beside an untiered route is the ordinary answered case and not a missing field. **Never read the silenced case off a migrated record's `tooling`/`needs` pair.** Those two are projected from its routes, and the projection carries tools and tiers and no ungranted claim at all: `arch/complexity-gate` tiers ESLint under `typescript` and names it `kind: subject`, so the projected pair reads that language as fully tiered while no route there was answering the check in the first place, and `arch/complexity` and `arch/hidden-coupling` read the same way through the projection while each keeps a TypeScript route that needs no grant. **The pair over-reports tiering a second way that has nothing to do with `kind: subject`, so an agent that has learned only the subject-route mechanism still misreads it:** the projection collapses a record's routes onto their tools, so one tool carrying a tiered route beside an untiered one reads as simply tiered. `deps/inventory` is that shape - `cyclonedx-py` prescribes the per-partition subcommands that read a dependency file, and separately, as an `alternative`, `cyclonedx-py environment`, which reads the installed environment and carries `resolved-tree` because it must. The pair therefore reports that tool as needing the tree while the route the record actually prescribes answers from a read-only clone. So read the tier off the route you are about to run, never off the tool: a tier on any one of a tool's routes is not a claim about the others. Assigning `no-evidence` to a check whose record says otherwise records an unanswered question that the clone could have answered, which is the same false negative as reporting a tool's empty output as a clean result.

   **An install hook is execution, not resolution.** A `postinstall` runs third-party code from the target's graph in the audit environment, which is the `target-execution` tier by what it does rather than by when it happens. So a tree that will not resolve with scripts disabled does not license dropping the flag under a `resolved-tree` grant: either the run also holds `target-execution`, or the check falls to the rule above - on a record declaring `tooling:`, where every tool it offers for this partition's language needs the grant, its `ungranted_note` governs, so the check is `no-evidence (not-permitted)` only where that note is the sentinel and otherwise reports the domain's own status with the missing axis named; on a record declaring `routes:`, where every answering-kind, non-`forbidden` route for that language needs the grant, `answers_ungranted: none` is what the record carries and the check is `no-evidence (not-permitted)`, while an untiered answering route left in that language is itself what still runs and there is no field to consult; and on either schema, where the record keeps something that answers from a read-only clone, that answers and there is no note to consult. This costs real coverage on a graph with native builds, and the alternative costs more - a grant the user understood as "read the licences" silently running whatever a dependency's install hook contains.

2. **Build the findings matrix.** Consolidate the evidence into a table: **item × check × status × severity × handbook**, plus a one-line evidence pointer (`file:line`, tool output, or metric) for every row. The `handbook` cell is read from the check record's `handbook:` frontmatter, so the matrix introduces no new source of truth; a record carrying an empty list renders its `handbook_note` instead, marked as deliberately beyond the handbook. Cite a stable identifier, a matrix row `id` or a heading, never a line number, which a later edit shifts so that it silently stops pointing at the clause it was written to ground.

   Status is a small fixed scale the domain defines (e.g. pass / partial / fail, or ok / warn / violation). Whatever scale the domain picks, three outcomes are distinct and must never collapse into one another: the domain's own clean-result value (`ok` in the example scale above) means the check ran against this partition and found nothing, while **`no-evidence`** and **`not-applicable`** are additions to that scale, not replacements for it - **`no-evidence`** means the check applies here and no tooling or fallback could run, and **`not-applicable`** means the check has no lens in this partition's languages. `no-evidence` carries a reason, because the ways a check can fail to run are not equally anyone's fault and each reason names what would answer the question next time: `not-permitted` (it needed a grant this run does not hold, so re-running with the grant answers it), `tool-unavailable` (no candidate could be obtained - unfetchable, not installed, or no network, so the audit environment answers it), `tool-failed` (a tool ran and errored or returned nothing parseable, so neither does), and `not-prescribed` (the record prescribes *nothing that answers this partition* - no command for it, and no `library` or `procedure` route that applies here either - and offers no route a grant would enable, so nothing about this run or this environment will ever answer it - the gap is in the record or in the ecosystem, and only a report that says so lets a reader stop looking for a fix that does not exist). **Every clause of that gloss is required, and the two after the first are what keep it honest.** "No command" alone is not the test, because a `kind: library` route hands you code to compute over and a `kind: procedure` route tells you what to do rather than what to run, and a language whose only routes are those still answers: `arch/over-decomposition` prescribes exactly one Python route, an untiered `grimp` library route that reads a read-only clone, and a rule testing only for a command would certify that check as permanently unanswerable. And: a partition a record prescribes nothing for while keeping a tiered route is `not-permitted`, because the grant does answer it, and reporting the absent prescription there is the standing false lead this vocabulary exists to prevent. So where more than one reason is true, report the one a reader can act on, and put the other in the row's evidence pointer: a partition can be both answerable with a grant and permanently without any route that answers from a read-only clone, and the reason cell holds one of those while the pointer is where the reader learns the cheap path is closed for good. **The vocabulary grows only for a genuinely different answer to that question**, which is the test to apply to a fifth reason rather than counting the ones already here. The *status* scale does not grow at all: a fourth status would collapse the distinction this paragraph just drew, in the other direction. Render the reason with the status, as `no-evidence (not-permitted)`. Reporting `no-evidence` as a clean result reports absence of tooling as absence of findings; reporting `not-applicable` as a clean result is how a polyglot repository earns a clean bill of health for code nobody looked at. Severity is Critical / Important / Minor. Summarize counts. Write the findings report to the `out_path` resolved in step 0, never under `target_root`, and record any policy decisions so they are not re-litigated. The rule is unconditional, and it holds when the audited repository is the one asking: a point-in-time report is a fact *about* a tree at a ref rather than a part of that tree, and writing one into the audited tree turns a read-only audit into an uninvited commit on somebody else's branch. A carve-out for the self-audit case would also make step 0's refusal conditional on something step 0 cannot yet know, and would put a sanctioned write inside the very tree the no-writes check watches.

**If the mode is report-only, stop here** - present the findings matrix + report (with a short recommended-remediation sketch), modify no files, and ask the user whether to proceed to fixes. Steps 3–6 run only in report + fix mode.

**If the mode is report + fix, the remaining four steps are** [references/remediation-loop.md](references/remediation-loop.md) - plan the remediation, apply the fixes one task at a time with a per-item review, review the whole branch, open the PR. Read it at this point and follow it from step 3; the numbering continues, and `## Cross-cutting rules (all domains)` below applies to those steps as much as to these. A report-only run reaches none of it.

## Running a route

A record's frontmatter says what the check runs, and turning that into a command line is this section's subject. It is engine doctrine rather than the sweep's, because the deep-audit entry point is a domain skill invoked directly by name: such a run reads its own `SKILL.md`, this file, the references this file sends it to, and the records in its own `checks/` directory, so an instruction kept anywhere else does not reach it - and leaving it to the records means every record carrying its own copy of it, which is what the record schema exists to avoid. What must be *present* in the target before a tool answers is step 1's subject - read the grants and tiers there and the route's own `needs` here, and read this section's closing clause for how step 1's ungranted rule is scoped over a record's routes.

**A route hands you the tool's own command line, not a runner's, so getting the tool is a separate question from running it.** A `kind: command` route's `argv` spells the command the record prescribes - `pytest --cov-branch`, `pip-audit -r requirements.txt`, `cyclonedx-py requirements` - and a tool the audit environment does not already carry has to be obtained before that command runs. Obtain it with a **one-shot runner in front of the prescribed command** rather than by installing anything, because step 1's **Never install into the target** is unconditional and a check is not a reason to breach it: `uvx <tool>` for a package published on PyPI, `pipx run <tool>` where the environment carries `pipx` and not `uv`, `npx <tool>` for a package published on npm. **`uvx` and `uv run --with` are not interchangeable, and the route says which it needs rather than leaving it to your judgement of what the tool does.** uv's own documentation puts it as `uvx <name>` being nearly equivalent to `uv run --no-project --with <name> -- <name>`, so it always runs the tool isolated from the project, and says that a tool which should *not* be isolated - naming `pytest` and `mypy` - takes `uv run` instead. **`in_env: true` is the field that says a route's command has to run inside the materialized environment**, which is why the loader refuses `own_runner` beside it - a suppressed prefix never arrives there - and it is the same reason the isolated form is wrong for such a route: run those as `uv run --with <tool>` against the tree step 1 built, under the grant that tree needs. `test/coverage-reach`'s `pytest --cov-branch --cov-report=term-missing` is one, and the package to fetch is its tool, `pytest-cov`, so the invocation is `uv run --with pytest-cov` rather than `uvx pytest`, which would get an environment holding neither the target's package nor the plugin. A route without `in_env` answers from the target's files rather than from its installed environment, and `uvx <tool>` is right for it. **Do not decide this from what the tool looks like it does.** `pip-licenses` imports none of the target's code and loads no plugin, and it reads installed package metadata, so it is an `in_env` route and the isolated runner would have it report on an environment holding nothing of the target's - which is the empty result that reads exactly like a clean one. The named forms are where to start rather than the set of what is allowed: where a runner named here is absent from the audit environment, or the tool's registry is one none of them reaches, use any documented one-shot form that does reach that registry. Only where no runner at all reaches it is the tool genuinely unobtainable, and that is `no-evidence (tool-unavailable)` for this route rather than for the check, since another route may still answer it. **The runner has to reach the registry the tool is published in, and a `lang: any` or `lang: none` route's `lang` names no registry at all** - `lang` says which of the target's languages the route applies to, so such a route naming a registry package needs that package's own registry whatever the partition speaks, and `test/new-code-coverage`'s `diff-cover` is a PyPI package, so `uvx diff-cover` is the invocation on a TypeScript partition too. Letting the partition choose the registry is how a different implementation runs under the same name and nothing says so: an unrelated npm package called `diff-cover` also exists, so `npx diff-cover` does not fail - it prints a plausible diff-coverage number computed by a tool nobody prescribed. **The route's `registry` names it, so read the field rather than inferring the registry from anything else.** A `kind: command` route carries `registry: pypi` or `registry: npm` wherever its `lang` implies no registry, which is exactly the `lang: any` and `lang: none` case, and the loader requires it there wherever the command is not already complete as written - `test/new-code-coverage`'s `diff-cover` route carries `registry: pypi`, which is where `uvx` on a TypeScript partition comes from. Where `lang` names a language the registry is the one that language implies, `python` PyPI and `typescript` npm, and the loader holds the field against `lang` so the two cannot disagree. **Nothing holds the field against the route's `note`**, so where a note and a registry name different registries the field is what you act on and the note is what needs fixing. A route carrying `own_runner: true` fetches nothing and so carries no registry at all - the loader rejects one there - and on a record still declaring `tooling:` rather than `routes:` there is no field to read either, where `## Tooling fallback` is what says which registry that record's candidates come from. **A runner reaches only one of the three kinds of thing a record can name, so read what the route names before choosing how to run it.** A *registry package* is what the runners above are for, as long as the audit runs it **as a command**; one the audit has to *import* rather than execute - a parser an audit-owned script walks with, a plugin an audit-owned config loads - is not served by a one-shot runner at all, because the runner resolves the package into a sandbox and the audit's own script or config resolves its imports from where that file lives, so the import fails before the tool does anything. A *subcommand of the target's own package manager* has nothing to fetch: run it directly, and run it only where that package manager is the partition's own, because such a subcommand resolves from the lockfile of the manager that owns it, and no runner can supply a subcommand of a manager the target does not use. A *standalone binary* belongs to no language registry at all, so it is available where the audit environment already carries it and unavailable otherwise, and no one-shot runner will install it. Attempting either of the latter two as if it were a package fails the way a missing tool fails, which lands in the report as `no-evidence (tool-unavailable)` for a check the target could in fact have answered. **Prefer whatever the inventory reports already installed**, which is pinned by the target's own lockfile and already trusted by that project, and treat the runner as the fallback: it resolves a package at run time and executes third-party code in the audit environment, which is the same exposure the no-writes invariant below is checked rather than promised for, so **record the resolved version of every tool fetched this way** and, where policy forbids fetching at all, run only what is already installed and mark the rest `no-evidence`.

**A record may carry `routes:` instead of `tooling:`, replacing it and its `needs:`/`ungranted_note:` side-mappings with one list of routes, each one way of answering the check in one language - read the frontmatter for which schema a given record uses before choosing how to run anything, since the migration between the two is partial and ongoing and either can appear.** Match a route to your partition by its `lang`, except a `lang: any` or `lang: none` route, which applies regardless of the partition's language - `arch/complexity-gate`'s `lang: none` route, a repo-wide fact read off configuration rather than a lens over source, and skipping it because it names no partition language leaves the check unanswered. Within your language, a route's `kind` says what it is, not only what it names: a `kind: command` route is the only one that hands you something to run - its `argv`, or the matching entry in `argv_by_partition` for your own partition - so do not invent a command line for any other kind. **A partition key names a package manager, not a version of one, so a keyed entry can spell a subcommand this partition's manager does not have: where it does, the shared `argv` is what you run and the keyed entry is not.** `yarn` is the live case - every `yarn`-keyed entry in the tree spelling `dlx` is Yarn Modern's form, `dlx` does not exist in Yarn classic, and each of those routes carries an `npx`-led shared `argv` reaching the same registry for exactly this reason. Taking the keyed entry because its key matched is how a tool that was obtainable all along gets reported `no-evidence (tool-unavailable)`; the runner rule above says why the shared form is a real answer rather than a downgrade. Where such a route carries no shared `argv` and its per-partition map does not name your partition, that is the record saying this partition has no command for the check, not a defect and not a licence to supply one: report `no-evidence (not-prescribed)` for that partition unless another route answers it, because the input the missing command would need is exactly what the record is telling you the partition does not have. **Read "unless another route answers it" as including a route a grant would enable**: where the record keeps a tiered route for this language, the reason is `not-permitted` and not `not-prescribed`, because re-running with the grant answers the check and reporting an absent prescription instead sends the reader after a fix that does not exist. **This is a different question from `answers_ungranted`, and the two do not compete**: that sentinel is decided per language over the record's answering routes and says whether the check is silenced for the language as a whole, while the reason step 2 renders is read off what has a command on *this* partition - which is why a record can carry no sentinel, because the language keeps an untiered answering route, and still leave one of its partitions with nothing to run. Such a route may also carry a `then` - a second command the record prescribes in sequence, the same route's second half rather than a route of its own - and you run both, in the order the record writes them: dropping the second reports a tool that produced nothing, which is why `coverage run -m pytest` followed by `coverage report --show-missing` is one route rather than two. It carries `registry` wherever its `lang` implies none and its command is not already complete as written, naming the registry the runner in front of it has to reach, which is the field the runner paragraph above chooses from. It may also carry `own_runner`, that field's complement, which says the prescribed command is complete as written, so the one-shot runner the paragraph above otherwise requires goes in front of nothing - `true` where every command the route prescribes needs none, its shared `argv` and its per-partition overrides alike - or, on a route carrying no shared `argv`, the commands its map names, those being every command it prescribes - and a list of partitions where only their overrides do. Fronting such a command fetches a package the command never calls, and the run then reports that package's resolved version as the one that answered. A `kind: library` route is code the check computes over rather than invokes; treat it as an audit-owned script would be treated, not as something a one-shot runner executes. A `kind: procedure` route is what a record uses wherever it tells you what to do rather than what to run, which includes every tool it names without prescribing a command line for it, and it includes a tool that is itself a command-line tool for which the record still prescribes no command line - follow what its `note` instructs (read a contract, read CI config, walk a computed edge set) rather than guessing an invocation for it. A `kind: subject` route names a tool that is the check's subject rather than its instrument - running it answers a different check, the way `arch/complexity-gate` names `ruff`, `radon` and `xenon` as what `arch/complexity` runs rather than what this gate does - so a `subject` route answers nothing for the check that lists it. A route's `disposition` defaults to `runs`; `alternative` and `superseded` are offered but not run by default - a `superseded` route stays in the record to name the trap its replacement narrows, such as `cycles.md`'s bare `pydeps --show-cycles` and bare `madge --circular`, each of which can exit 0 with nothing on a real cycle - and `forbidden` marks a route named only to warn against, never one to run. `alone_insufficient` marks a route whose clean result does not by itself answer the check, so pair it with whatever its `note` says is still missing, and `applies_when` states a precondition the target must carry for the route to apply at all, skipped otherwise. A route's own `needs` carries the same two tiers `tooling:`'s side-mapping does, but per route rather than per record; `answers_ungranted: none` is the routes-schema counterpart of `ungranted_note: none`, and it is scoped the same way step 1 scopes that field - only where every answering-kind, non-forbidden route for your partition's language needs the withheld grant does the sentinel license `no-evidence (not-permitted)` for that language, so run whatever untiered route your language still offers before treating the sentinel as the end of the question.

## Cross-cutting rules (all domains)

- **Verify against evidence, always.** Every finding and every fix cites the artifact/tool output it rests on. Reviews exist to catch confident-but-wrong claims.
- **Cross-link, don't duplicate.** If another skill/doc already owns a topic (e.g. CVEs are reached from more than one lens), one owns it and the other links.
- **Attribution / provenance honesty.** Never fabricate a source, URL, license, or CVE id; "unverified, tracked in issue #N" is an acceptable honest outcome.
- **Fix pre-existing issues you touch** if small and real; discuss larger ones before expanding scope.
- **Keep the domain gate green per task**, so regressions are attributable.
- **No environment-specific values** in committed artifacts - placeholders with prose explaining what they resolve to.
- **No writes to the target's working tree or git history.** Not "do not touch the target": the emitter may later create issues in the audited project's tracker, which leaves the working tree untouched, and a rule worded too broadly would have to be broken instead of kept. Check it rather than promise it: capture `git status --porcelain` at `target_root` when scope is fixed and again after the matrix is built, and report any delta as a defect of the audit run. This catches the accidental case, because a package manager asked only to read will write a cache or a lockfile into the tree given the chance. Installing the target's dependencies is the same violation done deliberately, so it is never the way to satisfy a tool that needs them; `git worktree add` is barred for the same reason and is the more dangerous case, since it writes only under `.git/` and so leaves the working-tree comparison above green.
- **Project-agnostic.** Discover packages/layout/tooling/conventions from the target repo via the project inventory (its manifests and lockfiles, whatever they are, plus the contributor guide and existing config); impose a standard only if none exists, and confirm it with the user.
