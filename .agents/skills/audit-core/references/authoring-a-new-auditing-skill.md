# Authoring a new auditing skill

Read this when writing or restructuring a `<domain>-audit` skill. No audit run does that: a run consumes records it did not write, so nothing here has an addressee inside one, which is why [the sweep-obligations ledger](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/audit/sweep-obligations.md) dispositions this reference's own obligation `out of scope`.

A `<domain>-audit` skill is thin: it states the lens and defers the loop in `SKILL.md` to this engine.

**Checks are records, not prose.** Each check the domain runs is one file under that domain's own skill, at `<domain>-audit/checks/<slug>.md`, with its machine-checkable attributes in YAML frontmatter (`id`, `domain`, `locality`, `handbook`, `optin`, an optional `evidence` carrying what this check measures and what a row records as its evidence, where that belongs to the check rather than to any one route, and one of two mutually exclusive schemas for what the check runs: `tooling`/`needs`/`ungranted_note`, or `routes`/`answers_ungranted`) and its judgment prose in the body: the claim as lead prose, then `## Severity`, `## Tooling fallback`, `## Fix`, `## Review lens`, omitting any section the check has nothing to say in. `## Tooling fallback` is a section of a record declaring `tooling:`; a record declaring `routes:` has none, because there the routes are the fallback and a section beside them is a second copy nothing holds against the first - what the section carries on one schema, a route's `note`, `alone_insufficient` and `needs` carry on the other. **Every command the record prescribes appears in an inline backtick span**, because that is the only place the harness's form extractor reads: a command written anywhere else is invisible to every property that holds a record's prescription against what actually ran, and the suite stays green over it. `scripts/audit_checks.py` rejects a body carrying a fenced code block for that reason, in either spelling, and the rejection drops the whole record from the loaded set rather than warning - a four-space indented block is legal, so a record may still show a tool's observed output where that output prints fences. Where a placeholder is glued to a flag rather than standing alone, a name must end at a value delimiter - `=`, `:`, `/` or `@`, so `--cov=<pkg>` and `pkg@<version>` but not `-r<file>` - because the extractor matches such a token as a prefix and `-r` is a prefix of other flags. Write the value as its own token where the command allows it. An executing agent loads the subset its slice needs - `locality: local` checks per partition, one `global` check per agent - so no agent pays for the rest of the domain. A check that is decidable per-partition except for one repo-global fact splits into a `local` check and a `global` one, because "report this once" is not something N parallel agents can honour. `handbook` lists the handbook clauses grounding the check and is validated against the traceability matrix in both directions; a check that deliberately exceeds the handbook carries an empty list and a `handbook_note` saying why. Every record **detects before it prescribes** - prefer a tool the target project already runs, and give a fallback that works when none is installed, because a check that only works with its favourite tool present reports absence of tooling as absence of findings, and a tool that needs more than a read-only clone is named in `needs:` (or, on a record declaring `routes:`, on the route's own `needs` field) as well as in the prose, so the constraint is machine-readable where a run selects tools and explained where an agent reads what to do instead. That obligation is the record's rather than any one section's, and each schema discharges it in its own place: a record declaring `tooling:` in `## Tooling fallback`, which states which of its candidates applies to a partition and in what order; a record declaring `routes:` in the routes themselves, where their order and each route's `disposition` state the preference, and a route's `note`, `alone_insufficient` and `applies_when` say what still answers where the preferred tool is absent. A record whose every tool in some language needs a grant also carries an `ungranted_note` saying what the check still answers when that grant is withheld, because what a tool needs and what a check can do without it are different claims, and deriving the second from the first is wrong wherever the check has an axis that needs no tool at all. Under `routes:` the same rule runs per route rather than per tool and its field says less: `answers_ungranted` takes only the sentinel `none`, it is required exactly where a language's every answering-kind, non-`forbidden` route needs the grant, and what the check still answers there is carried by the untiered routes themselves - so a record keeping one of those carries no such field, and its absence is the answer rather than an omission. A `handbook_note` cites a stable identifier - a matrix row `id`, a check id, a heading - and never a line number: a `grep` command may stay in the note as the reproduction step, but the citation itself must survive an edit to the file it points at, since a line number a later edit shifts silently stops pointing at the clause it was written to ground. See `../../arch-audit/checks/` for the reference set.

A domain's records live with the domain, not in a shared tree under `audit-core`: this engine owns the record *schema*, each skill owns its *instances*. That keeps a domain portable - a repo adopting three of the nine copies three skill directories plus this engine - and keeps a record one hop from the `SKILL.md` naming it rather than two hops through a sibling skill, which is the nesting depth Anthropic's skill guidance warns leads an agent to preview a file instead of reading it.

**The skill file holds only what does not vary by check:** the subject and how to slice it, the ground-truth artifact to build once, the status scale, whether fixes touch code, and any opt-in *deliverables* (a generated config, a rendered report - things that produce an artifact rather than findings-matrix rows). Measure your own domain rather than sizing it against another's: the headers in this family differ several-fold, and any figure quoted here would be a snapshot that rots on the next edit - four of the figures this sentence used to carry had gone stale before anyone noticed, and the ratio written to replace them went stale on the next check that landed, because the check's domain owned the smallest header in the family and one added sentence moved the whole spread. Check count does not predict the size either. What actually drives it is (a) how many of the domain's checks are `global`-locality *and* need a stated, non-generic reason why no per-partition agent can decide them - a domain where every check shares one uniform reason (`deps`) states it once cheaply, while one with several case-by-case exceptions (`ci`, `eval`) must justify each - and (b) whether the domain carries a cross-cutting classification or fix pattern that applies across many checks at once and has no single check to record it in. `prompt`'s tier split (which checks apply to a formal SOP versus a general prompt) is exactly the second case: it applies across the domain's checks and has no single check to record it, so it lands in the header despite the domain carrying only one `global` check.
