# Test Audit (coverage, TDD adherence, test quality)

A domain specialization of **[audit-core](../audit-core/SKILL.md)** - read that first; it owns the loop (scope → parallel evidence → findings matrix → plan → subagent-driven fixes → review → PR), the `## Running a route` contract that turns this skill's records into commands, and the cross-cutting rules. The checks are records in [`checks/`](checks/) beside this file; load the ones your slice needs, not the directory. This skill supplies the testing lens for **deterministic, code-level tests**.

**Core principle:** a test suite's value is not its coverage percentage - it is whether it *fails when the code breaks*. A high number produced by tests that assert nothing, mock the thing under test, or never exercise the hard branches is a false safety net that is worse than an honest low number. The audit measures both reach (coverage) and strength (does a test actually catch a regression), and treats a confident-but-weak suite as a finding.

**Announce:** "I'm using the test-audit skill (on the audit-core engine) to audit the test suite."

**Also use** when tests are flaky, slow, or order-dependent and eroding trust in CI.

**Not for:** LLM/agent behavioral evaluation, prompt auditing, or smoke tests (use `eval-audit`); nor writing a project's first test suite from scratch (that's authoring - though the audit's gap list seeds it).

**Subject:** the test suite and the production code it is meant to protect. Establish first:

- **The test layout + runner** - where tests live, the framework (from the project inventory's test-runner field, e.g. `pytest` / `unittest` for a Python partition, `vitest` / `jest` for a TypeScript one, or the detected language's equivalent), markers, and how the suite is invoked (including what CI runs vs. what is excluded by default, e.g. integration markers).
- **What coverage is claimed / required** - any coverage floor the contributor guide or CI enforces, and the "new code ships with tests / don't lower coverage" rule if the project states one.
- **The deterministic core vs. I/O edges** - the pure logic (parsing, scoring, transforms, id-mapping, verdict application) that must be tested, versus S3/network/LLM edges that may be mocked or left to integration tests.

Slice the parallel evidence pass by package/module - one read-only agent per slice - so each maps its production units, the tests that cover them, and the coverage/quality of those tests. Two checks are **global**, each for its own reason. `test/new-code-coverage` measures coverage on the diff, a property of the change set that no per-package agent can compute. `test/coverage-floor-declaration` asks whether the project decided a coverage floor, which is one decision the project took once - a per-package agent would report the same project-level answer from every slice, or, worse, report the absence of a floor once per package as though each were its own finding.

**Detect** what the project has from the project inventory, which records the test runner and the audit-relevant tools each partition already runs: coverage, diff-coverage, flakiness/order tools, timeouts, property-based testing, and mutation testing - e.g., for a Python partition, `pytest-cov` / `coverage.py`, `diff-cover`, `pytest-randomly` / `pytest-rerunfailures`, `pytest-timeout`, `hypothesis`, and `mutmut` / `cosmic-ray` respectively; for a TypeScript partition, the partition's own runner's coverage - and `c8` only where that runner's tests run in the process `c8` wrapped, which Vitest's do not, so around a Vitest command it reports a high number over the handful of files node loaded directly and none of the source tree - `diff-cover` over an LCov report, `vitest`'s `sequence.shuffle` or `jest --randomize`, `testTimeout` / `slowTestThreshold`, `fast-check`, and `@stryker-mutator/core`; or another language's equivalents. Prefer a tool the project already runs; fall back otherwise.

Status per row: **ok / warn / violation** (coverage: meets-floor / below-floor / untested). Suppressions (an intentionally untested throwaway script, an I/O edge deferred to integration tests) must be explicit and recorded with a reason - never silently dropped.

Fixes here **add or change test code**, so they are **not** docs-only: the domain gate is "the (possibly expanded) suite passes **and** coverage does not drop" - run the normal install + lint/typecheck/test CI with coverage, plus the code-review gate. **One check closes outside that gate**, and reading the rule above as universal is how a fix agent closes it wrongly: `test/coverage-floor-declaration`'s fix is a `fail_under` line, a runner threshold or a CI step, which adds no test code at all. That gate cannot answer it either - a project with no floor whatsoever passes "the suite passes and coverage does not drop" every time - and neither can re-running the check's own detection, which finds the new number and goes green without being able to tell a floor that was decided from one lowered until the tree already met it. **The gate there is a read of the diff**: was the number written to state a bar the project intends to meet, does a low one carry the justification the clause asks for, and was the floor added rather than moved down to fit. **If production code is untestable** (hidden side effects, no seam), a small refactor to introduce a seam is in scope - but it must be behavior-preserving and reviewed. **Highest-leverage fix:** wire a coverage floor + **diff-coverage gate** into CI (new code must be covered) so the suite can't silently weaken - this enforces the "don't lower coverage" rule mechanically. Docs-only output: the findings report and any update to the contributor guide's testing conventions.

**Behavioral/eval cross-check** - hand off LLM/agent behavioral quality, prompt auditing, and smoke tests to `eval-audit`; note the handoff.
