# Eval Audit (evals, prompts, smoke tests)

A domain specialization of **[audit-core](../audit-core/SKILL.md)** - read that first; it owns the loop, the `## Running a route` contract that turns this skill's records into commands, and the cross-cutting rules. The checks are records in [`checks/`](checks/) beside this file; load the ones your slice needs, not the directory. This skill supplies the behavioral, model-level quality lens. Deterministic, code-level testing (unit coverage, assertion strength, flakiness) belongs to **`test-audit`**, and static prompt/SOP *authoring* quality (spec-conformance, constraint hygiene, clarity, cognitive load) belongs to **`prompt-audit`** - both siblings in the audit-skills program; this skill cross-links them rather than covering them.

**Core principle:** an eval is a measuring instrument, and an instrument you haven't calibrated can read anything. The audit asks two things: *are the behaviors that actually matter being measured at all?* (an unevaluated capability is an unmonitored one) and *do the numbers mean what everyone assumes they mean?* (a metric that doesn't track quality, a judge that rubber-stamps, a contaminated dataset, an unreproducible run, a single run reported as though it were a measurement, or a merged artifact that lost or double-counted a unit and looks complete either way, produces confident nonsense). A green leaderboard built on a broken instrument is worse than no leaderboard, because decisions get made on it.

**Announce:** "I'm using the eval-audit skill (on the audit-core engine) to audit the evals, prompts, and smoke tests."

**Not for:** deterministic unit-test coverage and quality (use `test-audit`); a one-off "how good is this output" spot check (just run it). Prompt-*injection as an application-security* concern overlaps `security-audit`; here the lens is behavioral robustness, and this skill sends the application-security half there rather than covering it.

**Subject:** the project's evaluation assets and the behaviors they are meant to measure. Establish first:

- **What behaviors matter** - the agent/model capabilities, quality dimensions, and failure modes the product depends on (accuracy, grounding/citation, refusal handling, format adherence, latency/cost). This is the yardstick for "is it evaluated."
- **The eval assets** - datasets / ground truth, metrics and scorers, any LLM-as-judge, the runner, leaderboards / eval history, and the smoke-test workflow. Where the runner fans work out across agents or shards and merges what comes back, the merge site is an asset too: it is where `eval/merge-coverage-assertion` reads. Detect the framework (a bespoke `eval/` package, or `promptfoo` / `deepeval` / `ragas` / `langsmith` / OpenAI Evals).
- **The prompts / SOPs** - where system prompts, tool descriptions, and agent SOPs live, and whether the project has a prompt-change discipline (versioning, changelog, "explain why a prompt changed").

**The partition is one eval suite**, so slice the parallel evidence pass **by capability or by asset type** - one read-only agent per agent/capability, or one per concern (datasets, metrics, prompts, smoke test) - whichever partitions cleanly, and most checks are local to the suite an agent slices. A check is `global` here when its answer is one fact about the repository rather than one about a suite, which no per-suite agent can see in isolation: `eval/coverage`, because "is every behavior-that-matters covered" is answered against the whole capability set; `eval/smoke-test-gate` and `eval/regression-tracking`, because there is one gate and one leaderboard; `eval/run-variance`, because whether reported numbers carry the spread of the runs behind them is a property of the reported results, not of any one case in them; and `eval/merge-coverage-assertion`, because a per-suite agent that finds no fan-out in its own slice has established nothing about the repository, and the `not-applicable` this check offers is a claim about the whole surface. Two of the three opt-ins are global for the same repo-level reason - `eval/adversarial` and `eval/cost-latency` - while `eval/judge-calibration` is local; all three are loaded like any other.

**Detect** the project's eval stack (a `eval/` package with its own runner/report, or `promptfoo` / `deepeval` / `ragas` / `langsmith` / OpenAI Evals) and how evals are invoked, plus where prompts live and any prompt-analysis skill the project ships. Prefer the project's own harness; don't impose a framework it doesn't use. Record the eval config / dataset / prompt `file:line` (or the metric value and how it was produced) as the evidence pointer for every row.

Status per row: **ok / warn / violation** (coverage: measured / partial / unmeasured). Suppressions (a behavior intentionally out of eval scope, a known non-deterministic metric reported with a stated confidence interval) must be explicit and recorded with a reason - never silently dropped. Some issues are *reminders about interpretation*, not code fixes (e.g. "don't penalize a model for a sub-agent refusal") - record those as policy in the report.

Fixes here range from **eval/prompt code** (a new dataset, a fixed scorer, a prompt edit) to **interpretation policy** (how to read a number). The domain gate depends on the fix: code-touching fixes run the normal lint/typecheck/test CI plus a smoke/eval run where feasible; prompt edits should be re-evaluated behaviorally before trust. State which applies. **Highest-leverage fix:** wire a cheap, reproducible eval/smoke gate into CI. Docs-only outputs: the findings report, an eval methodology note, and leaderboard/eval-history updates.
