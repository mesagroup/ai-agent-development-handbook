# Prompt Audit (system prompts & Agent SOPs)

A domain specialization of **[audit-core](../audit-core/SKILL.md)** - read that first; it owns the loop (scope → parallel evidence → findings matrix → plan → subagent-driven fixes → review → PR), the `## Running a route` contract that turns this skill's records into commands, and the cross-cutting rules. The checks are records in [`checks/`](checks/) beside this file; load the ones your slice needs, not the directory. This skill supplies the **static authoring-quality** lens for prompts and SOPs.

The split from its closest sibling is deliberate and mirrors `test-audit` vs `eval-audit`: **`eval-audit`** owns *behavioral, model-level* prompt quality (does the prompt hold under adversarial input, has it drifted from the current tools/code, is the behavior actually measured); **this skill** owns *how well the prompt is written on the page* (is it well-formed, clear, consistent, and not overloaded). This skill hands the behavioural half there rather than overlapping it: a prompt can be immaculately structured and still behave badly, and vice versa, so a real prompt change usually wants both passes.

**Core principle:** a prompt is source code for a model, and the same things that make source unmaintainable make a prompt unreliable. A contradiction the model silently resolves the wrong way, a negative rule with no reason it quietly reintroduces, a section so dense it drops half its constraints - these are defects you can see *on the page*, before a single token is generated, and they are cheaper to catch there. A well-written prompt is not decoration: it is the difference between a directive the model follows every run and one it follows when the context happens to be short enough.

**Announce:** "I'm using the prompt-audit skill (on the audit-core engine) to audit the prompts and SOPs."

**Not for:** *behavioral* prompt quality - whether the prompt is evaluated, drifts from the tools, or resists injection (use `eval-audit`); prompt-injection as an *application-security* exposure (use `security-audit`); a one-off "make this prompt read better" edit with no audit trail (just edit it). This skill owns the static, on-the-page authoring quality; it cross-links the others rather than covering them.

**Subject:** the project's prompt and SOP assets - **Agent SOPs** (`.sop.md` files, the structured, reusable prompts specified by the [`agent-sop`](https://github.com/strands-agents/agent-sop) format) and **system prompts & tool descriptions** (the prompt `.md` files and Jinja2 `.j2` prompt templates that configure agents, sub-agents, and tools; for `.j2` templates, render every variant first and audit each rendered version, since a template can read fine and render broken). Detect where these live (in this repo: `.sop.md` files anywhere, plus the `**/prompts/` directories). For each artifact, **classify it first** - a formal SOP or a general prompt - because that decides which checks apply: every artifact is judged on the checks in [`checks/`](checks/) tagged Tier A, the universal well-specified-prompt principles; a formal SOP (`.sop.md`) is *additionally* judged on the Tier B checks, the structural spec. A general prompt is judged on Tier A **only** and is **never** penalized for lacking SOP sections, parameters, or the RFC 2119 vocabulary - a system prompt has no reason to carry an "Overview" heading. Also establish which prompts are **load-bearing** (drive a production agent or a sub-agent) versus throwaway (a one-off eval prompt), so severity can weight the former.

Slice the parallel evidence pass **one read-only agent per prompt/SOP file** (or per small group of related prompts) - each file audits cleanly in isolation, and cross-file concerns (a shared rule that drifted between two prompts) surface when the findings are consolidated; that is also why **the partition is one prompt or SOP file** and every check above is `local` - only the opt-in `prompt/cross-prompt-consistency` needs the whole library at once and is `global`.

**Detect** whether the project (or the environment) ships the **`prompt-analyzer`** skill; if present, its quantitative scan (`analyze_prompt.py`) is the accelerant `prompt/cognitive-load` runs on, not a gate - if it is not available, that check computes the same signal inline. Do not impose the tool as a dependency. Record the `file:line` (and the metric value where relevant) as the evidence pointer for every row; prefer reading the actual prompt file over any summary of it.

Status per row: **ok / warn / violation**. Suppressions must be explicit and recorded with a reason (e.g. "this safety rule is intentionally repeated at three points of use" - legitimate reinforcement, not drift; or "this prompt is a throwaway eval fixture, spec-conformance not required"). Never silently drop a row. Some findings are *interpretation notes*, not edits (e.g. "this redundancy is justified") - record those as policy in the report so they are not re-litigated next audit.

Prompt/SOP edits are **docs-level** changes, so they stay off the heavy code gates - **but a prompt is behavioral source**, so an edit that looks like a pure cleanup can change what the model does. State this up front and, for any load-bearing prompt, recommend a **behavioral re-check via `handbook-audit:eval-audit`** (or the project's smoke/eval run), qualified so the audited project's own same-named skill cannot stand in for the lens before the edit is trusted, and confirm at review time that the re-check happened or is explicitly flagged as still owed. Follow the repo conventions: keep prompt changes in **their own commit**, and the commit message must explain **why** the prompt changed, not only what. Docs-only outputs: the findings report and any prompt-quality policy notes.

**Opt-in deliverables** (produce an artifact, not findings-matrix rows - ask the user or enable via argument): **sub-agent decomposition analysis** - for an intrinsically overloaded prompt, apply the prompt-analyzer decomposition framework to identify natural split boundaries, propose sub-agents with their handoff contracts, and produce the decomposition diagram; recommend it when a single prompt exceeds ~10K tokens or a section can't be split without splitting the agent. **Reasoning-token strategy** - classify each step by how much it benefits from extended thinking and recommend where reasoning tokens earn their cost; useful when tuning a reasoning-capable model.

**See also: [eval-audit](../eval-audit/SKILL.md)** - behavioral, model-level prompt quality (injection-resistance, drift-vs-tools, is-it-evaluated). Owns the "does it behave" half; this skill owns "is it well written." A load-bearing prompt edit wants both. **[security-audit](../security-audit/SKILL.md)** - prompt-injection as an application-security exposure; this skill only notes structural weaknesses and links. The `/sop` skill (SOP specification) and the `/prompt-analyzer` skill (quantitative scan + qualitative framework) are the source materials this lens is built from.
