# Cycles

Import cycles between modules or packages (they defeat isolation and make the graph un-orderable).

## Severity

**Critical** - an import cycle across package boundaries. These break the architecture the team committed to.

**Important** - a cycle within a package.

## Tooling fallback

**Python** - `import-linter`'s cycle contract, `pydeps --show-cycles`, or `grimp`'s cycle detection on the built graph. `pydeps` doesn't execute the target - it reads import opcodes from compiled bytecode - but it only sees modules the import machinery can find, so an uninstalled dependency drops out of the graph and a cycle running through it goes silently unreported rather than erroring. **Run `pydeps --show-cycles --show-dot`: `--show-cycles` alone has no textual output channel at all.** It exits 0 with empty stdout and empty stderr whether a cycle is present or absent, because its answer is drawn onto an SVG side-file rather than printed, and those two states are indistinguishable to a caller reading the streams. `--show-dot` prints the underlying dot source as text instead, so a genuine cycle shows up as both directed edges of the pair (`a -> b` and `b -> a`) on stdout - measured in a scratch copy carrying a real two-module cycle, not as an artifact of the python lens smoke run, whose own results show only the bare `--show-cycles` form: exit 0 and zero bytes on both streams over that same cycle.

**TypeScript** - `madge --circular --ts-config <the partition's tsconfig>`, or `dependency-cruiser`'s `no-circular` rule on the built graph. `madge` excludes installed dependencies and brings its own TypeScript, so it needs no install and is the one to reach for first on an unresolved partition - but **only where the partition's `tsconfig` does not `extend` a base that lives in `node_modules`**, since it resolves the `tsconfig` through the TypeScript API like anything else, so a missing `extends` chain costs it `paths` too and it reports no cycles at exit 0 over a graph the aliased imports have dropped out of. **Give `madge` that `tsconfig` explicitly with `--ts-config`, on every partition - and give it the file that carries `paths`, which on a solution-style layout is not `tsconfig.json`.** A Vite or React project commonly ships `tsconfig.json` holding only `{"files": [], "references": [...]}` with the compiler options in `tsconfig.app.json` beside it; madge does not follow `references`, so pointing at `tsconfig.json` there is byte-for-byte the same as passing no flag at all. Measured on one such partition: 45 warnings and 6 cycles with `tsconfig.json` or with no flag, 31 warnings and 7 cycles with `tsconfig.app.json`. The instruction is followed, and the cycle it exists to expose stays hidden. Its `tsConfig` option is documented with a default of `null` and it discovers no config on its own - only a `.madgerc` or a `madge` key in the partition's `package.json` supplies one otherwise - so an invocation without the flag resolves no `paths` at all, and reports no cycles at exit 0 over a graph every aliased import has dropped out of, on a partition whose `tsconfig` extends nothing at all. The `extends` condition above is what remains once the flag is passed, not an alternative to passing it. Read the partition's `tsconfig` for that `extends` before trusting either tool: where it is there, neither has a complete first-party graph without the tree, and the check is `no-evidence (not-permitted)` rather than a clean cycle-free verdict. The `extends` claim about `madge` is reasoned from documented behaviour - TypeScript's `extends` resolution - and is not reproduced on a fixture here. The `--ts-config` claim no longer rests on reasoning: run against a real npm target whose `tsconfig` extends nothing, `madge --circular` without the flag reported `✔ No circular dependency found!` at exit 0 where the same command with it found two, and the dependency map went from 1090 edges to 122, reordering the hubs rather than thinning them - so the flag is what stands between this tool and a false clean, on a partition the `extends` condition never applied to. `dependency-cruiser` needs the target's own dependencies present for its own reason: where the `tsconfig` extends a base config living in `node_modules`, an uninstalled tree loses that `extends` chain and `paths` falls back to nothing, so a first-party aliased import stops resolving and a cycle running through it goes undetected rather than merely unreported. Feed it the compiler through a one-shot runner instead of relying on it being present, and **pin it below the major this tool rejects** (`npx --package 'typescript@^5' --package dependency-cruiser -- depcruise`, `pnpm --package=typescript@^5 --package=dependency-cruiser dlx depcruise` - **note the flags precede `dlx` on pnpm**, since `pnpm dlx --package=...` reads the flag as a package spec and fails with `ERR_PNPM_SPEC_NOT_SUPPORTED_BY_ANY_RESOLVER` - or `yarn dlx -p typescript@^5 -p dependency-cruiser depcruise`) - skip that and it reports zero modules cruised at exit 0, which reads as a clean cycle-free project rather than as nothing having been analysed. All three name the packages rather than leaning on the command name, and none of the three may be left to the reader to reconstruct: `depcruise` is the command this tool documents but not the name of the package that provides it, and npm carries an unrelated package under that name - a dependency-confusion placeholder whose bin prints a misconfiguration notice and exits 0 - so a bare `dlx depcruise` also comes back with nothing at exit 0, by a different route than a dropped co-package, and neither route looks like a tool that failed. Run against a real npm target at dependency-cruiser 18.2.0, three further routes each returned an unusable answer, and the version pin above is the first of them: an unpinned `typescript` co-package resolves to 7.x, outside the `>=2.0.0 <7.0.0` this tool declares, so `depcruise --info` reports no TypeScript transpiler and enables only `.js .cjs .mjs .jsx` - whereupon a **directory** argument cruises `totalCruised: 0` at exit 0, and the same invocation with the pin cruises the tree. Second, a target with no `.dependency-cruiser` config - the ordinary case, not the exotic one - **exits 1** with `Can't open a config file`, so this tool answers only once given `--config` with an audit-owned config or `--no-config`, and that choice is not free. Third, `--no-config` is what depcruise's own error message suggests and it **discards `--ts-config` along with the rules**: the tree that resolved its first-party graph under an audit-owned config came back with 281 unresolvable first-party specifiers and an empty cycle set under `--no-config`, at exit 0. So prefer an audit-owned config setting `options.tsConfig` and `enhancedResolveOptions.extensions`, and read [the smoke run](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/audit/typescript-lens-smoke-run.md) for the observed output behind each of the three. On pnpm the co-package is less dependable still, and its two failures point opposite ways: on pnpm 9.15.9 the ordering above supplies the compiler and `pnpm dlx --package=` errors outright, while on pnpm 11 `depcruise --info` reported no TypeScript under *either* ordering - so the tool ran and the compiler never arrived, with nothing on stderr to say so. Where the partition is pnpm, install into an audit-owned directory rather than trusting the runner to carry a second package.

**With none of them installed** - the edge set built for layering is all a cycle needs: walk it depth-first and record every back edge, or collapse it into strongly-connected components and report each component of size greater than one. Report the participating modules in cycle order, so the fix has a seam to cut.

## Fix

Break a cycle: extract the shared piece into a new lower module, or convert an import-time dependency into a lazy/local import only when extraction genuinely doesn't fit (note the trade-off).

## Review lens

**Cycle-fix adequacy** - a cycle "fix" doesn't just relocate the cycle.
