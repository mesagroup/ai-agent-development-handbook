# Over-decomposition

Too **fine - over-decomposition** ("ravioli code", the nanoservice anti-pattern): so many trivial single-responsibility units that the dependency graph, not any one component, is the thing you can't hold in your head. The tell is a graph-level shape - a high edge-to-node ratio, many modules carrying one public symbol / a handful of lines, and long call chains threading through pass-through units that only forward (the "poltergeist" / "middle man"). This is distinct from the over-abstraction axis (a *single* abstraction with no second consumer) and from a god-module (too *few* nodes doing too much) - here the fault is the aggregate shape of the whole graph.

## Severity

**Important** - **over-decomposition severe enough that a routine change is shotgun surgery** - one logical edit scatters across many trivial units and the dependency graph is the barrier to understanding.

**Minor** - a handful of over-decomposed pass-through modules that should be merged - real but low-cost, fix when touching the area.

## Tooling fallback

**Python** - from the same edge set, compute graph-level shape, not per-module counts. Flag a high **edge-to-node ratio** (many dependencies relative to the number of modules), the distribution of **public-symbols-per-module** and **LOC-per-module** (a long tail of one-symbol / few-line modules), and **call chains that thread through pass-through units** - modules whose functions only forward to another module (the same one-caller detection `arch/over-abstraction` uses: for each single-function module or one-method wrapper class, count call sites with `grimp` refs or a scoped grep, and **one** is the trigger). Record the ratio / the count of trivial nodes / the offending chain as the evidence. A finding needs a **read** confirming the units are genuinely trivial and merging them raises cohesion (files that change together) - a fine-grained split that maps onto real, independently-changing responsibilities is correct design, not a finding.

**TypeScript** - the same graph-level shape from `madge`'s or `dependency-cruiser`'s dependency map: the edge-to-node ratio, the distribution of exports-per-module and LOC-per-module, and the call chains threading through pass-through modules. The same read requirement applies - a fine-grained split that maps onto real, independently-changing responsibilities is correct design, not a finding. `madge` excludes installed dependencies and carries its own TypeScript, so it is the one to reach for first on an unresolved partition - but **only where that partition's `tsconfig` does not `extend` a base that lives in `node_modules`**, since it resolves the `tsconfig` through the TypeScript API like anything else, so the same lost `extends` chain takes `paths` from it and the edge-to-node ratio it returns is computed over a graph the aliased imports dropped out of, at exit 0. **Give `madge` that `tsconfig` explicitly with `--ts-config`, on every partition - and give it the file that carries `paths`, which on a solution-style layout is not `tsconfig.json`.** A Vite or React project commonly ships `tsconfig.json` holding only `{"files": [], "references": [...]}` with the compiler options in `tsconfig.app.json` beside it; madge does not follow `references`, so pointing at `tsconfig.json` there is byte-for-byte the same as passing no flag at all. Measured on one such partition: 45 warnings and 6 cycles with `tsconfig.json` or with no flag, 31 warnings and 7 cycles with `tsconfig.app.json`. The instruction is followed, and the cycle it exists to expose stays hidden. Its `tsConfig` option is documented with a default of `null` and it discovers no config on its own - only a `.madgerc` or a `madge` key in the partition's `package.json` supplies one otherwise - so an invocation without the flag resolves no `paths` at all, and the ratio comes back computed over a graph every aliased import has dropped out of, on a partition whose `tsconfig` extends nothing at all. The `extends` condition above is what remains once the flag is passed, not an alternative to passing it. Read the partition's `tsconfig` for that `extends` before trusting either tool: where it is there, neither has a complete first-party graph without the tree, and the check is `no-evidence (not-permitted)` rather than a graph-shape result. The `extends` claim about `madge` is reasoned from documented behaviour - TypeScript's `extends` resolution - and is not reproduced on a fixture here. The `--ts-config` claim no longer rests on reasoning: run against a real npm target whose `tsconfig` extends nothing, `madge --circular` without the flag reported `✔ No circular dependency found!` at exit 0 where the same command with it found two, and the dependency map went from 1090 edges to 122, reordering the hubs rather than thinning them - so the flag is what stands between this tool and a false clean, on a partition the `extends` condition never applied to. `dependency-cruiser` needs the target's own dependencies present for its own reason: where the `tsconfig` extends a base config living in `node_modules`, an uninstalled tree loses that `extends` chain and `paths` falls back to nothing, so first-party aliased imports stop resolving and the graph-shape metrics this check rests on - the edge-to-node ratio, the pass-through chains - go wrong rather than merely sparse. Feed it the compiler through a one-shot runner instead of relying on it being present, and **pin it below the major this tool rejects** (`npx --package 'typescript@^5' --package dependency-cruiser -- depcruise`, `pnpm --package=typescript@^5 --package=dependency-cruiser dlx depcruise` - **note the flags precede `dlx` on pnpm**, since `pnpm dlx --package=...` reads the flag as a package spec and fails with `ERR_PNPM_SPEC_NOT_SUPPORTED_BY_ANY_RESOLVER` - or `yarn dlx -p typescript@^5 -p dependency-cruiser depcruise`) - skip that and it reports zero modules cruised at exit 0, an empty graph that looks like a clean, undecomposed project rather than an unanalysed one. All three name the packages rather than leaning on the command name, and none of the three may be left to the reader to reconstruct: `depcruise` is the command this tool documents but not the name of the package that provides it, and npm carries an unrelated package under that name - a dependency-confusion placeholder whose bin prints a misconfiguration notice and exits 0 - so a bare `dlx depcruise` also comes back with nothing at exit 0, by a different route than a dropped co-package, and neither route looks like a tool that failed. Run against a real npm target at dependency-cruiser 18.2.0, three further routes each returned an unusable answer, and the version pin above is the first of them: an unpinned `typescript` co-package resolves to 7.x, outside the `>=2.0.0 <7.0.0` this tool declares, so `depcruise --info` reports no TypeScript transpiler and enables only `.js .cjs .mjs .jsx` - whereupon a **directory** argument cruises `totalCruised: 0` at exit 0, and the same invocation with the pin cruises the tree. Second, a target with no `.dependency-cruiser` config - the ordinary case, not the exotic one - **exits 1** with `Can't open a config file`, so this tool answers only once given `--config` with an audit-owned config or `--no-config`, and that choice is not free. Third, `--no-config` is what depcruise's own error message suggests and it **discards `--ts-config` along with the rules**: the tree that resolved its first-party graph under an audit-owned config came back with 281 unresolvable first-party specifiers and an empty cycle set under `--no-config`, at exit 0. So prefer an audit-owned config setting `options.tsConfig` and `enhancedResolveOptions.extensions`, and read [the smoke run](https://github.com/mesagroup/ai-agent-development-handbook/blob/main/docs/audit/typescript-lens-smoke-run.md) for the observed output behind each of the three. On pnpm the co-package is less dependable still, and its two failures point opposite ways: on pnpm 9.15.9 the ordering above supplies the compiler and `pnpm dlx --package=` errors outright, while on pnpm 11 `depcruise --info` reported no TypeScript under *either* ordering - so the tool ran and the compiler never arrived, with nothing on stderr to say so. Where the partition is pnpm, install into an audit-owned directory rather than trusting the runner to carry a second package.

## Fix

Merge over-decomposed units (the inverse): collapse trivial pass-through modules and poltergeists back into the unit they serve, so a responsibility that always changes together lives together and the graph loses the hops that carried no work. Merge along the same cohesion seam a split would follow - combine only units that change together; do not fuse genuinely independent responsibilities just to shrink the node count.

## Review lens

**Merge-fix adequacy** - a merge fix combined only units that actually change together (it didn't fuse independent responsibilities into a new god-module just to shrink the node count).
