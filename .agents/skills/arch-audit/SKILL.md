# Architecture Audit (structure, layering, coupling)

A domain specialization of **[audit-core](../audit-core/SKILL.md)** - read that first; it owns the loop, the `## Running a route` contract that turns this skill's records into commands, and the cross-cutting rules. The checks are records in [`checks/`](checks/) beside this file; load the ones your slice needs, not the directory. This skill supplies the structural lens.

**Core principle:** structure is judged against an architecture the project has actually declared or confirmed, never against a universal ideal - so establishing that spec comes before measuring anything against it, and a rule the team never agreed to is not a violation. What the fixes then change is the shape and never the behavior - for the checks that judge the code, which is most of them. The two declaration checks, `arch/runtime-declaration` and `arch/import-rule-declaration`, change a document instead: they ask whether the project wrote something down, so their fix adds a line to the binding-rules file or a layering contract and touches no code at all.

**One pairing:** `arch/coupling` and `arch/over-decomposition` are the same granularity question in opposite directions - too coarse and too fine - so neither alone answers whether the granularity is right.

**Announce:** "I'm using the arch-audit skill (on the audit-core engine) to audit the project structure."

**Not for:** a single new module's design review (just review it), or a pure performance/security question (those are other lenses).

**Subject:** the package tree (the importable source under `src/`, the top-level package, or wherever the project keeps its code) and its import graph - one graph per graph scope where the inventory records several, as the build paragraph below and `audit-core`'s graph scope prescribe - plus, for the two declaration checks, the binding-rules file and the project's layering-contract and manifest files, which are documents rather than code and are read without the graph.

**Establish the declared architecture first**, because it is the spec every layering finding is judged against. Read the contributor guide (CLAUDE.md / AGENTS.md / CONTRIBUTING) for a stated tier/layer structure and dependency rules ("A may import B, never the reverse; no cycles"). If it states them, they are the rubric. If no rules are documented, **infer** the intended layers from the directory structure and confirm the inferred rules with the user before flagging violations - don't invent an architecture the team never agreed to. **Inferring gets you a rubric; it does not make the absence a non-event.** That the project never wrote the rule down is itself reported, by `arch/import-rule-declaration`, so the two are one job each rather than two policies for one situation: this step supplies what `arch/layering` judges against, and that check reports what the step had to supply. An inferred rubric also marks every layering finding built on it as judged against tiers the audit proposed rather than tiers the project declared, which is worth saying in the report.

**Build the graph once per graph scope, first.** Produce the ground-truth artifact every agent that judges the code consumes - the declaration checks consume none of it, which is why neither is a reason to build it and neither waits on it - the import edge set plus per-module symbol/LOC counts - so agents read it rather than each re-parsing the tree and rebuilding a (possibly inconsistent) graph. The scope is the inventory's, never this skill's to choose: one edge set per deployable the inventory records, with the modules of every shared package a deployable reaches, directly or through another shared package, inside its set together with every edge among them, edges back into the deployable included, and one more set per shared scope the inventory lists - the shared packages connected by import edges in either direction, a lone shared package a scope of its own, every shared package in exactly one, grouped by the inventory and never regrouped here - holding the scope's modules, the edges among them and every inbound edge from the deployables that import them, so a hub's fan-in and `Ca` inside the package are counted once over the whole importer set rather than read off a set with no inbound edges; and a finding attributed to exactly one of those sets: a cycle, hub or ratio whose every module is a shared module - inside one package or across two of the scope - is a row under the shared scope and is suppressed from every importer's rows, while a deployable's rows carry only findings that involve at least one of its own modules, edges into the package included, so every finding has an owner and none has two; a partition the inventory left undetermined gets a set of its own with that reason attached to every number computed from it; a single-partition target is one set. Never build one edge set across deployables that do not import each other, because every ratio read off it describes modules that never meet; and never build one across deployables that do, either: an edge from one deployable into another is the importer's finding, a crossing of the deploy boundary reported in the importer's row, so two deployables importing each other are two such rows and not one graph with a cycle in it.

**Fan out by each check's `locality`.** `local`: `arch/complexity`, `arch/dead-code`, `arch/layering`, `arch/size` - one read-only agent per top-level package/tier, each mapping its slice's outgoing imports and internal shape. `global`: `arch/complexity-gate`, `arch/coupling`, `arch/cycles`, `arch/hidden-coupling`, `arch/import-rule-declaration`, `arch/over-abstraction`, `arch/over-decomposition`, `arch/runtime-declaration`, and the opt-in `arch/martin-metrics` - one agent per check, computing each whole-graph property once per graph scope from that scope's edge set and naming the scope, by the name the inventory lists it under, and its module count in every whole-graph row's evidence, because a per-tier agent sees only its slice's edges and *cannot* compute a whole-graph property - a cycle, a ratio over the graph, an edge that bypasses the import graph - and a ratio over two deployables that never import each other is not a property of anything; plus the repo-wide facts that must be reported once rather than per tier - `arch/complexity-gate`'s configured threshold, `arch/runtime-declaration`'s comparison of the runtimes the whole tree carries against the ones the binding-rules file declares, and `arch/import-rule-declaration`'s single question about whether the tier-import rule was written down at all, which no single tier's slice can answer because none of those is a tier's to see. The last of the three is `global` for a reason worth stating rather than inferring from the list: it asks about one project-level declaration, so a per-tier agent would either repeat the same answer from every slice or report the absence once per tier as though each tier were its own finding. Do **not** fan a cheap local check out to its own agent - that over-fans the work and duplicates the graph build.

Status per row: **ok / warn / violation**. The parenthetical variant - **conforms / borderline / violates** - reads a row against a documented rule, so it belongs to the checks that judge the code and not to the two that ask whether something was declared: `arch/runtime-declaration` and `arch/import-rule-declaration` report on the ordinary scale, and scoring the second of those as *conforms* against a rule the project never wrote is the verdict it exists to prevent. Suppressions - an intentionally allowed edge, a framework hook a dead-code tool can't see - must be explicit and recorded with a reason, never silently dropped.

**Most fixes here touch code**, so the domain gate is "imports resolve, the type checker passes, **and** the test suite passes" - run the normal install + lint/typecheck/test CI, and the code-review gate. Take the actual commands from the inventory's package manager and test runner rather than assuming one ecosystem's. Every fix that changes code is a **behavior-preserving refactor**: the moved, split, merged or deleted code does the same thing afterwards, and a review lens that says so applies to every such check whether or not the check restates it. **Three checks close outside that gate**, and reading the rule above as universal is how a fix agent closes them wrongly: `arch/complexity-gate`'s fix is a threshold in the project's config plus a required CI job, `arch/runtime-declaration`'s is a line added to the binding-rules file, and `arch/import-rule-declaration`'s is a tier-import rule written into that file or into a layering-contract config - the last two touch no code at all. **The gate is not the same for all three.** For the first two it is re-running the check's own detection and reading the result. For `arch/import-rule-declaration` that is not enough, because two wrong closes pass it: a rule written permissively enough to forbid nothing, and a tier list collapsed until there is nothing to constrain. Both leave detection green and declare no constraint, so the gate there is a read of the change - does the written rule forbid an edge the tree could contain, and are its tiers the tiers the project has. Each of the three has a wrong close its own record names, and each is cheaper than the right one: lowering the threshold, removing the runtime from the tree, and writing a rule that permits everything. The highest-leverage fix in this domain is a layering contract (`import-linter` / `tach`) wired into CI so the violation can't silently recur. Docs-only output: the findings report and any architecture-diagram update.

**Opt-in deliverables** (ask the user, or take from an argument; default off): a layering-contract bootstrap that encodes the confirmed rules as an `import-linter` / `tach` config (or the detected language's equivalent layering-contract tool) - the same artifact that closes `arch/import-rule-declaration` outright where the deliverable is granted; where it is not, that finding still closes on the written rule. Default off governs whether the audit *produces* the config, never whether the finding needs one, and a full complexity/coupling metric report per graph scope with a dependency-graph render. The opt-in *check* - package stability metrics - is `arch/martin-metrics`, loaded like any other.
