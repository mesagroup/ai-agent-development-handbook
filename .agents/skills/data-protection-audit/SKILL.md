# Data Protection Audit (privacy posture)

A domain specialization of **[audit-core](../audit-core/SKILL.md)** - read that first; it owns the loop (scope → parallel evidence → findings matrix → plan → subagent-driven fixes → review → PR) and the cross-cutting rules. The checks are records in [`checks/`](checks/) beside this file; load the ones your slice needs, not the directory. This skill supplies the **data-protection** lens: the personal-data surface, the two artifacts that are supposed to describe it, and what the code does at each edge of it.

**Core principle:** an audit here produces two kinds of answer, and mixing them is the failure this domain is most prone to. One kind is what the repository shows - a region key, a lifecycle rule, a provider reachable from an import. The other is what no repository can show - whether an agreement was signed, whether a provider honours the retention window it publishes, whether a fixture's source was a consenting person. Name every item of the second kind as unverifiable from here, with what would settle it and who holds that evidence. A report that lists an unsigned agreement as passing has not audited it; it has failed to look, and said so in the vocabulary of success.

**Announce:** "I'm using the data-protection-audit skill (on the audit-core engine) to audit the project's data-protection posture."

**Not for:** first-party call-site leaks of secrets or personal data into logs and error messages (`security/sensitive-data` owns those, and this skill cross-links it rather than restating its rows); third-party package CVEs (`deps-audit`); pipeline credentials and token permissions (`ci-audit`); and legal judgment on whether an agreement or a transfer route suffices, which is out of scope entirely - this skill reports what is recorded and what is missing, and whoever owns compliance decides whether it is enough.

**Subject:** the project's **personal-data surface**, established before any check runs, because every check is a question asked of one part of it:

- **Where personal data enters** - uploads, form fields, integrations pulling from a customer's system, and whatever a user types at an agent.
- **Where it rests** - the primary store, the object store, the vector index, caches, logs, eval datasets, run artifacts, backups. The ones that get missed are the ones that are an implementation detail of something else, so enumerate from configuration rather than from the store a service is named after.
- **Every outbound edge that leaves the trust boundary**, and what crosses each one. An agentic product crosses on every model call, so an outbound transfer here is routine traffic rather than an exception to look for.

Plus the two artifacts that are supposed to describe that surface - the **data-flow map** and the **processor register**. They are subject and evidence at once, which is why their absence is a finding of this domain rather than a gap in it.

**Applicability - resolved in `audit-core` step 0, not in a record.** Whether the target processes personal data at all is asked there, alongside mode, grants and opt-ins, and for the same reason those are: a dispatched agent has nobody to ask. Answered **no**, the domain is out of scope for that run, and the report says so naming the operator's declaration as the reason - the way the front door reports a domain the user named that has no checks directory. Do **not** report `not-applicable` on every row instead: that status means the check has no lens in this partition's languages, and a second meaning on it would make a polyglot gap and an operator's scoping decision indistinguishable in the one column a reader uses to tell measured from unmeasured. Nor is the declaration a pass - it is an assertion about the target made from outside it, which is exactly the class of claim the core principle above says to report separately.

**Where nobody can be asked** - a sweep's dispatched domain agent, a non-interactive run - the lens runs, and **the absence of a documented personal-data surface is itself the finding**. That is `audit/SKILL.md`'s no-inferred-rubric rule applied to this domain, and the constraint it puts on the checks is the load-bearing half: **no check infers a personal-data surface from field names or file paths and then flags the code against the surface it invented.** "You have not written this down" is a diagnosis; "you violate the standard I made up for you" is not one, and consolidation cannot soften it afterwards, because the domain owns severity and an invented standard therefore reaches the roll-up as a confirmed finding.

**Slicing.** Each `global` record gets its own agent over the whole subject, because the finding it produces is a statement about the repository rather than about a partition: a register is one document, a store list is a union, a deletion path is one walk. `data-protection/residency-pinning` and `data-protection/boundary-minimization` are `local` and ride the per-partition agent, because configuration and the outbound call path both live in a partition, and a monorepo where one service pins its region while another defaults is the finding rather than an average. **Build the outbound-provider surface once**, as `audit-core` step 1's shared ground-truth artifact: `data-protection/provider-surface` reconciles it against the register and `data-protection/data-flow-map` checks the map's outbound edges against it, so two agents deriving it separately would be free to disagree about the one list the rest of the domain rests on.

**Status per row:** ok / warn / violation, plus `audit-core`'s `no-evidence` and `not-applicable`, which are additions to that scale rather than replacements for it. Then this domain's own distinction, which must never collapse into either: a claim the repository cannot settle is reported as **unverifiable from here**, with what would settle it and who holds that evidence. It is not `ok`, and it is not `no-evidence` - `no-evidence` says a tool could not run here, so a grant or an installed tool would answer it, and this says the evidence is not in a repository at all, so neither would.

**Fixes touch code**, which makes this not a docs-only domain: a required region key with startup validation, a redaction step in the shared outbound call path, a TTL or a bucket lifecycle rule, a deletion path that walks the map and a test that walks it with it. The domain gate is the target's own test suite plus whatever the region validation needs to keep passing. Two of the fixes are documents rather than code - the data-flow map and the processor register - and they are the two the audited team has to own rather than the audit, because their content is contract facts and processing purposes that no repository holds; the remediation plan names who. Docs-only outputs: the findings report, and those two artifacts.

**Opt-in deliverable - a sub-processor inventory.** Render it from `data-protection/provider-surface`'s derivation rather than from a fresh pass, so the inventory and the finding cannot disagree about who is called. Per `audit/SKILL.md` a deliverable is out of scope for a sweep however the user answers, because it is an artifact *of* the audited project rather than findings *about* it - offer it as a per-domain follow-up instead.

**Cross-checks** - hand each off by check id, and note the handoff in the report. `security/sensitive-data` for the call-site half of the trail claim: it reads logging and exception-handling call sites, and this domain owns the artifacts that outlive the call. `deps/inventory` for why the package graph is not the provider list - a provider reached over HTTP never enters it, so a clean dependency inventory is no evidence about the register. `eval-audit` for redaction's quality cost as a dimension: it owns whether a behaviour is evaluated at all, so a project with no eval suite is its finding rather than this domain's. `ci/permissions-secrets` for pipeline credentials, which are a question about who can read a secret rather than about where a request lands.
