# Data Protection Audit (privacy posture)

A domain specialization of **[audit-core](../audit-core/SKILL.md)** - read that first; it owns the loop (scope → parallel evidence → findings matrix → plan → subagent-driven fixes → review → PR), the `## Running a route` contract that turns this skill's records into commands, and the cross-cutting rules. The checks are records in [`checks/`](checks/) beside this file; load the ones your slice needs, not the directory. This skill supplies the **data-protection** lens: the personal-data surface, the two artifacts that are supposed to describe it, and what the code does at each edge of it.

**Core principle:** an audit here produces two kinds of answer, and mixing them is the failure this domain is most prone to. One kind is what the repository shows - a region key, a lifecycle rule, a provider reachable from an import. The other is what no repository can show - whether an agreement was signed, whether a provider honours the retention window it publishes, whether a fixture's source was a consenting person. Name every item of the second kind as unverifiable from here, with what would settle it and who holds that evidence. A report that lists an unsigned agreement as passing has not audited it; it has failed to look, and said so in the vocabulary of success.

**Announce:** "I'm using the data-protection-audit skill (on the audit-core engine) to audit the project's data-protection posture."

**Not for:** first-party call-site leaks of secrets or personal data into logs and error messages (`security/sensitive-data` owns those, and this skill cross-links it rather than restating its rows); third-party package CVEs (`deps-audit`); pipeline credentials and token permissions (`ci-audit`); and legal judgment on whether an agreement or a transfer route suffices, which is out of scope entirely - this skill reports what is recorded and what is missing, and whoever owns compliance decides whether it is enough.

**Subject:** the project's **personal-data surface**, established before any check runs, because every check is a question asked of one part of it:

- **Where personal data enters** - uploads, form fields, integrations pulling from a customer's system, and whatever a user types at an agent.
- **Where it rests** - the primary store, the object store, the vector index, caches, logs, eval datasets, run artifacts, backups. The ones that get missed are the ones that are an implementation detail of something else, so enumerate from configuration rather than from the store a service is named after.
- **Every outbound edge that leaves the trust boundary**, and what crosses each one. An agentic product crosses on every model call, so an outbound transfer here is routine traffic rather than an exception to look for.

Plus the two artifacts that are supposed to describe that surface - the **data-flow map** and the **processor register**. They are subject and evidence at once, which is why their absence is a finding of this domain rather than a gap in it.

**Applicability - ask it in `audit-core` step 0, alongside mode, grants and opt-ins, and for the same reason those are asked there: a dispatched agent has nobody to ask.** The question is whether the target processes personal data at all, and it is this skill's to ask rather than the engine's, because it scopes this domain and no other. **Ask the operator directly** on a direct invocation; on a sweep, take the declaration the front door passes you and neither re-ask nor decide for yourself. Answered **no**, the domain is out of scope for that run, and the report says so naming the operator's declaration as the reason - the way the front door reports a domain the user named that has no checks directory. Do **not** report `not-applicable` on every row instead: that status means the check has no lens in this partition's languages, and a second meaning on it would make a polyglot gap and an operator's scoping decision indistinguishable in the one column a reader uses to tell measured from unmeasured. Nor is the declaration a pass - it is an assertion about the target made from outside it, which is exactly the class of claim the core principle above says to report separately.

**Where nobody can be asked** - a sweep's dispatched domain agent, a non-interactive run - the lens runs, and **the absence of a documented personal-data surface is itself the finding**. That is `audit/SKILL.md`'s no-inferred-rubric rule applied to this domain, and the constraint it puts on the checks is the load-bearing half: **no check infers a personal-data surface from field names or file paths and then flags the code against the surface it invented.** "You have not written this down" is a diagnosis; "you violate the standard I made up for you" is not one, and consolidation cannot soften it afterwards, because the domain owns severity and an invented standard therefore reaches the roll-up as a confirmed finding.

**What establishes a surface, and what a severity band may rest on.** Several checks here have a band conditioned on personal data actually crossing an edge or resting in a store, and that condition is the one an audit is most tempted to supply by inference, because the rest of the row is right there in the code. So draw the line identically in every record: **inference may establish *that* a surface exists, which is what selects the band, and may never establish *what it contains*, which is what a finding cites.** What establishes it is the operator's declaration at scope time, an edge or store the data-flow map names, or an artifact that plainly carries personal data - an authentication table, an upload or file-intake endpoint, a store of customer documents, a call site handing user text to a provider. Where none of those establishes it, **the band drops one level and the row reports the payload as undocumented** rather than asserting a transfer: an unregistered provider whose payload nothing documents is a real finding at Important, and the same row called Critical is an invented one. A band resting on an inferred payload is withdrawn rather than downgraded.

**Slicing.** Each `global` record gets its own agent over the whole subject, because the finding it produces is a statement about the repository rather than about a partition: a register is one document, a store list is a union, a deletion path is one walk. `data-protection/residency-pinning` and `data-protection/boundary-minimization` are `local` and ride the per-partition agent, because configuration and the outbound call path both live in a partition, and a monorepo where one service pins its region while another defaults is the finding rather than an average. **Build the derived personal-data surface once**, as `audit-core` step 1's shared ground-truth artifact, and build it here rather than inside whichever record consumes it first, because a definition living in a consumer is one every other consumer either copies or re-derives - which is the disagreement building it once exists to prevent. It has the same three axes as the **Subject** above, since every record in this domain consumes one of them, and **each entry records both the evidence that produced it and the partition it belongs to**, so a consumer can restrict it to one partition without re-deriving it and a reader can judge a row's confidence from how the entry was found:

- **Outbound edges**, from four kinds of evidence, each catching providers the others miss: **SDK imports**, for a provider reached through a client library; **configured base URLs and endpoint settings**, for one reached over plain HTTP with no SDK, and for a gateway or proxy standing in front of one; **MCP server declarations and tool endpoint configuration**, for the ones an agent reaches at run time, which no import mentions; and **credential names** in environment templates, secret manifests and deployment configuration, for a provider whose call path is dynamic or lives in infrastructure rather than in code.
- **Stores**, from the deployment and infrastructure configuration: the database, the object bucket, the managed vector index, caches, queues, the search cluster, the log and trace retention on an observability backend, and the backup schedule. The provider axis does not imply this one - a bucket is not reached through an SDK import or a base URL - so a record needing stores takes them from here rather than from the edge list.
- **Entry points**, from request handlers, upload and file-intake paths, scheduled importers and integrations pulling from a customer's system. Weakest of the three against the code, because the code shows the channel rather than what comes down it.

`data-protection/provider-surface` reconciles the edge axis against the register, `data-protection/data-flow-map` checks the map against all three, and `data-protection/retention-limits`, `data-protection/deletion-path` and `data-protection/stored-artifact-pii` all consume the store axis - the last of them restricted to the stores that are artifacts of the run rather than of the product. A record added later consumes an axis the same way rather than deriving its own, and where it genuinely needs an axis this artifact does not carry, the axis is added here rather than in that record.

**A per-partition agent may read outside its partition; it is the *finding* that stays partition-scoped.** Configuration and shared code are routinely factored upward, so the two `local` records above would otherwise report the best-built repositories as the worst: a region pinned once in a root environment template or a shared configuration package, and one outbound client in a `core` package that every service imports, are exactly what those records' fixes ask for, and a partition agent that reads only its own directory finds neither and fires a Critical at the structure it wanted. So **follow an inherited setting or an outbound call into the package that supplies it before reporting an absence**, and where the thing is inherited, say where it lives instead of reporting it missing. Where one shared file serves many partitions, the finding is about that file rather than one row per partition importing it.

**Status per row:** **ok / warn / violation**, plus `audit-core`'s `no-evidence` and `not-applicable`, which are additions to that scale rather than replacements for it. This domain's own distinction rides on that scale as a **mandatory annotation and never as a fourth value**: a claim the repository cannot settle is `warn (unverifiable-from-here)`, rendered the way `audit-core` renders `no-evidence (not-permitted)`, and naming what would settle it and who holds that evidence. That is the only annotated form, and `violation (unverifiable-from-here)` is deliberately not one: a `violation` here means the repository settled the question, which is the opposite of what the annotation says, so the two can never apply to one row. Severity is a separate column, so an unsettled claim that matters is `warn (unverifiable-from-here)` at Critical rather than a `violation` wearing an annotation that contradicts it. The annotation rather than a new status, because `audit-core` says the scale itself does not grow, and because the sweep counts a coverage triple of checks that ran, `no-evidence` and `not-applicable`: a value outside that triple has no cell, so the consolidation buckets it as `ok` or as `no-evidence` and the distinction dies in the merge instead of in the domain. It is not `no-evidence`, which means the check applies here and no tooling could answer it - because a grant was withheld, because no candidate could be obtained, because one ran and failed, or because the record prescribes nothing for this partition and offers no route a grant would enable. **Every one of those is a statement about the means, and that is the line rather than whether a different environment would fix it** - which was the older wording here and stopped separating the two once `audit-core` gained a reason for a gap nothing about the run or the environment closes. This says something else: the evidence is not in a repository at all, so no grant and no tool reaches it, and the question is who holds it rather than what failed to run.

Which of the two statuses carries the annotation is decided by what the clone can read, not by how serious the claim is. Where the repository holds the record and only its **truth** is out of reach, that is `warn (unverifiable-from-here)`: a register naming a signed agreement is readable, and whether the agreement was executed is not. Where what is missing is itself readable and simply absent, that is a plain `violation` and takes **no annotation at all**, because the clone settled it: a register with no agreement field is a finding in full. Annotating that one would report a question as open when the repository already answered it.

**Fixes touch code**, which makes this not a docs-only domain: a required region key with startup validation, a redaction step in the shared outbound call path, a TTL or a bucket lifecycle rule, a deletion path that walks the map and a test that walks it with it. The domain gate is the target's own test suite, taken from the test runner the project inventory records rather than assumed, **and** the startup path itself: a fix that makes a region key required has to leave every entry point able to start once the key is supplied, so run whatever the inventory records as the target's own startup or smoke check alongside the suite. A required key that nothing supplies in the test environment turns a privacy fix into a broken boot, and the suite alone will not always show it. Two of the fixes are documents rather than code - the data-flow map and the processor register - and they are the two the audited team has to own rather than the audit, because their content is contract facts and processing purposes that no repository holds; the remediation plan names who. Docs-only outputs: the findings report, and those two artifacts.

**Opt-in deliverable - a sub-processor inventory.** Render it from `data-protection/provider-surface`'s derivation rather than from a fresh pass, so the inventory and the finding cannot disagree about who is called. Per `audit/SKILL.md` a deliverable is out of scope for a sweep however the user answers, because it is an artifact *of* the audited project rather than findings *about* it - offer it as a per-domain follow-up instead.

**Cross-checks** - hand each off by check id, and note the handoff in the report. `security/sensitive-data` for the call-site half of the trail claim: it reads logging and exception-handling call sites, and this domain owns the artifacts that outlive the call. `deps/inventory` for why the package graph is not the provider list - a provider reached over HTTP never enters it, so a clean dependency inventory is no evidence about the register. `eval/coverage` for redaction's quality cost as a dimension: it owns whether a behaviour that matters has an eval exercising it at all, so a project with no eval suite is its finding rather than this domain's. `ci/permissions-secrets` for pipeline credentials, which are a question about who can read a secret rather than about where a request lands.
