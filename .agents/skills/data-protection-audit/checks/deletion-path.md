# Deletion path over the derived copies

Whether a deletion path exists, walks the whole store list rather than the primary store alone, and is tested - because an agentic system spreads copies further than any other kind of system and almost none of them look like the database row somebody thinks they deleted.

## Severity

The bands that assert data survived a deletion rest on personal data resting in the store or copy in question, and that condition is sourced the way `SKILL.md` fixes it rather than inferred: the operator's declaration at scope time, a store the data-flow map names, or an artifact that plainly carries personal data - an authentication table, a store of customer documents, an index built over them. Where none of those establishes it, **each of those bands drops one level and the row reports the copy as unreached with its contents undocumented** - a copy no deletion path reaches is a true finding whatever is in it, while the same row called Critical asserts that personal data survived a deletion request on the strength of an index existing, which is what `SKILL.md` withdraws rather than downgrades. The bands about the mechanism - an untested path, a hardcoded store list - are about how the path is built rather than about a payload, so they stand whatever established the surface.

**Critical** - no deletion path at all, where a personal-data surface is established. The path is a feature to build before anyone asks for it, and this band is why: written on the day of the request it is written by whoever is on call, against the stores they can remember, under time pressure, and nobody can tell afterwards which copies it missed. This band asserts nothing about a copy surviving, so the drop rule above cannot phrase its downgrade - it takes the same handling `data-protection/data-flow-map` gives the absent map instead: where nothing but a field name or a path establishes a surface, the row is **Important** and reports that no deletion path exists and the surface is undocumented, never Critical. The absence is worth reporting either way; a Critical resting on an invented surface is not.

**Critical** - a path that reaches the primary store and misses a derived copy, which is a deletion in name only. Name the copies in the finding, because they are the substance of this check and none of them look like a row: embeddings and the vector index, cached model responses, stored traces and run records, eval datasets and the fixtures somebody once extracted from a real case because it reproduced a bug, and backups. An embedding of a personal document is personal data, and deleting the document does not empty the index. Some of these copies exist because good practice asked for them - a run record is observability doing its job, a dataset built from real inputs is evaluation doing its job - which is why they are the last place anyone looks, and the rest arrived as an implementation detail of something else, which is why nobody has them on a list. **The finding is that the path does not reach the copy, and never that the copy should not exist:** deleting a run-record store or an eval dataset to shorten the walk destroys evidence two other practices require, and removing a store from the data-flow map or the processor register makes the walk look complete while the data stays exactly where it was. Neither is a fix, and neither is the audit's to make.

**Important** - a complete path with no test, so nobody can know it works before the day it matters, and that day is the one on which somebody has asked and the answer has to be true. An untested walk is also the shape that rots fastest, because nothing fails when a store is added and the path is not extended.

**Minor** - a tested path whose store list is hardcoded rather than derived from the map, so the two lists drift the moment a store is added and nothing anywhere fails when they do. The path works today; the row is that its correctness rests on somebody remembering two places instead of one. **This band needs a map to exist.** Where there is none, it raises nothing and the report cites `data-protection/data-flow-map` instead: with no map there is trivially no list to derive from, so a row here would report that check's gap a second time and address its fix to an artifact nobody has yet.

## Tooling fallback

No tool decides this check: the question is whether one walk covers a list, and a scanner that could find the delete calls could not tell you which stores it should have found and did not. So this is a reading pass.

**Take the store list from the store axis of the derived personal-data surface `SKILL.md` builds once in `audit-core` step 1**, under the engine's rule that a shared ground-truth artifact is built once and consumed rather than rebuilt inside each agent. Take it from that artifact and **not** from `data-protection/data-flow-map`'s output, which is not available to this agent. `SKILL.md` names that axis's evidence, and **that axis is the reach list** - every store it records, including ones the copy enumeration in the bands above does not name, a search cluster built over customer documents or a queue among them. The copies named there are the ones a path built around the record misses most often, not a closed set, so a walk covering them is not thereby a complete walk. Say in the row which stores the enumeration produced and which the pass could not read, so a copy nobody looked at is visible as unexamined rather than counted as reached.

Then read three things against that list. **The deletion entry point** - an API handler, a management command, a scheduled job - and which stores it actually touches, store by store, so the finding is about reach rather than about existence. **The test suite**, for a test that asserts the walk rather than one that deletes a row and checks the row is gone. **The derived copies specifically**, because they are where the reading pass earns its cost: the code that writes an embedding, a cache entry, a trace or a fixture is usually not the code that writes the record, so a path built around the record will not mention them.

**The audit reads the path; it never runs it.** Walking a deletion against real data to see how far it reaches destroys the data this check exists to protect, and a deletion is the one finding that cannot be re-derived once it turns out to have been wrong. The evidence is the code and its test, and where those are not enough to decide reach the row says so.

**State the boundary, because it is the half no clone holds.** What a deletion actually did downstream - whether a provider deleted its retained copy, whether the backups holding the record have aged out - is outside the repository, so status follows `SKILL.md`'s rule for choosing which one carries the annotation. Where the repository records the mechanism and the window - a provider's deletion request and its published window, the backup rotation and its age - the clone read the record and cannot read its execution, which is `warn (unverifiable-from-here)`, naming the provider's own deletion confirmation and whoever operates the backups as what would settle it. Where nothing records either, the absence of any account of the downstream copies is readable and the clone has settled it, so that is a plain `violation` with no annotation, banded as the copy the path does not reach - Critical where an artifact establishes personal data in it, Important where nothing documents its contents, by the drop rule above. Neither case is ever `ok`. The provider row here is the provider's response to an erasure request, its deletion confirmation, and not the standing retention window it publishes - that is `data-protection/processor-register`'s recorded field.

## Fix

Build the deletion path as a feature that walks the map, so the store list has one definition and the path and the map go stale together rather than quietly apart - which is also why the map comes first, and why its absence is `data-protection/data-flow-map`'s finding rather than a reason to skip this one. Test the walk rather than the row: seed a record together with its derived copies, run the path, and assert each copy is gone. Where a copy cannot be deleted in place - a backup that ages out, a provider's retained copy - record the mechanism and the window instead, which is an answer rather than a silence and is what lets a request be answered in the form "gone here, and gone there by this date".

Two things this fix is not, and both are ways a deletion check turns into the risk it was reading for. It is not a deletion the audit performs to demonstrate the gap or to close it; the audited team runs deletions against its own data. And it is not the removal of a store, a dataset or a fixture from the code, the map or the register in order to make the walk complete - a copy the path cannot reach is a path to extend, and whether a store should exist at all is a decision for whoever owns the data, informed by `data-protection/retention-limits` rather than by this row.

**The other half of this section is that check's.** This one reads whether a deletion triggered by a request walks the derived copies, and whether a test asserts the walk. A store can fail both, and they are two gaps with two mechanisms, so say which one a row is about. The backup schedule's **window** is a retention limit and its **aging out** is this check's downstream boundary, so the missing window is reported once, there.

## Review lens

**Derived-copy reach** - the row enumerates which copies the path reaches and which it misses, and cites at a `file:line` relative to `target_root` rather than to any scratch copy the code that reaches each one it reports as reached, so a path called complete is checkable against the tree the audited team has.

**Test substance** - a test counted as covering the path asserts the walk over the stores rather than that one delete call returned. A test that would still pass with the vector index untouched is not evidence about this check, and citing it as coverage reports the gap this check exists to find as closed.

**Non-destructive remediation** - no row here recommends deleting data, dropping a store, or removing an entry from the data-flow map or the register, and no finding rests on a deletion the audit ran. A record about deletion that licenses either has become the risk it was reading for.

**Walk coverage** - the row names which stores the enumeration produced and which of them the pass could not read, so a walk over a short list is visible as a short walk rather than as a complete one. A path reported as reaching every copy is checkable only against the list it was judged over.
