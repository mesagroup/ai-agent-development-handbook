# CLAUDE.md

## Commands

```bash
uv sync --group dev
git config core.hooksPath .githooks   # once per clone; git does not do it for you
uv run pytest tests/ -q
uv run ruff check . && uv run ruff format --check .
uv run python scripts/render_handbook_traceability.py --check   # integrity gate
uv run python scripts/render_handbook_traceability.py           # regenerate the matrix Markdown
uv run python scripts/render_handbook_artifact.py               # needs the d2 CLI
uv run python scripts/render_python_fixture_expectations.py --check   # integrity gate
uv run python scripts/render_python_fixture_expectations.py           # regenerate the fixture expectations
uv run deptry .                                                       # dependency hygiene gate
uv run python scripts/build_python_fixtures.py --all                  # generate the five gitignored fixture trees
```

Run `ruff check` AND `ruff format --check` before committing. CI runs both.

`.githooks/commit-msg` refuses a commit message carrying an AI attribution trailer, and `core.hooksPath` is what makes git run it, so a fresh clone that skips that line has the rule in prose only. The rule itself is that no commit in this repository carries one, and it is a hook rather than a convention because prose was not enough: a harness injected an attribution instruction mid-session, declaring that it superseded earlier attribution guidance, and six commits were written with the trailer before anyone reading the log noticed the branch had changed convention. The hook names the assistant rather than the `Co-Authored-By` key, so a human co-author trailer still works; it matches only at the start of a line and skips comment lines, so a message discussing the convention is not caught by mentioning it; and a deliberate exception is `--no-verify`.

## Repository layout

- `docs/engineering/` — the handbook. Normative prose, ten parts.
- `docs/audit/handbook-traceability.yaml` — the matrix. Source of truth.
- `docs/audit/handbook-traceability.md` — generated. Never edit it; edit the YAML and re-render.
- `docs/audit/sweep-obligations.md` — hand-maintained, unlike its neighbour: one row per `audit-core` obligation, recording how the `audit` sweep discharges it. Editing `audit-core/SKILL.md`, a file under `audit-core/references/`, or `audit/SKILL.md` means checking it. `tests/test_sweep_obligations.py` catches a row whose anchor no longer occurs in `audit-core` exactly once, a quotation that is no longer verbatim, and a row that has slipped out of the checked set; it cannot judge whether a disposition is still true, which is a reading pass over the whole of `audit-core`.
- `docs/audit/python-fixture-expectations.md` — generated. Never edit it; edit `scripts/python_fixture_spec.py` and re-render. The seeded fixture trees and this record come from that one module on purpose: expectations kept in a second file are free to drift, and a seed present in the tree but missing from the expectations reads exactly like a tool that correctly found nothing.
- `.agents/skills/` — the audit skill family: `audit`, `audit-core`, and nine `<domain>-audit` skills.
- `.agents/skills/<domain>-audit/checks/<slug>.md` — one check record per auditable check.
- `.agents/skills/audit-core/references/` — the two sections of the engine that most runs never read: the remediation half of the loop, which only a report + fix run reaches, and the authoring guidance, which no run reaches at all because it addresses whoever writes a skill. `SKILL.md` points at each with the condition for reading it, and `tests/test_audit_core_references_are_reachable.py` holds that a reference is linked, resolves, and is not also still inline. The ledger's anchors search this directory too, so an obligation that moved here has not vanished.

## Plugin

This repository ships as a Claude Code plugin (`.claude-plugin/`). Three things read as oversights and are deliberate:

- `plugin.json` declares no `version`. Claude Code then falls back to the git commit SHA, so every install tracks every push. Adding a version pins consumers to it.
- `"skills": "./.agents/skills/"` is a custom path. Moving the tree to a conventional `skills/` means editing `SKILLS_DIR` in two scripts, every check record's path, the test fixtures and the integrity gate.
- `claude plugin validate` checks the manifest and does not enumerate skills, so it passes on a plugin that discovers none. `claude plugin details handbook-audit` does print the skill count — but it reads the **installed marketplace clone** under `~/.claude/plugins/marketplaces/`, which tracks a pushed commit and is usually behind. So it cannot see a skill added on an unmerged branch, and reporting its count as this branch's is how a working skill gets called undiscovered (or a broken one gets called fine). Two sound checks instead: `uv run python -c "import sys; sys.path.insert(0, 'scripts'); from audit_checks import SKILLS_DIR, load_checks; c, e = load_checks(SKILLS_DIR); print(len(c), e)"` proves the records parse from *this* tree, and the running session's own available-skills list names a newly written skill within a turn or two of the `SKILL.md` landing, which is the only live evidence that its frontmatter parses as a skill rather than as a file. Re-run `claude plugin details` after the merge, where it is the right tool.

The repository is private, so the absolute GitHub URLs the skills emit resolve only for members of the owning organisation. Audit reports handed to an outside reader will carry links that reader cannot open.

## Task management

This repository uses the `github-issues-workflow` skill. An issue per unit of work, a branch named `<number>-short-description`, `status:*` labels tracking progress, `Refs #<number>` in commit messages, and a PR that closes the issue. Never merge without explicit approval.

The tracker is held against [`docs/goal.md`](docs/goal.md): every issue body carries a `**Serves:** O<n>` line naming one of its outcomes, a batch's queue is composed in the outcome order there, and something found while implementing goes under `## Found, not fixed` in the pull request body rather than into a new issue, to be triaged when the batch closes. An issue that can name no outcome is a question for the maintainer, not a line to leave out.

The `status:*` labels exist in the repository and are not decorative: move the issue as the work moves, removing the previous status before adding the next.

## Issue references and provenance

The handbook, the skill family and this tooling were extracted with `git filter-repo` from the origin repository, whose name lives in the engagement's own records and never here. That repository keeps the build record and the PRs. Three placeholders stand for it in this tree: `<origin-repo>` resolves to its `owner/name`, so `<origin-repo>#NNN` is one of its issues where a bare `#NNN` is one of ours; `<origin-package>` resolves to its top-level Python package, as in `--cov=<origin-package>`; and "origin-specific" means specific to that repository. Always write the two bracketed ones inside a code span: outside one, Markdown reads `<origin-repo>` as an HTML tag and renders it as nothing, so `<origin-repo>#543` in bare prose shows as `#543` and points at the wrong tracker. The dated specs, plans and stories were swept to these placeholders on 2026-09-15 as a deliberate exception to never rewriting them, so a plan's commit template shows `<origin-repo>` where the commit it produced spells the name. Commit messages from before the split are immutable history this rule was not yet written for; a bare number in history is a number in this repository.

Path-based history surgery matches *historical* paths. A file renamed out of a directory needs that directory in the allowlist or its history truncates at the rename, with no error to tell you.

## Toolchain

- ruff's `extend-exclude = ["docs"]` is load-bearing. Recent ruff formats Python inside Markdown fences, and specs, plans and stories are a record of what was written at the time; reformatting their samples edits that record.
- `scripts/render_handbook_artifact.py` imports `markdown` lazily, so a missing dependency surfaces when the renderer runs rather than at import. It is declared in `pyproject.toml`; a lazy import is not a reason to leave one undeclared, and `deptry` now fails CI on one - that import is the case the gate's non-vacuity test undeclares, because a function-level import is exactly what a reader might expect the tool to miss.
- The artifact renderer reports `residual .md hrefs: 0`. A relative `.md` link out of the handbook tree (only `engineering-notes.md` today) is *unlinked* rather than mapped - it prints a `NOTE`, keeps the link text and drops the anchor, because a self-contained page cannot link to a file it does not contain. A *sibling* `.md` link naming no part still raises.
- Diagrams need the `d2` CLI.

## Check records

Every check is one Markdown file with YAML frontmatter: `id` (`<domain>/<slug>`), `domain`, `locality` (`local` or `global`), `handbook` (list of matrix row ids, may be empty), `handbook_note` (required when `handbook` is empty), `optin` (default false), an optional `evidence` carrying what the check measures and what a row records as its evidence, where that belongs to the check rather than to any one route, and one of two mutually exclusive schemas naming what the check runs - a record carrying both is rejected. The legacy schema is `tooling` (optional), `needs` (optional; maps `resolved-tree` or `target-execution` to tool names drawn from `tooling`) and `ungranted_note` (required exactly where every tool in some language carries a tier, rejected as vacuous elsewhere). The routes schema is `routes` (optional, and rejected empty where present; a list of mappings, each one way of answering the check in one language, carrying `lang`, `kind`, `tool`, an optional `package` where the installable differs from the tool's name, `registry` (the registry a one-shot runner must reach to fetch the tool, `pypi` or `npm` and nothing else, rejected on any kind but `command`, rejected beside `own_runner: true` because that says nothing is fetched, rejected where it contradicts what `lang` implies since a `lang: python` route on npm is a wrong `lang` rather than a foreign registry, and required exactly where `lang` is `any` or `none` on a command route whose command is not complete as written - there and only there does nothing else in the record say which registry to reach, and a consumer left to infer it from the partition runs whichever package that registry happens to carry under the same name, which is a working wrong tool rather than a missing one; `registry_for` derives it in one place, answering which registry a fetch would have to reach rather than whether this route needs a fetch - 26 of the 56 command routes that get an answer need no fetch, because a package-manager subcommand is run directly and a runner-led argv already spells its own, so a caller reading a non-empty answer as "put this runner in front" produces `npx npm audit`; deciding that is the three-kinds question and no field answers it yet), `argv` (rejected on every kind but `command`, and on a command route required only where no `argv_by_partition` stands in for it - the loader rejects a command route carrying neither, and an absent shared `argv` beside a per-partition map is how a record says the partitions the map does not name have no command at all, which an empty `argv` cannot say and which two records now need), `argv_by_partition` (a mapping of partition name to that partition's own command - except where the runner rule in `audit/SKILL.md` redirects it, since a partition key names a package manager rather than a version of one, so a `yarn`-keyed entry spelling `dlx` is Yarn Modern's form and a Yarn classic partition runs the shared `argv` instead - where a target's partitions split along more than the tool invocation itself - a python route's partitions are `uv`, `pip`, `poetry`, `pipenv` and `pylock`, and only four of those name a package manager), `then` (a second command the record prescribes in sequence, where it does - `coverage run -m pytest` followed by `coverage report --show-missing` is one route rather than two, and dropping the half that prints the report leaves a route that looks like a tool which produced nothing), `own_runner` (the prescribed command is complete as written, so whatever one-shot runner a lens would put in front of it puts nothing: `true` where every command the route prescribes needs none - its shared `argv` and its per-partition overrides alike, or, on a route carrying no shared `argv`, the commands its map names and nothing else, since those are every command it prescribes - or the partitions whose override needs none where the rest do - `false` and an empty list are both rejected rather than read as the default, because an absent key already says the launcher applies, so writing the field is a claim, and each of those two is that claim spelled as nothing at all), `disposition`, `needs`, `in_env`, `findings_stream`, `applies_when`, `alone_insufficient` and `note`) and `answers_ungranted` (`ungranted_note`'s counterpart: the sentinel `none`, required wherever a language's every answering-kind route needs a grant and none stays untiered). A record declaring `routes` carries no `## Tooling fallback` section and the loader rejects one: the routes are the fallback there, and a section beside them is a second copy nothing holds against the first. A migrated record's `tooling` and `needs` are derived from its routes by projection, so a consumer reading those two fields sees the same shape regardless of which schema the record declares - but the projection carries the tools and their tiers and carries no ungranted claim at all, so whether a withheld grant silences a language is never derived from the projected pair on a migrated record. That question is decided over the record's answering-kind, non-`forbidden` routes, where a `kind: subject` route neither gives a language a claim to silence nor supplies one's escape, and the projection keeps such a route's tool with its tier - which is how a language every route in was only ever inspecting the check's subject reads through the pair as fully tiered. A route naming no tool carries a non-empty `note` and the loader rejects one that does not: with neither a tool nor an argv the note is the whole prescription, and this is the one route kind where nothing else in the record stands in for it, so a note-less one reads through the projected pair and every set guard over the family exactly like a route that works. The projection also collapses a record's routes onto their tools, so a tool carrying one tiered route and one untiered one reads through the projected pair as simply tiered - which is why whether any *tool* still answers a language once the grant is withheld is read per route too, over those same answering-kind, non-`forbidden` routes and counting only the ones that name a tool. That reading and the silencing one bracket three states rather than two: a language keeping an untiered route that names a tool is unaffected by the grant; one whose tools are all tiered but which keeps an untiered reading answers something different and has to say what; one with no untiered answering route at all is silenced and says so with `answers_ungranted`. The two are deliberately over different sets, and collapsing them into one question makes the middle state unreachable.

A record declaring neither `tooling` nor `routes` must state in its body what to read instead.

`needs` is the second axis on a tooling name, on a record still declaring `tooling` directly rather than `routes`. `tooling` says where a tool comes from; `needs` says what must be present in the target before it answers - nothing beyond a read-only clone by default, a materialized dependency graph for `resolved-tree`, that plus running the target's own code for `target-execution`. The names repeat those in `tooling` on purpose and the validator checks the repetition, so a rename that misses one of the two places fails the gate. An omitted tier is a positive claim that no tool here needs it, which is why a record left unclassified reads as clean rather than as unfinished. Two guards in `tests/scripts/test_audit_checks.py` bound that, each covering what the other cannot: `test_a_tool_has_one_tier_across_the_family` catches a tool two records classify differently, and `test_the_classification_is_not_vacuous` holds the number of records carrying `needs` at the number the sweep and the migration between them produced, so removing a key fails the suite instead of quietly reading as the default - most of that population is projected out of routes rather than written as frontmatter now, which is why the floor is the guard and a grep for the key is not. What neither can see is a record that was never examined and genuinely needs a tier — the first is silent unless another record already classified the same tool, and the second only counts. That one is a reading pass. A route states the same tier directly as its own `needs` field, one axis on the route itself rather than a second mapping kept in step with a first.

`ungranted_note` is the third claim on a record still declaring `tooling`, and it is about the check rather than about a tool. `needs` says what each tool requires; the engine turns that into a conclusion about the check — every tool needs a grant, so a withheld grant means `no-evidence` — and that derivation is wrong wherever the check has an axis needing no tool. Five records had resorted to contradicting their own frontmatter in prose before this field existed. It is required on exactly the records the rule would silence and rejected as vacuous elsewhere, so absence is never a silent claim the way an absent `needs` tier still is. The value is either what still answers or the sentinel `none`; the loader rejects `None`, `NONE`, `null` and an empty value by name, because YAML turns the first two into ordinary strings that read as a fallback claim and the last two into nothing at all. `tests/scripts/test_audit_checks.py` holds a floor on how many records say something real, which is the only guard against satisfying the requirement with `none` everywhere — it cannot tell a correct `none` from a lazy one. The floor counts both spellings of the claim, because they are one property wearing two schemas, and the legacy half of it has no members at all: this field is required exactly where every tool in some language carries a tier, and no record still declaring `tooling` has such a language, so the requirement fires on nothing and everything the floor counts is on the routes side. What it counts there is not `answers_ungranted` - a record carrying that sentinel is one where nothing is left to answer, so the floor excludes it by construction, the same way it excludes `ungranted_note: none`. It counts a language whose answering routes are all tiered except an untiered one that still answers, which is the routes schema's way of saying what a non-sentinel `ungranted_note` used to say in prose. Read the legacy half's emptiness as where the field has got to rather than as a reason to stop describing it: a record written on the legacy schema brings the rule back into force as soon as it has a language whose every tool carries a tier, which is a shape several existing records are one tier away from. `answers_ungranted` is this field's counterpart on a record declaring `routes`, required by the same rule applied per route rather than per tool: a `kind: subject` route never counts toward a language's claim to silence, and a `disposition: forbidden` route never counts as its escape.

A `tooling` list, on a record declaring `tooling` rather than `routes`, holds candidates for the language, not commands guaranteed to run on a given partition - at most one package-manager subcommand in it applies to any one partition, and `## Tooling fallback` states which and in what order. Every candidate must still be something *some* partition in that language can run, which is one of three kinds: a registry package a one-shot runner can fetch, a subcommand of the target's own package manager, or a standalone binary in no language registry. Only the first is fetchable, so an entry of the second or third kind that the record does not distinguish gets attempted as a package, fails like a missing tool, and reports `no-evidence` for a check that could have been answered. Never name one ecosystem's package manager as if it were the language's - `npm audit` is not the JavaScript audit command, it is npm's, and it resolves from a lockfile a pnpm or yarn target does not have. Where the kinds differ across package managers, `## Tooling fallback` states the precedence and names the ecosystem-neutral option. Verify a name against the tool's own documentation, not against whether a fetch succeeds: the unscoped `cyclonedx-npm` resolves to a dependency-confusion placeholder rather than to the CycloneDX generator, which is `@cyclonedx/cyclonedx-npm`, so a runner fetches it, runs it, and produces nothing - indistinguishable from a tool that ran and found nothing. A route names its kind directly - `command`, `library`, `procedure` or `subject` - names the registry a fetch has to reach as its `registry`, and states precedence as its `disposition` and its position among the record's routes, so none of the three depends on `## Tooling fallback` prose there, and the ecosystem-neutral option this paragraph tells a `tooling:` record to name in prose is a field on the other schema.

Every review-lens paragraph carries a `**Label** - ` prefix.

**Every command a record prescribes appears in an inline backtick span**, because that is the only place the form extractor in `tests/scripts/test_python_fixture_harness.py` reads. A command written anywhere else is invisible to every property that holds a record's prescription against what actually ran, and the suite stays green over it. The loader rejects a fenced code block for that reason, in either spelling and at up to three spaces of indentation, which is CommonMark's own fence rule; a *four-space indented* block is not what it forbids, because its content is literal text, so a record may show a tool's observed output there even where that output prints fences. No record body carries one today - computed, zero of 84 - so that allowance keeps an escape open rather than protecting a use the tree makes. The remaining escape is a command written in prose with no backticks at all, which is an accepted limit rather than a parser to write: this convention is what makes it acceptable, and enforcing the fence is what stops the idiomatic way of hiding a command. Where a record glues a placeholder to a flag, a name must end at a value delimiter - `=`, `:`, `/` or `@`, so `--cov=<pkg>` and `pkg@<version>` but not `-r<file>` and not a bare `/<dir>` - because the harness matches such a token as a prefix, and `-r` is a prefix of other flags while nothing but `--cov=<pkg>` is spelled `--cov=`. Write the value as its own token where the command allows it, as `pip-audit -r <requirements>` does; where it does not, a placeholder in the middle of a value or inside single quotes, the shape has to change rather than the spacing. The delimiter rule judges the head alone, so what it does not buy by itself is unambiguity among values sharing a namespace - `@stryker-mutator/` is as true of `@stryker-mutator/core` as of the runner package, and both are named in that same command. What settles that is the text after the placeholder: a reduced token keeps the literals on both sides of every hole, so `@stryker-mutator/<runner>-runner` demands a token that also ends `-runner`, and each hole has to be filled by at least one character. A placeholder standing as its own token still drops out entirely, and one whose head does not earn a mark is still refused rather than matched loosely.

## Matrix and records are one edge set

A matrix row's `checks:` entry and a record's `handbook:` entry are the two directions of the same edge. Change one, change the other, or the gate fails. Add the citation and the row in the same commit.

Where a consistency property can move out of prose and into the validator, move it.

## Writing

- Markdown is never hard-wrapped: one paragraph is one source line. Never reflow lines you did not change.
- No em-dash (U+2014) in `docs/engineering/`, `docs/superpowers/specs/`, `docs/superpowers/plans/`. Use ` - `.
- Never commit environment-specific values: absolute personal paths, profile names, tokens, hostnames, emails. Use `<placeholder>` and say what it resolves to.
- Never name another specific project or repository in this organisation or in the Lidia one, in a tracked file or in the tracker. An audit target, a client system or a sibling project is a `<placeholder>` with a description of what it is; the real name lives in the engagement's own records. A repository name identifies an engagement, and this repository is shared beyond it.
- Links in `.agents/skills/` to files in this repo are absolute GitHub URLs, because the skills run from a plugin cache in other repositories where a relative path resolves to nothing. Everything under `docs/` links relatively: those files are read in the repo or on GitHub, the plugin does not ship them (`plugin.json` points only at `.agents/skills/`), and an absolute URL bakes the org and repo name into every report and artifact the file is copied into.

## Prose about the code — write claims that cannot go stale

- Name a thing, don't number it: "the `checks` argument", not "the fourth argument".
- State the structural reason, not the current snapshot.
- Never assert a count you did not compute. Compute it in the same breath, or state no number.
- Avoid claims about a sibling ("every other check does X"). Verify as you write, or rephrase so the claim is local.

## Stale-prose pass — scope by blast radius, not by the diff

Before pushing, make one pass for prose the change invalidated **without touching**. Do not scope it to the diff.

- Removed or renamed a symbol, parameter or field? `grep` for its name and for the prose describing it.
- Changed what a fixture or helper produces? `grep` for its name and read every comment near a caller.
- Changed a shape, invariant or default? Read the whole file, not the hunk.

Dispatch it to a subagent that has not seen the implementation.

When dispatching any agent from a git worktree, pass the worktree's absolute root and require the agent to confirm `git rev-parse --show-toplevel` matches before it reads or edits. Agents left to infer the path resolve it to the primary checkout instead: a reader then reports evidence from a tree you are not working in, and a writer's edit lands where your `git status` never shows it, so it drops out of the commit and afterwards looks as though the agent simply missed the file.

## Tests

New code ships with unit tests, and adding code must not lower coverage. Scripts are not exempt: load them with `importlib.util.spec_from_file_location` and exercise their pure helpers, with `scripts/` on `sys.path` via `tests/scripts/conftest.py`. A new module in `scripts/` also joins `[tool.deptry] known_first_party` in `pyproject.toml`, because the modules there import each other as top-level names and `deptry` reads such an import as a missing dependency; `tests/test_deptry_gate.py` holds that list against the directory, so the failure is a red local test rather than a surprise in CI.

Mutation checks against `scripts/run_python_fixture_lens.py` run with `PYTHONDONTWRITEBYTECODE=1`. `.pyc` invalidation compares the source's mtime and size, and some of the mutations this table invites move a token between fields without changing either, so a mutate-run-revert inside one second can leave the next run honouring the mutant's cached bytecode. It shows up as a failure on a byte-identical clean tree, or, in the direction that matters, as a green run over a mutation that should have failed. A mutation that does change the file's length is not exposed to it, which is why the instruction is the flag rather than a judgement about each mutation.

## Errors

No bare `except Exception: pass`. Every exception is reported to the caller with type and message, logged at the right level, or re-raised.
